# Benchmark

Measures what Model Router costs per solved task, and how often tasks get solved, against Claude Code without it. Results go to [docs/BENCHMARKS.md](../docs/BENCHMARKS.md). Standard-library Python only. Nothing here ships with the plugin.

Every stored row measured an older design, in which the router read the brief and picked the level itself (`plugin_ref` 780ee86 for the tables, `bench_commit` c42886d for the pilot). On the six harder pilot tasks that router cost more per run than `defaults`, Claude Code with no plugin. Today's plugin, where Claude names each call's model and effort, has not been benchmarked yet.

- `tasks/<id>/`: one task each. `task.json` gives its class, brief and `revision`. Raise the revision, with a line in `revisions`, whenever a change could change a run's outcome; every row records it, and rows on an earlier one are left out of the tables. A change to a check keeps the revision only when it can't move any recorded verdict (where the work dir is gone, the commit body shows why no verdict can move). `repo/` is the fixed set of files a run starts from. `check.py <workdir> <answer-file>` exits 0 when the task was solved, 1 when it wasn't and 2 when the check itself broke: `run.grade` starts every check through a launcher that turns an error the check raises into 2, so a bug in a check can't read as a wrong answer. It returns the verdict, a reason (the last line printed) and a hash of the check's code. Checks share `tasks/passcheck.py`; `run.py` runs them with `python -I`, so neither the check's folder nor the work dir is on `sys.path`, on a throwaway copy of the work dir with the cwd in a scratch folder under `run.RUNS`, which is also the check's temp folder, so code a run left behind can't write into the checkout or the results and no other run can read the copy. A socket, a pipe, or a file or folder the run made unreadable is left out of that copy, so it reads as missing and fails the run instead of breaking the check. A work dir the run made unreadable gets its owner's access back first, so the check grades what it holds. `solution/` (for tasks that change files, or write the DESIGN.json, RESEARCH.json or FINDING.json the brief asks for) or `reference_answer` (for a lookup answered in the reply) is a known-good result, and `tests/test_bench.py` checks that each check fails on `repo/` as shipped and passes on it. `wrong/<name>/` and `right/<name>/` hold files laid over `repo/` and `solution/` (`answer.txt` is the reply and isn't copied, `remove.txt` lists paths to delete); a test asserts that every `wrong/` fails and every `right/` passes, as a verdict and never as broken. A `wrong/` folder can hold an `expect.txt`, a substring the check's reason must contain; one without it must fail as "the check exited 1".
- `configs.json`: the configurations. `plugin` is the router with today's defaults and `plugin-nogate` the same with `verify_gate` off; both load with `--plugin-dir`. `plugin` carries `"judged": true`, which makes it the router the tables judge (`analyze.py --router` picks another). `plugin-next` is an older build kept for its stored rows (`plugin_ref`). `defaults` runs Claude Code with no plugin. `pinned` has no plugin and defines three agents inline with `--agents`, each on a fixed model and effort: `searcher` on Haiku at medium, `worker` on Sonnet at medium and `reviewer` on Opus at high. Its `delegate` prompt names the three, since the main loop could otherwise pick `general-purpose`, and a per-call `model` or `effort` on the Agent call outranks an agent's own (https://code.claude.com/docs/en/sub-agents). `<model>-<effort>` (haiku, sonnet and opus at low, medium and high) forces every subagent onto one model with `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` and `CLAUDE_CODE_SUBAGENT_EFFORT`, which needs Claude Code v2.1.257 or later; `haiku`, `sonnet` and `opus` force the model at its default effort. Forcing makes Claude Code ignore the `model` field in subagent definitions, but a fork, and a skill that runs in a subagent with `model: inherit`, still run on the parent's model (https://code.claude.com/docs/en/sub-agents#run-every-subagent-on-one-model). `session-<model>-<effort>` runs the whole session on one model and effort (`--model`, `--effort`) with nothing forced. `sonnet-via-opusplan` runs `--model opusplan`, which runs Sonnet throughout a headless `dontAsk` run; its rows were recorded as `opusplan`, and `was` maps them. `advisor` adds `--advisor opus`. `price_model` names the model a configuration's subagents mostly run on. A configuration with `"plugin": true` is a router variant: its `plugin_options` go in through `--settings` as `pluginConfigs` (project settings can't set plugin options), and `analyze.py` gives it its own column but never makes it a baseline. So do the six variants that only archived rows hold (`analyze.ARCHIVED_ROUTERS`). The plugin keeps three options, `routing_mode`, `max_tier` and `verify_gate`, so no configuration sets any other.
- `run.py`: runs each task under each configuration with `claude -p --output-format stream-json --verbose`, checks the result, and appends one JSON line per run to `results/`.
- `analyze.py`: computes each cell's pass rate (exact 95% binomial interval) and cost per solved task (95% bootstrap interval), one verdict per baseline on each class row and on an `all tasks` row, and whether each class's tasks tell models apart, and writes `docs/BENCHMARKS.md` below the page head, which `tools/docs_assets.py` writes. It gives docs_assets the docs' figures (`figures`, keyed by role: the router, Claude Code's defaults, the cheapest baseline and the strongest forced one) and the yes/no facts the docs' prose states (`PROSE`, `FACT_TEXT`); `--check` fails when one stops being true.

## What a run is

Each run gets a fresh copy of the task's files in a temporary directory, never the repository, and a Claude Code config folder of its own inside it (`CLAUDE_CONFIG_DIR`, with `CLAUDE_CODE_PROJECT_DIR_NAME=run` so its transcripts land in `projects/run/`). So `~/.claude.json`, user settings, plugins, the router's data folder and transcripts never come from the machine's own, and all of it goes when the run's folder does. Because a Keychain login is keyed to the config folder, `run.py` refuses to start without `CLAUDE_CODE_OAUTH_TOKEN` (make one with `claude setup-token`) or `ANTHROPIC_API_KEY`, or a `CLAUDE_CODE_USE_*` provider switch. Managed settings still load from the machine. Every row lists the managed settings files and the macOS plist it found in `managed_settings`. Server-managed settings, which claude.ai sends to an eligible login, and the Windows registry policy can't be seen that way, and the stream doesn't report them, so an empty list doesn't prove no policy applied (https://code.claude.com/docs/en/managed-settings.md).

Subagents run commands. `Bash` is allowed plainly, and one `--settings` JSON runs it inside the OS sandbox with `sandbox.enabled`, `sandbox.autoAllowBashIfSandboxed`, `sandbox.allowUnsandboxedCommands: false` and `sandbox.failIfUnavailable` (https://code.claude.com/docs/en/sandboxing, https://code.claude.com/docs/en/settings-reference). Writes stay in the work dir and the temp folder, and there is no network. `sandbox.credentials` denies reads of credential folders (`~/.ssh`, `~/.aws`, `~/.claude` and others in `run.CREDENTIAL_FILES`) and unsets every secret variable before each sandboxed command (only names the settings accept: a letter or `_`, then letters, digits and `_`). `sandbox.filesystem.denyRead` hides every place `run.answer_paths` knows to hold answers or graded runs: this checkout, whose `check.py`, `solution/` and `right/` folders hold the answers, the repository's git data and main checkout, every worktree `git worktree list` names, Claude Code's shared temp folder `/tmp/claude-<uid>` (other sessions copy files there) and, when the harness's own environment sets `CLAUDE_CODE_TMPDIR`, `$CLAUDE_CODE_TMPDIR/claude-<uid>`, the results file's folder and `--keep`. It also hides `run.RUNS` (`/tmp/mrb-<uid>`, in its `/tmp` and `/private/tmp` forms), which holds every run's scratch copy and every copy a check grades, and `allowRead` re-opens the run's own. `CLAUDE_CODE_TMPDIR` is set to that scratch copy, kept under about 30 bytes since Claude Code falls back to the shared folder for a longer one, so the run's sandboxed commands get a temp folder of their own (https://code.claude.com/docs/en/env-vars). The file tools get no blanket approval: `--allowedTools` is `Bash` and `Edit(./**)`, so in `dontAsk` mode Read, Grep and Glob read only the work dir and Edit and Write change only it. The same `--settings` JSON adds `permissions.deny` rules `Read(//<path>/**)` and `Edit(//<path>/**)` for the paths above (https://code.claude.com/docs/en/permissions), and `PWD` and `OLDPWD`, which can name the checkout, are dropped. A clone that is not a worktree of this repository is not hidden. `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is not set: it would strip `CLAUDE_CONFIG_DIR` from the router's hooks and turn auto-allow off. On Linux the sandbox needs `bubblewrap` and `socat`; where it can't start, Claude Code refuses to run instead of running unsandboxed. The runner also loads no CLAUDE.md, auto memory or MCP servers, and drops any `CLAUDE_CODE_*`, `CLAUDECODE`, `CLAUDE_PLUGIN_*` or `CLAUDE_PROJECT_DIR` variable it inherits, except `CLAUDE_CODE_USE_*` and `CLAUDE_CODE_OAUTH_TOKEN`.

The prompt has two arms (`--arms`). `delegate`, the default, tells the session to hand the task to one subagent and relay its answer. `direct` sends the brief as a person would type it. Each row records its `arm`, and each arm gets its own table.

In the `delegate` arm a task's `shape` picks another prompt for its brief, and each row records it (`single` for a task without one, and for every `direct` row, since that arm sends the bare brief). Analyze takes accuracy by level from single-agent rows only, and gives a redo task's redo rate from `agents_started`: a run that started one agent type twice or more. `redo` lets it run the check the brief names and send the work back, `fanout` gives each question its own subagent, all started at once, and `plan-build` hands out the brief's steps one at a time, in order. `redo-failing-check`, `fanout-three-lookups` and `mixed-plan-then-build` use them. The `redo` class has one task so far, so its class verdict rests on that task alone. Its check is stricter than the `tools/check_changelog.py` the agent runs: it also turns down a line that carries a commit hash, a commit subject pasted from `commits.txt` or a commit-type prefix at its start, so a run can pass the visible check and still fail. What a line says is not graded, since every word list tried misgraded right lines, and a false fail here would count as a redo the work didn't need. CONTRIBUTING.md leaves out a rule that script enforces, so a first answer written from the doc fails it, but an agent that reads the script first can pass on the first try with no redo. Measure how often the first try fails (the page's redo rate) in a pilot before reading the class verdict. `mixed-plan-then-build` keeps `mutants.py`, six broken builds of the feature: each wraps the work's own `handle_post`, so every name the work defines stays, and the check fails a `test_idempotency.py` that still passes with one installed. Four of them charge a repeated key again, and one of those deletes the payment row it made, so a test must check the charges, not the payment rows. Another answers a retry without a charge but with a body unlike the first response's, so a test must check what the retry answers. Every extra charge goes through the work's own code, so a test that mocks the gateway where the work looks it up still sees it. DESIGN.json's reasons need only be non-empty text; what they argue is not graded. The brief asks for tests that send requests to `handle_post` and check what each one answers and charges for that reason. Its probe counts a charge when the work calls the gateway, so a charge the work's own rollback erases from `gateway_log` still counts, and it retries a request that died right after its first commit, so a key stored in a commit of its own after the payment's fails.

A batch copies `plugins/model-router` once when it starts and loads the router from that copy, so an edit or a checkout during the batch can't reach later runs. A router row carries the `plugin_hash` of the plugin it loaded (the copy, or for a `plugin_ref` the export of that commit), and a row with no plugin carries null, beside `bench_commit` (HEAD) and `bench_dirty` (uncommitted changes in `bench/` or the plugin). The run order is shuffled with `--seed`, a random one when it is left out, and every row records `order_seed` and its `batch` (`--batch`, else the start time and the seed). Processes started together pass the same `--batch`.

Each row reads the stream. The result is its last `result` line. A run that stopped before the session began (`claude_started` false) is set aside in `results/limited/` with `limited_reason` `no_start`. When the sandbox can't start, Claude Code writes an `error_during_execution` result with zeroed totals and `startup_failure_reason` `sandbox_required_unavailable` (https://code.claude.com/docs/en/agent-sdk/typescript); the row keeps that field. A run with that field is `no_start`, and so is one that exited on its own with no `system/init` event and either no result or an error result of 0 turns and no API status. It costs 0, since nothing reached the API. A run killed for a timeout or an interrupt is never `no_start`, since it may have spent. A router run whose `system/init` event doesn't list the plugin, or lists a plugin error, is set aside with `plugin_not_loaded`, since it measured Claude Code without the router (https://code.claude.com/docs/en/headless). So is a router run whose stream or transcripts show a subagent running while the ledger holds no `spawn` row, with `router_silent`: the router logs a spawn row for every call it sees except a fork's, so its hooks never acted (no Python 3.9 or later, a handler that fails every time, a data folder it can't write). The row's `router_silent` field records it. A run whose only subagents are forks is set aside this way too, since the router leaves a fork alone and logs no spawn for it. A router variant's `plugin_options` go in as `pluginConfigs` in `--settings`, which the settings reference scopes to user or managed settings without naming `--settings` (https://code.claude.com/docs/en/settings-reference#pluginconfigs). The plugin keeps no copy of its options, so a router variant's run is set aside with `options_not_applied` only when its ledger holds a row an option rules out: a `gate` row with `verify_gate` off, or a rewritten spawn with `routing_mode` off. `options_applied` records it: false for such a row, true for none, which is no proof the options arrived, and null for a configuration that sets none. `agents_started` counts the subagents started, by type, from the stream's Agent calls (a type that isn't 1 to 64 letters, digits, `_`, `.`, `:` or `-` counts as `invalid`, so model-written text never reaches the page), and `agent_overrides` the Agent calls that set their own `model` or `effort`. `agent_calls` lists each Agent call in order: its `agent`, the `named_model` and `named_effort` the call set itself (null for none), and `ran_on`, the model of the first message the stream shows the subagent sending (`parent_tool_use_id`), null when it shows none. Since Model Router keeps the model a call names and leaves a call that names none on its parent's model, the page counts how often Claude named each. A `delegate` run of `pinned` that used none of its pinned agents, used another agent, or set an override is set aside with `off_pin`. `permission_denials` keeps each denied tool with the first 200 characters of its input, beside `terminal_reason` and `errors`. A run that failed or had a denial keeps its transcripts in `transcripts/<results file>/` beside the results file, named in the row's `transcripts` (git ignores every `transcripts/` under `results/`); read them before trusting a check. A router row also carries `agent_costs`, its spend by agent type from Claude Code's estimate per subagent in the ledger (`main` is the rest of the run's total: the main loop, and agents with no estimate, such as workflow agents), `routed`, its spawn decisions in order (`agent`, `level`, `model`, `effort`, `source` and `escalated_from`, plus `on_record` when the ledger says false), and `gate_events`, the ledger's rows with event `gate`. A usage row names its agent's type, and the transcripts' `subagents/agent-<id>.meta.json` stand in when it doesn't. Every row carries `wall_ms`, the runner's clock around `claude`. `grade` holds the `verdict` (`pass`, `fail` or `broken`), the check's `reason` and its `check_hash`; `passed` is true only for `pass`, and analyze leaves a `broken` run out of the tables. `final_answer` keeps what the deleted work dir held, so a fixed check can be tried on recorded runs. A row's `schema` is `run.ROW_SCHEMA`, 3 now. Rows below 3 ran with an exact Bash allowlist that denied many test runs and with the machine's config folder, so `analyze.load` keeps them in `legacy`, apart from `rows`: they get their own tables under "Before the sandbox", judged on `analyze.LEGACY_ROUTER` (`plugin-next`), with no verdict or rank, and new rows under the same ids never pool with them. The docs' prose still quotes that stored run, so `tools/docs_assets.py` and `analyze.py --check` read `figures(results, legacy=True)`.

## Cost rules

Every run spends real money or subscription usage. `--budget` caps each run with `--max-budget-usd`, which a run can pass by one response plus what its running subagents spend before they stop. `--max-total` starts a run, and each retry of one, only with room for twice its cap (a margin, not a bound); with no room left the runner stops with exit code 1. Cost is Claude Code's `total_cost_usd`. A run with no result, a timeout or a crash, is priced from its saved transcripts at list price, each message once, and only when they hold no usage, or a message with tokens on a model the registry can't price, is it charged the whole budget; `cost_source` says `result`, `transcripts` or `budget`.

A run the API refuses for a rate or usage limit, or one that loses the network, is not a failed task. The runner pauses (1 minute, then twice as long each time), runs it again, and after 5 pauses stops with exit code 2, keeping every finished run. Limited runs go to `results/limited/`, so their spend is on record but out of the results. Any other error before a cent is spent (an invalid API key, a credit balance too low, a model the account can't use) goes there too, with `limited_reason` `api_error`, without a pause or a retry, as do a run that never started (`no_start`), a router run whose plugin didn't load (`plugin_not_loaded`), whose router never acted (`router_silent`) or that didn't get its options (`options_not_applied`) and a pinned run off its pins (`off_pin`); 3 such runs in a row stop the runner with exit code 2. A `no_start` row costs 0. A run that failed for the network before the runner caught it goes by hand to `results/infra/`, with `infra_reason`, and is run again. `results/archive/` keeps rows from older harnesses, out of the comparison.

## What a verdict means

The rule is fixed before any run. For each baseline the router gets one verdict on each row of a table: one row per task class, and an `all tasks` row over every task in the table. Its runs and the baseline's are paired by task, and each of 2,000 resamples draws the row's tasks with replacement, then each drawn task's runs with replacement. For the pass rate each task's runs get one solved and one failed run added, so a cell where every run passed still has spread. The non-inferiority margin is 10 points of pass rate.

- WIN: the 95% interval of the router's cost per solved task minus the baseline's is below zero, the lower bound of its pass rate minus the baseline's is above minus 10 points, and the router solved at least the baseline's share of runs (per-task pass rates averaged). A saving counts only at an equal or higher pass rate.
- LOSE: the router's pass rate is behind beyond noise, or it costs more per solved task beyond noise while the upper bound of its pass rate minus the baseline's is below plus 10 points (the mirror of the WIN rule).
- No difference shown: anything else, a cheaper router that solved fewer runs included. It is not parity, and the page never calls it a pass.
- No verdict: the two ran different tasks or in different batches, either has a row below schema 3, or more than a quarter of either's runs had a Bash call denied. A row with no verdict has no rank either.

A row is LOSE when any baseline beats the router, has no verdict when any comparison has none, and is WIN only when the router wins against every baseline. A class is saturated when the weakest forced baseline can't be told from the strongest by an exact one-sided test; then an equal pass rate there says nothing about quality.

A class with one task can't reach WIN: even at 10 runs with every run solved its pass-rate interval is about -25 to +25 points. The measurement plan below has 6 tasks, one or two per class, so its verdict is the `all tasks` row, where the 6 tasks resample together. With 6 tasks in 6 classes, every run solved and the router cheapest, the analyzer gives these lower bounds of the pass-rate difference against `defaults` and `haiku-high`: -12.5 to -14.6 points at 6 runs per task and configuration, -11.7 at 8, and -8.3 to -9.7 at 10. Only 10 runs give WIN (`tests/test_bench.py` checks these verdicts, with `pinned` as a third baseline).

## Running a round

Start with a smoke test of two `plugin` runs and read both rows: `permission_denials` should be empty, `plugin_loaded` true, and `agent_calls` should list each Agent call with the model and effort it named and the model it ran on. No page says whether sandbox auto-allow covers a background subagent's Bash in a `-p` `dontAsk` run. A row set aside lands in `$HOME/mrb-smoke/limited/smoke.jsonl`. Keep the smoke files in a folder of their own: every run's sandbox hides the results folder, and the runner stops before the first run when it can't write there.

```bash
export CLAUDE_CODE_OAUTH_TOKEN=...   # or ANTHROPIC_API_KEY
python3 bench/run.py --tasks rootcause-cart --configs plugin --runs 2 --seed 1 --batch smoke-1 --budget 1 \
    --max-total 4 --model claude-opus-5-5 --out "$HOME/mrb-smoke/smoke.jsonl" --keep "$HOME/mrb-smoke/keep"
```

Then read each run's kept transcript in `$HOME/mrb-smoke/keep/<run>/session/` and check that a sandboxed heredoc and a temp file written and read back both worked; a temp folder the sandbox can't read breaks them.

A calibration round finds the tasks that tell models apart: the five tasks of work that isn't code and the six harder coding tasks from the pilot under `haiku-high` and `defaults`, 2 runs each, 44 runs, about $8 at $0.26 a `defaults` run and $0.10 a `haiku-high` one.

```bash
python3 bench/run.py --tasks legal-services-agreement finance-ledger-reconcile finance-runway-forecast \
    research-study-synthesis ops-inbox-triage impl-merge-customers bugfix-statement-queries security-admin-route \
    rootcause-wallet-race cross-amount-cents design-checkout-retries --configs haiku-high defaults --runs 2 --seed 2 \
    --batch calibration-1 --budget 1.5 --max-total 20 --model claude-opus-5-5 \
    --out bench/results/pilot/calibration-1.jsonl
```

Keep a task when `defaults` solves at least 2 of every 3 runs and `haiku-high` at most 1 of every 3 (`analyze.splitting_tasks(rows, "defaults", "haiku-high")`). At 2 runs each, that is both `defaults` runs solved and neither `haiku-high` run. Two kept tasks are needed, from the 7 candidates outside the 4 fixed coding tasks of the measurement round. With fewer, swap candidates and run it once more; if that fails too, these tasks can't tell Haiku from Opus, and a verdict would favour `haiku-high` by construction.

A measurement round runs 6 tasks (4 fixed coding tasks, where the router should save money, and the 2 kept ones) under `plugin`, `plugin-nogate`, `defaults` and `haiku-high`, 2 runs each: 48 runs, about $16 if a router run costs what the old router's did in the pilot ($0.47), with $0.26 a `defaults` one and $0.10 a `haiku-high` one. `plugin-nogate` is a router variant, so the verdicts are against `defaults` and `haiku-high`, and its rows show what `verify_gate` adds. Read them first: a row set aside with `options_not_applied` says `pluginConfigs` in `--settings` didn't reach the plugin, and nothing in a row proves it did. Round 1, with the kept tasks in place of `<kept-1>` and `<kept-2>`:

```bash
python3 bench/run.py --tasks bugfix-statement-queries cross-amount-cents design-checkout-retries security-admin-route \
    <kept-1> <kept-2> --configs plugin plugin-nogate defaults haiku-high --runs 2 --first-run 0 --seed 3 \
    --batch measure-1 --budget 1.5 --max-total 25 --model claude-opus-5-5 --out bench/results/measure-1.jsonl
python3 bench/analyze.py bench/results/*.jsonl --out docs/BENCHMARKS.md
python3 bench/analyze.py bench/results/*.jsonl --out docs/BENCHMARKS.md --check
```

Run five rounds, on at least two days, every round with all four configurations. Rounds 2 to 5 change only `--first-run` (2, 4, 6 and 8), `--seed`, `--batch measure-<n>` and `--out bench/results/measure-<n>.jsonl`. Each round is its own batch, and since the router and every baseline ran in the same batches the verdicts stand. New rows reuse the ids `plugin`, `defaults` and `haiku-high` from the stored rows, and never pool with them, since those are below schema 3.

Read the `all tasks` verdicts after round 3 (6 runs per task and configuration) and after round 5 (10), and at no other point, since each look is one more chance for noise to pass. A LOSE on pass rate can show at the first look; with every run solved, neither a WIN nor a LOSE on cost can before the second. The class rows hold one or two tasks each, too few for a WIN, so read them for a LOSE only. Still undecided after round 5 is reported as "no difference shown". Five rounds are 240 runs, about $78. Rows under `results/pilot/` stay out of the page's tables, which read `results/*.jsonl`.

`--keep <dir>` copies each run's scratch folder and transcripts there, `--timeout` kills a run after that many seconds (default 900), `--model` sets the session model for every configuration that doesn't set its own (default `sonnet`), and `--claude` takes an argv prefix (`--claude python3 stub.py`) for a stub or wrapper. Leave out `--tasks` or `--configs` to run all of them; either flag with no id after it, an id that matches nothing, or an id or arm named twice, stops the runner with exit code 2, naming the ids. So does a results file, `limited/` folder or `--keep` folder it can't write, before any run.

## Adding a task

Make `tasks/<id>/` with `task.json` (`class` is one of the names in `run.CLASSES`, and an optional `shape` names a prompt in `run.SHAPES`), `repo/`, `check.py`, and `solution/` or `reference_answer`, plus a `wrong_answer` for an answer given in the reply. Give a task `wrong/` answers for each mistake it is built around, and `right/` answers for each fair form of a right one (a test fails for a task with neither a `wrong_answer` nor a `wrong/` folder). A task whose answer is one choice among candidates (a security review naming the vulnerable line) asks for a JSON file with fixed keys, so a list, a range or a second finding fails. Run `python3 -m unittest tests.test_bench`.

A check must be deterministic. It ends with `passcheck.finish(ok, reason)`, which prints the reason a row records (18 older checks end with `sys.exit` instead, and 16 of those give no reason, so their row says "the check exited 1"). Lines that run the work dir's code sit in `with passcheck.agent_code():`, so whatever that code raises (an exit included) fails the task, while an error in the check itself exits 2. A check never catches `Exception` or `BaseException`. To import the run's code, a check adds the work dir with `passcheck.use_work`, which appends it to `sys.path` (so it can't replace a standard-library module). A `SystemExit` the run's code raises fails the task only inside `passcheck.agent_code()`. A check runs the work dir's own tests with `passcheck.tests_pass`, which returns False for a test the run removed or made unreadable, a test that hangs and output that isn't UTF-8 (a shipped test that can't be read raises, so it reads as a broken check). A check that imports the run's code shares its process, so that code can end it with exit code 0.

A check whose task runs the agent's code to decide the answer does not import it. It runs that code in a child, a `probe.py` beside `check.py`, through `passcheck.probe(work, script, payload)`, on data the check generates from a fixed seed, and decides in the parent from the child's last JSON line, since only JSON crosses and the parent compares it exactly. A probe never holds the expected answer.

## Work that isn't code

Five tasks give the agent documents or data and ask for an answer file with fixed keys, so the check is exact: `legal-services-agreement` (class `document`), `finance-ledger-reconcile` and `finance-runway-forecast` (`analysis`), `research-study-synthesis` (`research`) and `ops-inbox-triage` (`operations`). Each folder's `wrong/` answers are the mistakes a careless reading makes. The two finance checks work their expected answer out from the shipped data by the task's written method, so an edit to the CSVs moves the answer with it. A check may read its own task's shipped `repo/` this way, and never the agent's copy of the data, so a run that edits its CSVs can't move the answer. `document` and `operations` have one task each so far, so a verdict for either class rests on one task. None of the five has been run against a model yet.

`run.py` starts every check without credential variables: any whose name holds `TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `AUTH` or `CREDENTIAL`, has `PAT` as a whole word (`GH_PAT`, not `PATH`), or starts with `ANTHROPIC_` or `CLAUDE_CODE_OAUTH`. A credential kept in a file (`~/.aws`, `~/.netrc`) is not hidden from it.
