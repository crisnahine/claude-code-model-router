# Benchmark

Measures what Model Router costs per solved task, and how often tasks get solved, against Claude Code without it. Results go to [docs/BENCHMARKS.md](../docs/BENCHMARKS.md). Standard-library Python only. Nothing here ships with the plugin.

- `tasks/<id>/`: one task each. `task.json` gives its class, brief and `revision` (raise it, with a line in `revisions`, whenever a change to the task could change a run's outcome; every row records it and the page says how many rows ran on an earlier one. A change to a check keeps the revision only when it can't move any recorded verdict: a test grades each recorded lookup answer again, and for a check whose runs can't be graded again, since the work dir is gone, the commit body shows why no verdict can move (the new code only raises where the old code failed the same way, say). Every other change to a check raises it), `repo/` is the fixed set of files a run starts from, and `check.py <workdir> <answer-file>` exits 0 when the task was solved, 1 when it wasn't and 2 when the check itself broke: `run.grade` starts every check through a launcher that turns an error the check raises into 2, so a bug in a check can't read as a wrong answer, and it returns the verdict, a reason (the last line the check printed) and a hash of the check's code. Checks share `tasks/passcheck.py` (the JSON answer readers, the FINDING.json rule, the work dir's tests) and load it by file path. `run.py` runs every check with `python -I`, so neither the check's folder nor the work dir is on `sys.path`. `solution/` (for tasks that change files, or write the DESIGN.json, RESEARCH.json or FINDING.json their brief asks for) or `reference_answer` (for an answer given in the reply: lookups) is a known-good result; `tests/test_bench.py` checks that each pass check fails on `repo/` as shipped and passes on that result. Known answers sit beside the check: `wrong/<name>/` and `right/<name>/` hold files laid over `repo/` and `solution/` (`answer.txt` is the reply and isn't copied, `remove.txt` lists paths to delete), and one test asserts that every `wrong/` fails and every `right/` passes, each as a verdict of the check, never as a broken one. A `wrong/` folder can hold an `expect.txt`, a substring the check's reason must contain, so the answer fails for the mistake it is named for. A `wrong/` folder without one must fail as "the check exited 1", so a check that gives reasons can't gain an unpinned fixture.
- `configs.json`: the configurations. `plugin` loads the router with `--plugin-dir`. `defaults` runs Claude Code with no plugin. `haiku`, `sonnet`, `opus` and `fable` force every subagent onto one model with `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1`. Forcing needs Claude Code v2.1.257 or later. While `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` is on, "Claude Code ignores the `model` field in subagent definitions, and Claude can't pass a model when it starts a subagent", but a fork, and a skill that runs in a subagent with `model: inherit`, still run on the parent conversation's model (https://code.claude.com/docs/en/sub-agents#run-every-subagent-on-one-model). The bench's prompt starts a subagent with the Agent tool, and the 1,120 recorded runs started only general-purpose, Explore, `claude` and the router's own agents ([docs/BENCHMARKS.md](../docs/BENCHMARKS.md), "Agents started"), so forcing covers them. Read a pilot row whose `subagents.by_type` shows any other type with that in mind. `sonnet-medium`, `haiku-high`, `sonnet-high`, `opus-high` and `fable-high` also set `CLAUDE_CODE_SUBAGENT_EFFORT`. `opusplan` sets the session model (`model`), and `advisor` adds `--advisor opus` (`args`). `price_model` names the model the full-suite estimate prices each configuration's runs at. A router variant is any other configuration with `"plugin": true`. Its `router_config` becomes the run's own `.claude/model-router.json`, its `plugin_options` go in through `--settings` as `pluginConfigs` (project settings can't set plugin options), and `plugin_ref` loads the plugin exported from that commit instead of the checkout's. `analyze.py` gives a variant its own column but never makes it a baseline.
- `run.py`: runs each task under each configuration with `claude -p --output-format json`, checks the result, and appends one JSON line per run to `results/`.
- `analyze.py`: computes pass rate (exact 95% binomial interval) and cost per solved task (95% bootstrap interval, each cell seeded by its session model, class and configuration), a quality verdict per class, and writes `docs/BENCHMARKS.md` below the page head, which `tools/docs_assets.py` writes, and gives docs_assets the same numbers for the chart and the docs' figures. `figures` keys them by role: the router, Claude Code's defaults (no plugin, no forced model), the best baseline over all runs and the strongest forced one. Only the router is named by its role alone, so its id appears in no doc or chart definition. A baseline is named by its role or by its own id: `BENCH_SERIES` in `tools/docs_assets.py`, `PROSE` and the docs' span keys (`opus.pooled.haiku-high`) use baseline ids. It also computes the yes/no facts the docs' prose states about each session (`PROSE`, `FACT_TEXT`), and `--check` fails when one stops being true.

## Running it

Every run spends real money at list price, or counts against a subscription's usage. `--budget` caps each run with `--max-budget-usd`, which a run can pass by one response plus what its running subagents spend before they stop. `--max-total` starts a run, and each retry of one, only with room for twice its cap, a margin rather than a bound; with no room left the runner stops with exit code 1. A run the API refuses for a rate or usage limit, or one that loses the network (an ENOTFOUND, ENETUNREACH or "Connection lost" error from Claude Code), is not a failed task: the runner pauses (1 minute, then twice as long each time), runs it again, and after 5 pauses stops with exit code 2, keeping every finished run. Limited runs go to `results/limited/`, so their spend is on record but out of the results. Any other error before a cent is spent (an invalid API key, a credit balance too low, a model the account can't use) is not a failed task either: the run goes to `results/limited/` with `limited_reason` `api_error`, without a pause or a retry, and 3 in a row stop the runner with exit code 2. `results/archive/` keeps the first pilots, which ran on an older harness (no saved sessions, a plugin data folder shared with other sessions), so they stay out of the comparison.

```bash
python3 bench/run.py --tasks lookup-retry-limit bugfix-pagination --configs plugin defaults haiku \
    --runs 1 --budget 0.5 --max-total 3 --out bench/results/<name>.jsonl
python3 bench/analyze.py bench/results/*.jsonl --out docs/BENCHMARKS.md
python3 bench/analyze.py bench/results/*.jsonl --out docs/BENCHMARKS.md --check
```

`--check` builds the page in memory and fails when the file differs. Leave out `--tasks` or `--configs` to run all of them. `--model` sets the session model, the same for every configuration that doesn't set its own, as `opusplan` does (default `sonnet`). `analyze.py` writes one results table per session model. `--first-run <n>` numbers the runs from `n`, so a batch run in rounds keeps each round's configuration order. A router run's line carries `agent_costs`, its spend by agent type (`main` is the main loop) from the router's ledger, and `routed`, its spawn decisions in order: agent, level, model, effort and, from a router that logs it, `escalated_from`. `--claude` takes an argv prefix (`--claude python3 stub.py`), for a stub or a wrapper. Every line carries `wall_ms`, the runner's clock around the `claude` process, next to `duration_api_ms` from Claude Code's result. A run whose result is `error_during_execution` with a zero cost is recorded as an unknown cost, like a missing one, and counts the whole budget, unless the API refused the run for a limit or the network, which spent nothing. The page's run metrics take latency from `wall_ms`, never from Claude Code's `duration_ms`, which can leave time out.

A run that failed for the network before the runner caught it goes by hand to `results/infra/`, with the reason in `infra_reason`, and is run again. The page counts those, and the runner's own `results/limited/` lines, as set aside.

Each run gets a fresh copy of the task's files in a temporary directory, never the repository. It loads no user settings, CLAUDE.md, auto memory or MCP servers, and the runner drops any `CLAUDE_CODE_*` variable it inherits except the provider switches (`CLAUDE_CODE_USE_*`) and `CLAUDE_CODE_OAUTH_TOKEN`. Each run also gets a plugins root of its own in that temporary directory (`CLAUDE_CODE_PLUGIN_CACHE_DIR`), so the router starts every run from an empty data folder and never reads or writes `~/.claude/plugins/data/model-router-inline/`, which other `--plugin-dir` sessions share. Its data goes with the temporary directory.

Sessions are saved, as Claude Code saves them by default, because the router's Stop check reads the transcripts to see whether a test ran. After each run the runner deletes that run's folder under `~/.claude/projects/`, the one named after its scratch copy, and nothing else.

Each raw line records `bench_commit`, the HEAD it ran on, and `bench_dirty`, whether `bench/` or the plugin had changes HEAD doesn't hold. When the `m6-*` files were recorded, the check also counted the bench's own output under `bench/results/`, so once the first results file of a session was written, every later line said `bench_dirty: true`. That is why the 320 main rows of the `m6-*` files carry it while the 16 probe rows before them don't. The code that ran for all of them is `499d046`; the check now leaves `bench/results/` out.

Each row's `grade` holds the `verdict` (`pass`, `fail` or `broken`), the check's `reason` and its `check_hash`, and `passed` is true only for `pass`. A `broken` run was neither solved nor failed, so analyze leaves it out of the tables and counts it in a page note. A run the bench itself stops after Claude Code returns (Ctrl-C while grading, a `--keep` folder it can't write) still writes its row, `broken` when the check didn't finish, and removes its scratch and session folders before the runner stops. Each row also keeps `final_answer`, because the runner deletes the work dir after grading: the reply (cut to the 80,000-character row cap), every text file the run added or changed against `repo/` (up to 20,000 characters each and 80,000 per row), the files it removed, and the names of files left out for size, because they aren't text, because they can't be read or because they link outside the work dir, so a later fix to a check can be tried on the recorded runs. A row's `schema` is `run.ROW_SCHEMA`, 2 now. `analyze.py` takes a missing key (`wall_ms`, `routed`, `plugin_state`) as the mark of an older harness only on a row below that schema. Rows on an earlier `revision` of their task are left out of the tables and counted in a page note.

The page's quality verdict is separate from the cost verdict. Per class, the router's pass rate is tested against every baseline that has 10 runs with an exact one-sided test, Holm-adjusted across the baselines: `BEHIND` when one solved more beyond noise, `NOT SHOWN BEHIND` when none did. That is not parity, since 10 runs per cell can't show a tie. A class is saturated when the weakest forced baseline (the lowest model, then the lowest effort, among the configurations that force every subagent onto one model) can't be told from the strongest by the same test, and then no quality claim is made. A class whose cells cover different tasks or run counts is PARTIAL.

## The quality-tier pilot

The six quality-tier tasks (one per class) run under `defaults`, `plugin` and the three forced baselines, 3 times each:

```bash
python3 bench/run.py --tasks impl-merge-customers bugfix-statement-queries security-admin-route \
    rootcause-wallet-race cross-amount-cents design-checkout-retries \
    --configs defaults plugin haiku sonnet opus --runs 3 --budget 1.5 --max-total 45 \
    --model claude-opus-5-5 --out "bench/results/pilot/quality-pilot-$(date +%F).jsonl"
python3 bench/analyze.py bench/results/pilot/*.jsonl --out "$TMPDIR/quality-pilot.md"
```

The same pilot can run as three processes at once, each with its own two tasks, its own `--out` and a $15 share of the $45 cap:

```bash
pilot() {  # <part> <$ share> <task> <task>
    python3 bench/run.py --tasks "$3" "$4" --configs defaults plugin haiku sonnet opus --runs 3 --budget 1.5 \
        --max-total "$2" --model claude-opus-5-5 --out "bench/results/pilot/quality-pilot-$(date +%F)-$1.jsonl"
}
pilot a 15 impl-merge-customers bugfix-statement-queries &
pilot b 15 security-admin-route rootcause-wallet-race &
pilot c 15 cross-amount-cents design-checkout-retries &
wait
python3 bench/analyze.py bench/results/pilot/*.jsonl --out "$TMPDIR/quality-pilot.md"
```

Each process checks only its own spend, so the shares must add up to $45 or less, and the task sets must not overlap or a cell gets more than 3 runs. Three sessions at once are more likely to hit a rate limit; each runner pauses and retries on its own, as above. Rows the API refused for a rate or usage limit go to `bench/results/pilot/limited/`, so the pilot's tables leave them out.

Run it only on the branch where QB and Q0 to Q5 are merged, since `plugin` is the checkout's router. 6 tasks x 5 configurations is 30 cells, and 3 runs of each is 90 runs. Rows go to `results/pilot/`, so the page's tables, built from `results/*.jsonl`, don't pool these 3-run rows with the 10-run ones. `analyze.py` picks `plugin` as the router there because it is the only plugin configuration in those rows. `analyze.py` reads a task as splitting the models (`splitting_tasks`) when `opus` solved at least 2 of every 3 runs and `sonnet` at most 1 of every 3, and lists those tasks in each class's Quality line when both ran. That is a reading rule for 3 runs, not a significance test. The 10-run measurement needs the maintainer's go after the pilot.

What it should cost, as a guide. On the Opus session the recorded mean per run is $0.152 for `defaults`, $0.154 for `opus`, $0.122 for `plugin` and $0.075 for `haiku` (`results/`, 80 runs each). `sonnet` has no Opus-session rows and is put at $0.11: the $0.075 relay plus a Sonnet subagent at half of Opus's price per token (https://platform.claude.com/docs/en/about-claude/models/overview). `plugin` is put at `opus`'s $0.154, since these briefs should route to Opus. These tasks are assumed to cost 3 times the old ones per run, which is an unmeasured guess. That gives 18 runs per configuration x ($0.152 + $0.154 + $0.154 + $0.075 + $0.11) x 3, about $35. `--budget 1.5` is about 4 times the dearest recorded Opus-session run of these five configurations ($0.367, `plugin`), so the cap should end no run. `run.py` starts a run only while spend plus twice the budget stays under the cap, so the single process stops before its last runs when the real multiplier is above about 3.7, and each $15 process when it is above about 3.2 (if its two tasks cost like the rest), since each keeps its own $3 margin. The rows already written are kept.

## Adding a task

Make `tasks/<id>/` with `task.json` (`class` is one of the names in `run.CLASSES`), `repo/`, `check.py`, and `solution/` or `reference_answer`, plus a `wrong_answer` for an answer given in the reply. Give a task `wrong/` answers for each mistake it is built around, and `right/` answers for each fair form of a right one (a test fails for a task with neither a `wrong_answer` nor a `wrong/` folder). A task whose answer is one choice among candidates, such as a security review naming the vulnerable line, asks for a JSON file with fixed keys instead of a reply, so the check reads one value and a list, a range or a second finding fails. Run `python3 -m unittest tests.test_bench`. A check must be deterministic: the same files and answer always give the same exit code. It ends with `passcheck.finish(ok, reason)`, which prints the reason a row records (18 older checks end with `sys.exit` instead, and 16 of those give no reason, so their row says "the check exited 1"), and the lines that run the work dir's code sit in `with passcheck.agent_code():`, so whatever that code raises (an exit included) fails the task, while an error in the check itself exits 2. A check never catches `Exception` or `BaseException`. A check that imports the run's code adds the work dir with `passcheck.use_work`, which appends it to `sys.path` so a work-dir module can't replace a standard-library one, and counts a `SystemExit` as a failure. It runs the work dir's own tests with `passcheck.tests_pass`, whose child is isolated the same way and imports `unittest` before it can see the work dir. `tests_pass` returns False for a test the run removed or made unreadable, a test that hangs and output that isn't UTF-8, since the run can cause each; a shipped test that can't be read raises, so it reads as a broken check. A check whose task runs the agent's code to decide the answer does not import it. It runs that code in a child, a `probe.py` beside `check.py`, through `passcheck.probe(work, script, payload)`, on data the check generates from a fixed seed, and decides in the parent from the child's last JSON line. Code that exits early, prints nothing or returns an object that compares equal to anything fails that way, because only JSON crosses and the parent compares it exactly. A probe never holds the expected answer. Code written to read or rewrite the probe's own state is not stopped; that is sabotage a reviewer sees in the diff. A check that imports the run's code directly still shares its process, so work-dir code can end it with exit code 0. `run.py` starts every check without credential variables: any whose name holds `TOKEN`, `KEY`, `SECRET`, `PASSWORD`, `AUTH` or `CREDENTIAL`, has `PAT` as a whole word (`GH_PAT`, not `PATH`), or starts with `ANTHROPIC_` or `CLAUDE_CODE_OAUTH`. That covers the environment only: the check runs as the same user, so a credential kept in a file, such as `~/.aws` or `~/.netrc`, is not hidden from it.
