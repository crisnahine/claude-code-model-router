# The upstream watcher: a daily check of the changelog, docs and model retirements

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.2.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Checked on 2026-11-24 against Claude Code 2.1.331, with every page fetched that day as `.md`. Code read in the `redo-fixes` worktree.

## What we built

- `hooks/hooks.json` runs `refresh-cache` as an async SessionStart command hook on every source (startup, resume, clear, compact, fork), next to the sync `session-start` hook.
- `hooks.refresh_cache` calls `upstream.refresh(force=False)`, which returns at once when the cache is under 24 hours old (`CACHE_TTL_SECONDS`) or a failed fetch is still in its backoff (`_retry_wait`: 1 hour, doubling to a day).
- `upstream.fetch` runs `_fetch` in a worker thread cut off at 25 seconds (`FETCH_BUDGET`). `_fetch` reads the changelog RSS (`parse_rss`), `llms.txt` (`parse_llms_index`, which maps each page URL to its one-line summary, then hashes the summary), the alias table in `model-config.md` (`parse_model_aliases`), the "Model status" table in `model-deprecations.md` (`parse_deprecations`), and `GET /v1/models` with `ANTHROPIC_API_KEY` when no gateway or cloud provider is set (`api_models`). `http_get` gives each body 10 seconds and refuses redirects when it sends the key.
- The first fetch marks everything as reviewed (`refresh` stores `snapshot`). `diff` then compares the reviewed mark with the cache: new releases, docs pages added, removed or with a changed summary, pages in `WATCHED_PAGES`, new or removed model families, newly deprecated models, and deprecated models that routed calls ran on (`health.seen_running`).
- `hooks.session_start` turns that into `additionalContext` for Claude: an older version of a family running (`behind`), a new alias, a retiring model in use, and "N Claude Code release(s) and M plugin-relevant docs page change(s) since the last review", each "worth telling the user once". The note stays until the user runs `/model-router:refresh` (a `docs-researcher` agent reviews the changes) and then `ack`.
- `report.models_data` adds `doc_aliases` and `not_in_registry` from the cache. The `update_check` option (on by default) turns the fetch and the notes off. `plugin.json` lists `code.claude.com`, `platform.claude.com` and `api.anthropic.com` under `network`.
- For maintainers, `.github/workflows/upstream-watch.yml` runs `model-router.py upstream-check --baseline compat/baseline.json` daily and keeps one open issue. The baseline is rewritten by hand with `--write`.
- Routing reads none of the cache. `mod.py` uses only the ID parser `upstream.version_of`. Aliases, `newest` and `older_aliases` come from the shipped `config/models.json`.

## What the sources say

A plugin's own network calls

- The manifest field only declares. "`network` | Object | The hosts your plugin reaches, such as `"network": { "hosts": ["api.example.com"] }` ... `claude plugin validate` lists them. The field doesn't allow or block any host. Requires Claude Code v2.1.328 or later." https://code.claude.com/docs/en/plugins/manifest-reference.md
- Plugin code runs as the user, outside Claude Code's controls. "A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges." "Claude Code's permission rules and sandbox cover the tool calls Claude makes, not the code a plugin runs by itself." "Claude Code runs hooks, monitors, MCP servers, LSP servers, and the processes a mod starts outside the sandbox." https://code.claude.com/docs/en/plugins/security.md. Same on the sandbox page: "The sandbox covers shell commands only. Claude's file tools, MCP servers, and hooks run outside it." https://code.claude.com/docs/en/sandboxing.md
- Managed settings have no host-level control for a hook process. They can only stop hooks as a whole: under `allowManagedHooksOnly`, "Everything else is blocked: user, project, and local hooks, hooks and mods from other installed plugins", and `disableAllHooks` turns hooks off. https://code.claude.com/docs/en/settings-reference.md
- A mod's own requests do fall under policy. "Network policy covers `$.http.fetch`." "Your organization's policy doesn't allow WebFetch: Claude Code also refuses every mod's `$.http.fetch` request." A policy mod can "hook `http.fetch` ... and refuse requests from users' mods". But "None of these covers a program the mod starts with `$.process.run`, which reaches the network with the user's own access." https://code.claude.com/docs/en/plugins/mods/admin.md
- The nonessential-traffic switch is defined for Claude Code's own traffic. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` "disable[s] nonessential network traffic: auto-updates, telemetry, error reporting, the `/feedback` command, ... release notes, ... and availability checks". https://code.claude.com/docs/en/env-vars.md. For mods it is narrow: "a mod that you or your users install can still make these requests. The variable stops only the mods built into Claude Code, plus any `$.http.fetch` request that carries the session's Anthropic credentials." https://code.claude.com/docs/en/plugins/mods/admin.md
- Offline fleets are told to set that switch. "For fleets with no outbound git access, combine a seed with `directory` or `file` marketplace sources on a shared mount. Set `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` as well, which also turns off plugin auto-update." https://code.claude.com/docs/en/plugins/org.md
- A hook can see that switch. "A hook process inherits the parent environment, apart from the `OTEL_*` exporter variables ... and, when `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is set to `1`, the variables it strips." In a HIPAA session Claude Code "also removes Anthropic credentials from the hook's environment." https://code.claude.com/docs/en/hooks.md
- Admins are told that blocking `code.claude.com` is harmless. "`code.claude.com` | Claude Code documentation lookups by the built-in claude-code-guide agent and pre-approved WebFetch requests. Blocking this host only affects documentation lookups." https://code.claude.com/docs/en/network-config.md
- Async hooks have no timeout and die with `-p`. "Once an async hook is running in the background, Claude Code doesn't enforce `timeout` on it." "In non-interactive mode with the `-p` flag, Claude Code kills any async hook still running at teardown and finalizes it with outcome `cancelled`." https://code.claude.com/docs/en/hooks.md. In the code, `refresh` writes `failed` only from its `except` branch, so a run killed mid-fetch stores neither a cache nor a failure, and the next start fetches again.
- Hooks have one channel for the user and one for Claude. "To surface a message to the user on any platform, return `systemMessage` in JSON output." "Use `additionalContext` for information Claude should know about the current state of your environment or the operation that just ran." https://code.claude.com/docs/en/hooks.md

How Claude Code tells users about its own versions and about retiring models

- Updates: "Claude Code checks for updates on startup and periodically while running. Updates download and install in the background, then take effect the next time you start Claude Code." `DISABLE_AUTOUPDATER` and `DISABLE_UPDATES` turn this off. https://code.claude.com/docs/en/setup.md
- Release notes: "`/release-notes` | View the changelog in an interactive version picker." https://code.claude.com/docs/en/commands.md. The feed comes from `raw.githubusercontent.com`: "In interactive sessions, Claude Code also fetches it in the background at startup when its cached changelog doesn't yet cover the running version, such as the first start after an update; non-interactive and cloud sessions never fetch it." https://code.claude.com/docs/en/network-config.md. The changelog, 2.0.17: "`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` now disables release notes fetching." https://code.claude.com/docs/en/changelog.md
- Retiring models: "When the requested model has a scheduled retirement date or is automatically remapped to a newer version, Claude Code shows a warning that names the requested model. Interactive sessions show it as a startup notice. From v2.1.182, the same warning is written to stderr in non-interactive mode ... The check also covers a `model` set in subagent frontmatter." https://code.claude.com/docs/en/model-config.md
- Aliases follow new models with each Claude Code release. "Aliases point to the recommended version for your provider and update over time. To pin to a specific version, use the full model name." The "Version history" table lists "the Claude Code version at which each model alias changed the model it resolves to", for example "v2.1.293 | `haiku` resolves to Haiku 5.5 on the Anthropic API". https://code.claude.com/docs/en/model-config.md
- Anthropic tells customers itself. "Impacted customers will always be notified by email and in the documentation." "Anthropic notifies customers with active deployments for models with upcoming retirements, providing at least 60 days' notice before model retirement for publicly released models." https://platform.claude.com/docs/en/about-claude/model-deprecations.md
- The page's dates apply to Claude Code on the Claude API only. "Claude Code uses the Claude API, including when you sign in with a Claude plan, so this page's dates apply. If Claude Code is set up for another platform or for a gateway, the dates are those of the platform that serves its requests." Amazon Bedrock and Claude Models on Google Cloud (Google managed) "set their own retirement schedules". https://platform.claude.com/docs/en/about-claude/model-deprecations.md

How a plugin's changes reach users

- By release. "If you publish through your own marketplace and your `plugin.json` sets `version`, increment it and push. Users who run `claude plugin update` or have auto-update on then receive the new version." "Auto-update: off by default for your marketplace." https://code.claude.com/docs/en/plugins/publish.md
- Defaults: auto-update is "Off by default: every other marketplace, including the community marketplace, third-party marketplaces, and local development marketplaces." Users turn it on in `/plugin`, **Marketplaces** tab. https://code.claude.com/docs/en/plugins/install.md
- Timing and switches: "In an interactive session, after you send your first message, Claude Code waits a random delay of up to ten minutes. It then refreshes every marketplace with auto-update on". "If you set `DISABLE_UPDATES=1`, `DISABLE_AUTOUPDATER=1`, or `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, the whole pass is off". https://code.claude.com/docs/en/plugins/loading.md
- Compatibility: "`engines` | Object | The Claude Code versions that the plugin works on, as a semver range under the `claude-code` key". https://code.claude.com/docs/en/plugins/manifest-reference.md

Staying current with model releases, for an application built on Claude

- "Regularly check the documentation for updates on model deprecations." (Best practices, item 1.) https://platform.claude.com/docs/en/about-claude/model-deprecations.md
- For Claude Code users: "update it first, because a newer model can need a newer version of Claude Code. Then, check which model you're using ... Also, change the old model everywhere you set a model, including subagent definitions". https://platform.claude.com/docs/en/about-claude/model-deprecations.md
- The Models API gives `lifecycle` and `retires_at`, needs the key (`-H "Authorization: Bearer $ANTHROPIC_API_KEY"`), and warns about `line`: "`null` when the model belongs to no line; do not infer a line from the `id`." https://platform.claude.com/docs/en/api/models/list.md. `upstream.version_of` infers the family from the ID for `behind`.
- Claude Code asks before it uses that key: "In interactive mode, you are prompted to approve the key once before it overrides your subscription." https://code.claude.com/docs/en/env-vars.md. `api_models` sends the key whenever it is in the environment, approved or not.

What the feeds hold today

- The RSS feed `https://code.claude.com/docs/en/changelog/rss.xml` held 15 items, 2.1.314 to 2.1.331, on 2026-11-24. No docs page names it. The changelog page names its own source: "This page is generated from the CHANGELOG.md on GitHub." https://code.claude.com/docs/en/changelog.md. A baseline more than about three weeks old loses releases from the issue without a warning.
- `llms.txt` is a list of "- [Title](URL): summary" lines. https://code.claude.com/docs/llms.txt. Because the code hashes the summary, a change to the body of `hooks.md` or `model-config.md` with the same summary line counts as no change. `docs/CLAUDE_CODE_DOCS.md` says the plugin "flags changes to the pages it is built on", which holds only for summary edits.

## Verdict

Partly right.

The maintainer half is right: a daily CI job that reads the official changelog and deprecations page and opens one issue matches "Regularly check the documentation for updates on model deprecations", and the fix reaches users the documented way, by a version bump that `claude plugin update` or auto-update installs. The user half is not justified. Routing reads none of the fetched data, and the notes it feeds are maintainer work. Claude Code already covers what a user needs: it updates itself, offers `/release-notes`, warns at startup about a retiring model, and moves aliases with each release. The fetch runs where Claude Code's own background traffic would not: in `-p` and cloud sessions, and under `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. As a Python process it also escapes the one policy admins have over plugin requests. And it costs context: the note stays in every session until the user runs a docs-researcher review and `ack`.

## What to change

1. **Stop the automatic fetch on users' machines.** Delete the async `refresh-cache` entry in `hooks/hooks.json`, `hooks.refresh_cache` and its `HANDLERS` entry, the `update_check` block in `hooks.session_start`, and the `update_check` option (`plugin.json` `userConfig`, `settings.Settings.update_check`, `settings.resolve`, `settings.record`). In `upstream.py` delete `refresh`, `ack`, `pending`, `_retry_wait`, `_failures`, `FAILED_RETRY_SECONDS`, `CACHE_TTL_SECONDS`, `newest_versions`, `behind`, `path`, `load` and the `upstream.json` state file. Delete the CLI commands `refresh`, `status` and `ack` in `cli.py`, `report.status`'s "No upstream data cached" path, and `doc_aliases` and `not_in_registry` in `report.models_data` and `report.models`. That is a change to `model-router.models/1`, so bump `MODELS_SCHEMA` or keep both keys as empty lists for one release. Update the tests and fixtures that cover these (`test_session_start_mentions_pending_upstream_and_new_models`, the `Upstream` refresh and backoff tests, `tests/fixtures/json-outputs/models*.json`), and the docs that describe the daily fetch: `docs/CLAUDE_CODE_DOCS.md` "Staying current", `docs/SECURITY.md` "Network", `docs/ARCHITECTURE.md` (the change table, the state files table, the `models --json` keys), `docs/FAQ.md`, `docs/GUIDE.md`, the README options count, and the `plugin.json` description ("tracks new and retiring models"). Backed by https://code.claude.com/docs/en/network-config.md (Claude Code's own changelog fetch is interactive-only), https://code.claude.com/docs/en/env-vars.md (release notes and update checks are nonessential), https://code.claude.com/docs/en/model-config.md (the startup retirement warning, aliases that move) and https://code.claude.com/docs/en/plugins/mods/admin.md (what policy can and can't stop). Judgment: no source forbids a plugin's fetch.

2. **Drop the Models API call that uses the user's key.** Delete `upstream.api_models`, `MODELS_API`, the `RefuseRedirect` branch in `http_get`, `_api_lines`, `api_lines` in `snapshot` and `diff` (and in `compat/baseline.json`), the Models API branch in `merged_lifecycle`, `Settings.api_key`, and the credential section of `docs/SECURITY.md`. The CI workflow sets no key, so this call never ran there. It sends a key the user may have declined in Claude Code, for notices only. Backed by https://code.claude.com/docs/en/env-vars.md (the approval prompt for `ANTHROPIC_API_KEY`) and https://platform.claude.com/docs/en/api/models/list.md (the call needs the key). Judgment.

3. **Move the maintainer pieces out of the shipped plugin.** Move what CI uses (`http_get`, `fetch`, the parsers, `diff`, `snapshot`, `has_pending`, `report.status`, the `upstream-check` command) from `plugins/model-router/scripts/modelrouter/` to a repo tool such as `tools/upstream_check.py`, which the marketplace source `./plugins/model-router` does not ship. Move `skills/refresh` to a repo-level skill under `.claude/skills/refresh/`, with `compat/baseline.json` as the only reviewed mark. Point `.github/workflows/upstream-watch.yml` and its issue text at the new path. Change `test_only_upstream_opens_connections` to assert that no shipped module opens a connection. Backed by https://code.claude.com/docs/en/plugins/publish.md (releases reach users by version) and https://code.claude.com/docs/en/plugins/manifest-reference.md. Judgment.

4. **Remove `network` from `plugin.json` once nothing shipped opens a connection.** The field is defined as "The hosts your plugin reaches", so after items 1 and 3 it would list hosts the plugin never reaches. Required by https://code.claude.com/docs/en/plugins/manifest-reference.md once items 1 and 3 land.

5. **In CI, watch the pages themselves, not their summary line.** Replace the summary hash in `parse_llms_index` and `_fetch` (`pages`) with a hash of each watched page's `.md` text, keeping `llms.txt` only to find added and removed pages. Add the platform pages the registry's numbers come from: pricing, the models overview, effort, and optimizing for cost and intelligence. Then fix the claim in `docs/CLAUDE_CODE_DOCS.md`. Backed by https://code.claude.com/docs/llms.txt, an index of one-line summaries whose links point at each page's `.md` copy. Judgment.

6. **In CI, read releases from the documented changelog.** Read `https://code.claude.com/docs/en/changelog.md` (or the GitHub `CHANGELOG.md` it names) in place of the RSS feed in `CHANGELOG_RSS` and `parse_rss`. At least, fail the job or say so in the issue when the oldest release in the feed is newer than the baseline's next version. Backed by https://code.claude.com/docs/en/changelog.md ("generated from the CHANGELOG.md on GitHub"). The RSS URL is on no docs page. Judgment.

7. **Tell users how to get registry and model fixes.** In `README.md` and `docs/GUIDE.md`, say that auto-update is off for this third-party marketplace, how to turn it on (`/plugin`, **Marketplaces** tab), and that `claude plugin update model-router@claude-code-model-router` gets a fix now. Backed by https://code.claude.com/docs/en/plugins/install.md. Judgment.

8. **Only if the owner keeps a fetch on users' machines instead of item 1:** skip it when `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, `DISABLE_AUTOUPDATER` or `DISABLE_UPDATES` is set, and in cloud sessions (`$CLAUDE_CODE_REMOTE` is `"true"` there, per https://code.claude.com/docs/en/hooks.md). Fetch only `model-deprecations.md`. Make the request from the mod with `$.http.fetch` so the WebFetch policy and policy mods apply. Show the one remaining note (a retiring model that routed calls ran on) as `systemMessage`, not as `additionalContext` that asks Claude to pass it on. This touches `hooks.refresh_cache`, `settings.resolve`, `hooks.session_start` and `hooks/router.ts`. Backed by https://code.claude.com/docs/en/network-config.md, https://code.claude.com/docs/en/plugins/loading.md, https://code.claude.com/docs/en/plugins/mods/admin.md and https://code.claude.com/docs/en/hooks.md. Judgment.

## What the sources do not say

- Whether a third-party plugin should honor `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`. The mods admin page says the switch doesn't stop a user mod's requests. It says nothing about a settings hook's own process.
- Whether Claude Code's startup retirement warning covers a model a mod sets in `agent.spawn`, or the `model` on an Agent call. It names the session model and subagent frontmatter only. This was the one user-facing gap the runtime check covered: the router routes by alias on the Claude API and sends full IDs only from the shipped `newest` table, so a stale install is the case left.
- Any documented way for a plugin to tell users that a newer version of itself exists, beyond auto-update and `claude plugin update`.
- Whether `network.hosts` should also list hosts that a plugin's agents reach through WebFetch or WebSearch (the `architect` and `docs-researcher` agents do).
- Whether a hook process trusts the CA certificates Claude Code trusts (its bundled set, the OS store, `NODE_EXTRA_CA_CERTS`). The network configuration page describes Claude Code's own connections only.
- Whether `$.http.fetch` uses Claude Code's proxy and CA settings.
- How a settings hook can tell an interactive session from `claude -p`. No SessionStart input field says so, so item 8 can't copy Claude Code's interactive-only rule exactly.
- Any RSS feed for the changelog or the deprecations page, or any promise that the "Model status" and alias tables keep their Markdown layout, which the parsers depend on.
- Any privacy or data-usage statement about what a third-party plugin may send, or how often a plugin may poll Anthropic's docs hosts.
