# Docs, site and discovery files

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.2.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

## What we built

- `tools/docs_assets.py` (1,464 lines) runs `build(snapshot())` and writes 61 SVGs into `docs/assets/`: `brand_assets`, `banner_assets` (a banner and icon for each of the 20 `PAGES` in `tools/docs_pages.py`), `badge_assets`, `hero`, `headline`, the five diagrams (`diagram_ladder`, `diagram_redo`, `diagram_two_paths`, `diagram_precedence`, `diagram_stop_checks`) and `social_preview`. About 1,000 of its lines are drawing code.
- The same run writes the page heads (`docs_pages.with_head`), the index cards (`with_cards`), the benchmark spans in the six `FIGURE_PAGES` and the site (`with_figures`), the README alt text (`img_alt`, `badge_alt`) and `CITATION.cff` (`citation`). Only the ladder is checked against the code (`check_ladder_against_registry`).
- `site_files` (about 40 lines) rewrites `site/index.html`: the FAQ as `<details>` from `docs/FAQ.md` (`site_faq_html`), the same FAQ as `FAQPage` JSON-LD (`site_faq_ld`), and five regex rewrites (`softwareVersion`, `dateModified`, `softwareRequirements`, the "Five levels" feature, the footer). It writes `site/sitemap.xml` with `<lastmod>` set to the release date, and `site/robots.txt`. `sync` copies 15 `SITE_ASSETS` from `docs/assets/` to `site/assets/`. `--check` fails CI on drift, SVG accessibility, contrast and text overflow.
- `site/index.html` (572 lines) is hand-written apart from those spans. Its head has a JSON-LD `@graph` (`WebSite`, `WebPage`, `Person`, `SoftwareApplication`, `SoftwareSourceCode`), the `FAQPage` block, Open Graph and Twitter tags, a `google-site-verification` tag and `rel="alternate" type="text/markdown"` pointing at the raw README.
- `site/llms.txt` is hand-written. `site/d9915f7964ab865623adf3a19419e014.txt` is an IndexNow key file (commit 2efd799 says so). `.github/workflows/pages.yml` deploys `site/` on every push to `site/**` on `main`.
- `docs/assets/video.mp4` (2 MB, rendered outside the script) is copied to `site/assets/video.mp4`. Every page links to the Pages copy.
- The listing: the entry in `.claude-plugin/marketplace.json` (`description`, `category`, `tags`), `plugins/model-router/.claude-plugin/plugin.json` (a 90-word `description`, `keywords`, `homepage`, `repository`), `plugins/model-router/README.md` (184 words) and the root `README.md`. `tests/test_model_router.py` `test_readme_and_description_keep_their_search_phrases` and `test_the_marketplace_names_the_product_model_router` lock search phrases into these descriptions.

Checked live on 2026-11-24: `https://crisnahine.github.io/robots.txt` exists (it comes from the owner's user-site repository) and already lists `https://crisnahine.github.io/claude-code-model-router/sitemap.xml`. `site/llms.txt`, `sitemap.xml`, `robots.txt` and the key file all answer 200 under `/claude-code-model-router/`.

## What the sources say

### llms.txt (owner: llmstxt.org, Jeremy Howard, v2)

- Format. "An H1 with the name of the project or site. This is the only required section", then "A blockquote with a short summary of the project", then "Zero or more markdown sections (e.g. paragraphs, lists, etc) of any type except headings", then H2 sections "containing "file lists" of URLs"; "The "Optional" section is used, by convention, for secondary information" (https://llmstxt.org/). Ours has the H1, the blockquote, a facts list, `## Docs` and `## Optional`. Follows the spec.
- Location. "The file can be placed at the site root, or at any path within it, covering the pages under that path", and the spec names "a GitHub Pages project site" as the case it serves (https://llmstxt.org/). Ours sits at `/claude-code-model-router/llms.txt`. Follows.
- Links. "The links in an llms.txt file should therefore point to LLM-friendly content, such as the markdown versions of pages described above" (https://llmstxt.org/). Ours points `## Docs` at the HTML site and at `video.mp4`. Those two links are misused; the rest point at raw Markdown.
- Link relations. "we recommend using standard link relations: `rel="alternate" type="text/markdown"` points to the markdown version of a page, and `rel="describedby"` points to the llms.txt file that covers it" (https://llmstxt.org/). Ours has the `alternate` link, aimed at the README rather than a Markdown copy of the page itself, and no `describedby` link.
- Who reads it. Google: "It's completely fine if you decide to create and maintain LLMS.txt files (or other similar files) for other services or systems that use these files. Doing so will neither harm nor help your site's visibility or rankings in Google Search, as Google Search ignores them" (https://developers.google.com/search/docs/fundamentals/ai-optimization-guide). So its only readers are agents that fetch it.
- Repo fact: the benchmark figures in `site/llms.txt` (70 of 70, $0.121, $0.151, $0.075, 6 of 8) are typed by hand. `site/llms.txt` is not in `FIGURE_PAGES`, so a rerun of `bench/analyze.py` leaves them stale, which breaks the repo's own rule that "a figure changes by rerunning analyze, never by hand" (`CONTRIBUTING.md`).

### CITATION.cff (owners: the Citation File Format project and GitHub)

- Required keys are `authors`, `cff-version`, `message` and `title`; `type` is "enum (`software` or `dataset`)"; `license` takes "The SPDX license identifier(s)"; `url` is "The URL of a landing page/website for the software or dataset"; `repository-code` is "The URL of the work in a source code repository" (https://github.com/citation-file-format/citation-file-format/blob/main/schema-guide.md). Ours has every required key, `type: software`, `license: Apache-2.0`, and valid optional keys. Follows the spec.
- Its reader: "When you add a `CITATION.cff` file to the default branch of your repository, a link is automatically added to the repository landing page in the right sidebar, with the label "Cite this repository."" (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-citation-files). It is generated from the manifest version and the changelog date, so it can't drift. Right as built.

### Structured data (owners: schema.org and Google Search)

- `FAQPage` is valid: "A FAQPage is a WebPage presenting one or more "Frequently asked questions"" (https://schema.org/FAQPage), and ours matches the visible `<details>` FAQ.
- Google no longer uses it. 2026-05-08: "Deprecating the FAQ rich result feature ... This feature will no longer appear in Google Search starting May 7, 2026." 2026-06-15: "Removed documentation for the FAQ rich result feature ... The FAQ rich result feature is no longer shown in Google Search results" (https://developers.google.com/search/updates). The old guide, https://developers.google.com/search/docs/appearance/structured-data/faqpage, now redirects (301) to that entry. On AI search: "Structured data isn't required for generative AI search, and there's no special schema.org markup you need to add. However, it's a good idea to continue using it as part of your overall SEO strategy, as it helps with being eligible for rich results on Google Search" (https://developers.google.com/search/docs/fundamentals/ai-optimization-guide). The `FAQPage` block has no Google feature left to make eligible. It serves no reader there.
- `SoftwareApplication` rich result: required are `name`, `offers.price`, and "Rating or review ... You must include one of the following properties: aggregateRating ... review" (https://developers.google.com/search/docs/appearance/structured-data/software-app). Ours has no rating or review, so it isn't eligible, and the project has no real ratings to add.
- Two of its fields don't say what schema.org defines. `downloadUrl`: "If the file can be downloaded, URL to download the binary" (https://schema.org/SoftwareApplication); ours is the repository page. `operatingSystem`: "Operating systems supported"; ours says only `macOS`, while the README says "its unit tests also run on Linux and Windows in CI". Misused.
- Open Graph: "The four required properties for every page are: og:title ... og:type ... og:image ... og:url" (https://ogp.me/). Ours has all four. The social preview PNG is 1280 by 640 and 90 KB, inside GitHub's "PNG, JPG, or GIF file under 1 MB ... (1280 by 640 pixels for best display)" (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview). Follows.

### Crawl and verification files (owners: IETF, sitemaps.org, Google, IndexNow)

- robots.txt: "The rules MUST be accessible in a file named "/robots.txt" (all lowercase) in the top-level path of the service" (RFC 9309 section 2.3, https://www.rfc-editor.org/rfc/rfc9309.html). Google: "It cannot be placed in a subdirectory (for example, at https://example.com/pages/robots.txt)" (https://developers.google.com/crawling/docs/robots-txt/create-robots-txt). Ours is served at `/claude-code-model-router/robots.txt`, so no crawler reads it, and the host's real robots.txt already lists our sitemap. Serves no reader.
- Sitemap location: a sitemap at "http://example.com/catalog/sitemap.xml can include any URLs starting with http://example.com/catalog/" (https://www.sitemaps.org/protocol.html). Ours is in its own path. Follows. Google: "You might need a sitemap if: ... Your site is new and has few external links to it" (https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview). It earns its place.
- Sitemap `lastmod`: "Note that the date must be set to the date the linked page was last modified, not when the sitemap is generated" (https://www.sitemaps.org/protocol.html). Google "uses the <lastmod> value if it's consistently and verifiably (for example by comparing to the last modification of the page) accurate" (https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap). Ours sets `lastmod` and JSON-LD `dateModified` to the release date in `CHANGELOG.md`. A docs edit after a release changes `site/index.html` (FAQ text, figures), deploys, and leaves both dates at the release day. Misused.
- IndexNow: "To submit URLs, you must "prove" ownership of the host ... Once you submit your URLs to search engines, search engines will crawl the key file to verify ownership". For a key file off the host root, "you must tell search engines the location of this text key file in each IndexNow notification by specifying the location using the keyLocation variable" (https://www.indexnow.org/documentation). Nothing in the repo submits to IndexNow: no workflow, script or doc names it. The key file serves no reader unless someone submits by hand.
- Search Console tag: Google says you "can unverify previous owners by removing their verification token (for example, removing the HTML tag from the site, for HTML-tag-verified owners)" (https://support.google.com/webmasters/answer/9008080). The tag has to stay while the owner wants Search Console. Right.

### The plugin listing and README (owner: Claude Code docs)

- What Claude Code asks of a README: "Set `description`, `author`, `homepage`, and `repository` in `plugin.json`, and add a `README.md` at the plugin root. `homepage` must parse as a URL" (https://code.claude.com/docs/en/plugins/publish, "Prepare your plugin for release" step 5). And `claude plugin validate` prints advice when "a plugin's README has no line that installs the plugin from a marketplace"; a line counts when `plugin install` is followed by "The plugin's name and `--marketplace <source>`" (https://code.claude.com/docs/en/plugins/cli-reference, "Advice on the README"). Ours has all four fields, a README at `plugins/model-router/`, and the line `/plugin install model-router --marketplace crisnahine/claude-code-model-router`. Follows. The Claude Code docs ask nothing more of README content.
- `description` is "Short explanation of what the plugin provides" and `keywords` are "Discovery tags" (https://code.claude.com/docs/en/plugins/manifest-reference). Ours is a 90-word feature list that opens with search phrases, and tests require those phrases. Misused against "short".
- Which description users see: the entry's `description` is "Shown in `/plugin` listings and details"; "For a field you set on the entry, users see the entry's value, even when `plugin.json` sets a different one"; and "Before install, Claude Code can read `plugin.json` only for entries with a relative-path source" (https://code.claude.com/docs/en/plugins/marketplace-reference). Our entry sets a second, different description, so `/plugin` never shows the `plugin.json` one. Our source is relative (`./plugins/model-router`), so with no entry `description` the `plugin.json` text would show before install too.
- `category` is "Free-form category for organizing the catalog" and `tags` "Free-form tags for search" (https://code.claude.com/docs/en/plugins/marketplace-reference). Ours follow.
- The trust warning ends "See each plugin's homepage for more information" (https://code.claude.com/docs/en/plugins/security). Our `homepage` is the repository, whose README covers install, privacy and removal. Follows.

### Anthropic's directory (owner: Anthropic, claude.com; applies only if the plugin is submitted there)

- "The directory shows your README as the listing's description", and it blocks without "a README of at least 40 words in the plugin folder, preferably named `README.md`. Words inside code blocks don't count" (https://claude.com/docs/plugins/pre-submission-checklist). Ours passes the length check.
- "Describe in the README everything the plugin runs, sends, or fetches" (https://claude.com/docs/plugins/pre-submission-checklist, "Prepare for the security scan"). Our plugin-folder README links to the root README and names none of what the plugin runs (eight hook events, a mod, `python3`), fetches (a daily fetch from `code.claude.com`, `platform.claude.com` and `api.anthropic.com`) or stores (the ledger). That is a gap.
- The directory policy: "Developers must document how their Software works, its intended purpose, and how users can troubleshoot issues"; "Developers of Software that collects user data or connects to a remote service must provide a clear, accessible privacy policy link" (https://support.claude.com/en/articles/13145358-anthropic-software-directory-policy). The directory reads `icon`, `documentationUrl`, `supportUrl`, `privacyPolicyUrl` and `termsOfServiceUrl` from `plugin.json` (https://code.claude.com/docs/en/plugins/manifest-reference, "Directory listing fields"). Ours sets none of them.

### Repo facts no source speaks to

- `docs/assets/video.mp4` and `docs/assets/video-poster.jpg` are referenced by no page. The README, the plugin README, `site/llms.txt` and the site all use the Pages copy, so `sync` stores the same 2 MB video twice, again with each render.
- The diagram copy has already drifted from the code. `diagram_redo` says a redo is "The same call, issued again in the same request after its result came back". It never mentions the "Redo:" description marker that `docs/FAQ.md`, `site/llms.txt` and the site FAQ have described since commit cbbf560. Its vote numbers (6, 30%) repeat `learn.VOTES_NEEDED` and `learn.SHARE_NEEDED` with no check. The site's hand-written intro still says "Each call's brief is scored for risk, scope, load and ambiguity".

## Verdict

Partly right. CITATION.cff, the sitemap's location, Open Graph, the social preview, the verification tag and the Claude Code README rules (a README at the plugin root, an install line, the four metadata fields) all follow their owners' specs, and llms.txt follows the llmstxt.org format. Four things serve no reader: the `FAQPage` JSON-LD, since Google dropped FAQ rich results on 2026-05-07; the subpath `robots.txt`, which RFC 9309 says crawlers never read; the IndexNow key, which no submission uses; and the duplicate `docs/assets` video. Some pieces are misused against their own definitions: the sitemap `lastmod` and `dateModified`, `downloadUrl` and `operatingSystem`, two llms.txt links that aren't LLM-readable, and a long, phrase-stuffed `plugin.json` description that the marketplace entry hides anyway. The plugin-folder README also lacks the disclosure Anthropic's directory requires.

## What the sources do not say

- Whether any agent or AI search product reads a project's `llms.txt` on a GitHub Pages subpath. llmstxt.org describes intended use, and Google says Google Search ignores it. No other consumer's documentation was checked. Not documented.
- Whether Bing or any other search engine still uses `FAQPage` markup. Only Google's pages were checked.
- Whether `rel="alternate" type="text/markdown"` may point at a different document, the README, rather than a Markdown copy of the page at its own URL. The spec describes the same-URL form only.
- Whether `/plugin` search reads the entry's `tags`, the manifest's `keywords`, or both. The docs call both "tags" for search or discovery and say no more.
- Whether the owner means to submit to Anthropic's directory. Items 6 and 7 and the `documentationUrl`, `supportUrl` and `privacyPolicyUrl` fields matter most there. The checklist also says a name "made only of generic words, such as `test-plugin`" is "Held for a reviewer". Whether `model-router` counts is not documented, and a rename costs every install (https://code.claude.com/docs/en/plugins/publish), so no rename is proposed.
- Whether "Claude Code Model Router" in the README heading, the site title and the JSON-LD `alternateName` counts as presenting the plugin as official. The checklist's brand rule names only `name`, `displayName` and `author.name`.
- Any rule on banners, badges, a hero image or a demo video in a plugin's docs. No owning source covers these, so the roughly 1,000 lines of drawing code in `tools/docs_assets.py` are a taste call, not a spec question.
- Whether a social preview image is uploaded in the repository settings. GitHub keeps that outside the repository, so it can't be checked from here.
