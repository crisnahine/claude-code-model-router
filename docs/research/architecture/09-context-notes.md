# What the plugin puts in Claude's context: the session note and the per-prompt notes

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Checked 2026-11-24 on Claude Code 2.1.331 (`claude --version`). Every page was fetched that day as `.md`. The generated type files are not in the `redo-fixes` worktree; the ones read here are in the main checkout at `plugins/model-router/.claude-plugin/types/`, headed "Written by Claude Code 2.1.330", and are cited as `[mod-types]`.

## What we built

- `hooks.session_start` (SessionStart, matcher `startup|resume|clear|compact|fork`, 10 s) returns `additionalContext`. In `auto` mode the base text is 354 characters, three sentences: Model Router sets each agent's model and effort from its brief; calls omit `effort` unless the user named one and name `model` only when the user did or what was read shows the task harder or easier than its brief; a redo keeps its `description` with "Redo:" in front and runs one level higher.
- The same hook adds a line for `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL`, a model behind its family's newest, a new alias, a retiring model and pending upstream changes. Most end "Worth telling the user once." With FORCE on, the note grows to about 600 characters. `advise` mode has its own two sentences.
- `hooks.user_prompt` (UserPromptSubmit, 5 s) reads the prompt with `intake.from_prompt` (the regex in `profile.py`) and returns a note only when the estimated need is above the session's model (`Request.below`). The note gives the level, the regex signals, and the role agent to ask for the plan (`gates.strong_agent`). It returns a second note when the prompt seems to name a model (`request.named_model`): "an Agent call with model: X runs on it, and Model Router keeps it."
- `fallback._note` adds one line next to every Agent call the PreToolUse fallback rewrites (only when the mod is not active): what was set and why, then the "Redo:" sentence again.
- `hooks.post_agent` adds a note when a foreground run switched models and its brief had a risk signal. `hooks.agent_failed` names the model to use after a model error.
- `calls.marked_redo` reads the mark. The `route` skill repeats the same rules at length.
- Tests: `test_the_text_in_context_every_session_stays_within_budget` holds the default note to 360 characters. `test_the_notes_state_facts_and_give_no_commands` bans sentences that open with a command word.

## What the sources say

### How hook text reaches Claude

- "Claude Code wraps the string in a system reminder and inserts it into the conversation at the point where the hook fired. Claude reads the reminder on the next model request, but it doesn't appear as a chat message in the interface." https://code.claude.com/docs/en/hooks#add-context-for-claude
- Where it lands: "SessionStart and SubagentStart: at the start of the conversation, before the first prompt"; "UserPromptSubmit and UserPromptExpansion: alongside the submitted prompt"; "PreToolUse, PostToolUse, PostToolUseFailure, and PostToolBatch: next to the tool result". Same page and section.
- A system reminder is how Claude Code delivers CLAUDE.md, the output style and hook text alike: "The following all reach Claude as system reminders: Your CLAUDE.md files; The instructions of your output style; Text a hook returns as `additionalContext`; The list of available skills". "In a logged API request, a system reminder appears wrapped in `<system-reminder>` tags inside a user message, or on some models as a separate message with the `system` role." https://code.claude.com/docs/en/glossary (section "System reminder")
- For UserPromptSubmit, "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name; Claude reads both." https://code.claude.com/docs/en/hooks#userpromptsubmit-decision-control
- "Claude Code saves the injected text in the session transcript. For mid-session events like `PostToolUse` or `UserPromptSubmit`, when you resume ... Claude Code replays the saved text rather than re-running the hook for past turns ... `SessionStart` hooks run again on resume." https://code.claude.com/docs/en/hooks#add-context-for-claude
- After compaction: "SessionStart hooks that match the `compact` source: Claude Code runs them and adds their output to the compacted context", while "Context that hooks added earlier" is "Summarized with the rest of the conversation". https://code.claude.com/docs/en/context-window
- "Claude's first response still waits for the hooks to finish, so their context reaches Claude." https://code.claude.com/docs/en/hooks#sessionstart
- Subagents do not get it. A non-fork subagent starts with its own system prompt, the task message, CLAUDE.md, git status, preloaded skills and a sibling roster; hook context from the main conversation is not on the list. https://code.claude.com/docs/en/sub-agents#what-loads-at-startup. The event that adds text to a subagent is SubagentStart: "String added to the subagent's context at the start of its conversation, before its first prompt." https://code.claude.com/docs/en/hooks#subagentstart
- Subagents nest by default: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation." https://code.claude.com/docs/en/sub-agents#let-subagents-spawn-their-own-subagents

### Size limits

- "A hook's `additionalContext`, `systemMessage`, and `initialUserMessage` strings, and its plain stdout, are capped at 10,000 characters." Over it, Claude Code "replaces the output with the file path and a preview of up to the first 2,000 characters", "this cap has no setting or environment variable to raise it", and "Claude Code doesn't ask Claude to read the file, so keep anything Claude must always see within the cap." https://code.claude.com/docs/en/hooks#json-output
- "When several hooks return `additionalContext` for the same event, Claude receives all of the values." A `<system-reminder>` tag in the string reaches Claude with its `<` replaced by `&lt;`. https://code.claude.com/docs/en/hooks#add-context-for-claude
- A UserPromptSubmit hook that times out "is canceled and its output, including any `additionalContext`, is discarded. The prompt still reaches Claude without that context." https://code.claude.com/docs/en/hooks#userpromptsubmit
- No page sets a size below 10,000 characters for hook text. The 360-character budget is the repo's own.

### The prompt cache

- Claude Code orders a request as system prompt (core instructions, tool definitions), project context (CLAUDE.md, auto memory, unscoped rules), then conversation. "An addition to the conversation layer leaves the system prompt and project context cached. A change to the system prompt invalidates everything." https://code.claude.com/docs/en/prompt-caching
- "Claude Code never invalidates the cache for a plugin's skills, commands, agents, hooks, monitors, or themes. It appends their content after the existing conversation, so the next request pays for that content and still reads everything before it from the cache." https://code.claude.com/docs/en/prompt-caching (section "Plugin components that keep the cache")
- Hook text sits in the cached prefix and its place matters: 2.1.265 "Fixed agent teammates and resumed subagents moving SubagentStart hook context and preloaded skills out of the prompt prefix on later turns, which broke prompt-cache reuse." https://code.claude.com/docs/en/changelog
- A changed tool description or system prompt section in a running conversation needs `breakPromptCache: true`, and then "the prompt cache starts over, so that turn is slower and more expensive." https://code.claude.com/docs/en/plugins/mods/reference (section "Send a changed system prompt section or tool description with `breakPromptCache`")
- Context cost by feature: Hooks "Zero, unless hook returns additional context"; CLAUDE.md and output styles cost "Every request". https://code.claude.com/docs/en/features-overview (section "Context cost by feature")

### Wording, and the prompt-injection defense

- "Write the text as factual statements rather than imperative system instructions. Phrasing such as "The deployment target is production" or "This repo uses `bun test`" reads as project information. Text framed as out-of-band system commands can trigger Claude's prompt-injection defenses, which causes Claude to surface the text to you instead of treating it as context." https://code.claude.com/docs/en/hooks#add-context-for-claude
- The defense acts on harness text too: 2.1.207 "Fixed spurious prompt-injection warnings triggered by benign system-generated conversation updates". https://code.claude.com/docs/en/changelog
- What `additionalContext` is for: "information Claude should know about the current state of your environment or the operation that just ran". "For instructions that never change, prefer CLAUDE.md." https://code.claude.com/docs/en/hooks#add-context-for-claude
- Text near a tool result: "Claude is trained to treat instructions that appear inside tool results with appropriate skepticism." https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks
- Emphasis: "Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule." https://code.claude.com/docs/en/best-practices (section "What you can stop doing"). "The model treats an instruction that contains "never" as absolute." https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2
- Nothing is enforced: CLAUDE.md "is delivered as a user message after the system prompt ... there's no guarantee of strict compliance". https://code.claude.com/docs/en/memory. "Your prompt, `CLAUDE.md`, or a skill ... there's no *guarantee* that it'll follow your instructions." https://code.claude.com/docs/en/best-practices (section "Deterministic and non-deterministic instructions")
- Every always-on line costs attention: "every line in it takes a little of Claude's attention on *every* task, whether it's relevant or not." https://code.claude.com/docs/en/best-practices (section "Keep CLAUDE.md short")

### The Agent tool's own text

From `[mod-types]` `claude-code-tools/index.d.ts`, built from the tool's input schema:

| Field | The tool's text | What our notes ask | Fit |
| :- | :- | :- | :- |
| `model` | "Optional model override for this agent. Takes precedence over the agent definition's model frontmatter and the configured default subagent model." No limit on when | Name it only when the user did or the task reads harder or easier than its brief | Allowed, narrower than the tool |
| `effort` | "Set this ONLY when the user, or instructions such as CLAUDE.md or a skill, explicitly ask that this agent or delegated work run at a specific effort level, never on your own judgment; otherwise omit it" | Omit it "unless the user named one" | Allowed, but drops the CLAUDE.md and skill case the tool names |
| `description` | "A short (3-5 word) description of the task" | Put "Redo:" in front on a redo | Fits the field; no meaning beyond display is documented |

- The docs agree: the model is a parameter "which Claude can pass when it starts the subagent"; effort is passed "When you ask Claude to run a non-fork subagent at a specific effort level". https://code.claude.com/docs/en/sub-agents#choose-a-model, https://code.claude.com/docs/en/sub-agents#choose-an-effort-level. 2.1.292 "Added an `effort` parameter to the Agent tool, so Claude runs a sub-agent at the effort level you ask for". https://code.claude.com/docs/en/changelog
- Under FORCE, "Claude Code ignores the `model` field in subagent definitions, and Claude can't pass a model when it starts a subagent." https://code.claude.com/docs/en/sub-agents#run-every-subagent-on-one-model
- A named model above the user's cap is lowered by the router (`test_a_model_named_on_the_call_is_lowered_to_the_cap`), so "Model Router keeps it" in the named-model note is not true there. That is the repo's behavior, not a source.

### Other carriers

- CLAUDE.md: "To include instructions in a plugin, write them as a skill. Claude Code doesn't load a `CLAUDE.md` at the plugin root, and `claude plugin validate` warns `CLAUDE.md at the plugin root is not loaded as project context`." https://code.claude.com/docs/en/plugins/components#skills. Writing into the user's own CLAUDE.md is not a documented plugin path.
- Skill: loads "On demand, when invoked or relevant"; best for "Reference material, repeatable workflows". https://code.claude.com/docs/en/features-overview (tab "CLAUDE.md vs Rules vs Skills"). Only the description is listed each session, cut at 1,536 characters, inside a listing budget of "1% of the model's context window". Once invoked, the body "stays there across later turns", and after compaction Claude Code keeps "the first 5,000 tokens of each". https://code.claude.com/docs/en/skills. "If a rule must hold every time ... add it to the plugin as a hook rather than a skill." https://code.claude.com/docs/en/plugins/components#skills
- Output style: `force-for-plugin` "Overrides the user's `outputStyle` setting. If multiple enabled plugins set this, Claude Code uses the first one loaded." Custom styles "leave out Claude Code's section of built-in software engineering instructions ... unless `keep-coding-instructions` is set to `true`." It is for "Every response in a certain voice, length, or format", and "styles don't change how" non-fork subagents respond. https://code.claude.com/docs/en/output-styles
- `tool.describe` (mod): fires "Once for each tool, when its description is first sent to Claude" and returns `{ description }`. https://code.claude.com/docs/en/plugins/mods/reference#tools. In `[mod-types]` the hook's input has `tool`, `description`, `isDeferred`, `provider` and `mcpServer` only; no parameter schema, so the `effort` parameter's text can't be rewritten there. The type file opens "EARLY ACCESS: this surface may change between releases without notice." The built-in guard passes over a user's `tool.describe` hooks only for "the descriptions of your organization's tools". https://code.claude.com/docs/en/plugins/mods/admin#know-which-hooks-of-a-users-mod-dont-run
- What a tool description is for: "What each parameter means and how it affects the tool's behavior". https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools. But changing the subagent tool's text changes delegation: "Change your subagent tool's description only if Claude Fable 5.2 starts more subagents than your tasks need." "In Anthropic's testing at `high` effort, a longer description focused on this roughly halved the number of subagents compared to a shorter version." https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2
- `prompt.section`, `prompt.compose`, `prompt.context` and `prompt.attachment` (mod) never run for a user's mod where the guard loads (managed settings, or a Team or Enterprise login). https://code.claude.com/docs/en/plugins/mods/admin#know-which-hooks-of-a-users-mod-dont-run
- `prompt.submit` (mod) can "Add text only Claude reads, after the prompt" with `next({ ...e, context })`. https://code.claude.com/docs/en/plugins/mods/events (section "Rewrite or add to a prompt"). It is not on the guard's list.
- `systemMessage` (any hook): "Warning message shown to the user." "To surface a message to the user on any platform, return `systemMessage`." https://code.claude.com/docs/en/hooks#json-output. SessionStart input carries `source` ("startup", "resume", "clear", "compact" or "fork"). https://code.claude.com/docs/en/hooks#sessionstart-input

### Plugins and standing instructions

- A plugin's standing instructions are its skills, agents and commands: "Skills, commands, and agents: these enter Claude's context as instructions, so they influence what Claude does with the tools it already has." https://code.claude.com/docs/en/plugins/security
- The documented cost figure counts only those: "The always-on figure counts each component's name plus its `description` and `when_to_use` frontmatter." The sample `claude plugin details` output marks a hook row "harness-only" with no model context cost, and "Hooks and MCP servers get no cost estimate". https://code.claude.com/docs/en/plugins/measure. So the session note is not in the figure a user sees.
- Standing lines can raise cost: "Standing instructions to delegate: Lines that tell the model to delegate can sit in system prompts, skills, and agent files. Read those files before you migrate and remove the lines you no longer need if the model delegates too much in testing." https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2
- No page describes a plugin giving the main conversation standing instructions through SessionStart text. The hooks page's own examples are environment facts (branch, changed files, active issue). https://code.claude.com/docs/en/hooks#sessionstart-decision-control

## Verdict

Partly right. The carrier is the right one: a plugin can't ship CLAUDE.md, a skill loads only on demand, an output style would override the user's own style, `prompt.section` is blocked under the guard, and `tool.describe` can't reach the `effort` parameter's text and is documented to shift how often Claude delegates, while SessionStart `additionalContext` works on both paths, comes back after compaction, stays cached, and is far under the 10,000-character cap. The wording follows the hooks page (facts, no commands, no emphasis), and the per-prompt note is silent unless needed. What is off is the content: the effort sentence is narrower than the Agent tool's own rule, notes meant for the user go through Claude and repeat on every resume and compaction, the named-model note says something false under FORCE and above the cap, one note is worded for code only, and the redo rule is repeated next to every rewritten call.

## What the sources do not say

- Whether a hook's `additionalContext` counts as one of the "instructions such as CLAUDE.md or a skill" in the Agent tool's effort text. The glossary puts all three in the same channel, but the tool text names only CLAUDE.md and skills.
- Which request layer the SessionStart reminder sits in, and whether a synchronous SessionStart hook's text is added again on every resume. Only the async case is documented (https://code.claude.com/docs/en/hooks#limitations).
- Whether PreToolUse and PostToolUse `additionalContext` sits inside the `tool_result` block or beside it. The hooks page says only "next to the tool result".
- Any measured comparison of a system reminder, a tool description and a skill for how reliably Claude follows a convention such as the "Redo:" mark.
- Whether a `tool.describe` change to the Agent tool reaches subagents or teammates. The type file says only that it fires "when the engine first renders the tool's schema in a session".
- Whether a `description` that starts with "Redo:" changes anything but what the task list shows.
- Whether `prompt.submit` context reaches Claude as a system reminder, or how it is placed for the cache.
- Whether leaving hook text out of the `claude plugin details` figure is meant for hooks that add context.
- How a background run's model swap reaches the parent. Background is the default, PostToolUse returns `async_launched` for it, and the SubagentStop input lists no `modelsUsed`, so `hooks.post_agent`'s swap note fires only for foreground runs.
- Whether nested subagents, which never see the session note, need the redo mark. Nesting is on by default; how often it happens under this plugin is not measured.
