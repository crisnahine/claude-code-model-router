# State: the files under the plugin data directory, locking and migration

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

## What we built

- `store.data_dir` uses `CLAUDE_PLUGIN_DATA`, else `~/.claude/plugins/data/model-router-local`, and creates the folder on every call, reads included.
- Nine record kinds are keyed by session id, each in one JSON file that every session shares: `sessions`, `prompts`, `routes`, `edits`, `pending`, `launched`, `done`, `mod`, `allowlist`. `store.mutate_entry` keeps the 200 most recently written sessions per file (`KEEP_ENTRIES`), `calls.KEPT_FOR` drops a session from `routes`, `launched` and `done` after a day, and `store.keep` keeps 100 records per session.
- Five more are shared by design: `state.json` (the options as the last SessionStart saw them, `settings.record`, plus model health, `health._edit`), `learned.json` (`learn._update`), `upstream.json` (`upstream.refresh`), `locks.json` (`store._count`) and `ledger.jsonl` (`store.append_ledger`, cut to its newer half past 4 MiB).
- A write is a temp file plus `os.replace` (`store.write_atomic`). Every read-modify-write takes a lock file made with `O_CREAT | O_EXCL` (`store.locked`): it waits up to 1 s, breaks a lock older than 10 s, and otherwise skips the write (`Busy`) and counts it in `locks.json`, which is written without a lock.
- Each JSON file carries `schema` (`store.SCHEMA = 1`). `store._read_state` runs `MIGRATIONS` (one step, which returns its input), reads a file from a newer release without ever writing it, and moves a file that fails to parse aside, keeping three copies (`store._set_aside`).
- The mod (`hooks/router.ts`) keeps what only it reads in module variables (`agentEffort`, `callerEffort`, `inFlight`, `turnRequests`, `agentType`, `sessionEffort`, 500 entries each) and sends every event to a new Python process (`ask`), which reads and writes the files above.

## What the sources say

Pages fetched 2026-11-24 as `.md`, with Claude Code 2.1.331 installed. ### Where the data directory is and how long it lives

- Location and use: "`${CLAUDE_PLUGIN_DATA}` | `~/.claude/plugins/data/<id>/`, created on first reference and kept across plugin updates. `<id>` is the plugin identifier with every character other than a letter, digit, `_`, or `-` replaced by `-`" (https://code.claude.com/docs/en/plugins/manifest-reference#environment-variables). The hooks page names state as a use: "the plugin's persistent data directory, for dependencies and state that should survive plugin updates" (https://code.claude.com/docs/en/hooks, "Reference scripts by path").
- One folder per plugin id, and the id names the origin: "Every plugin has an id of the form `<name>@<origin>`", with `@<marketplace>`, `@inline`, `@skills-dir` and `@synced` (https://code.claude.com/docs/en/plugins/loading). A `--plugin-dir` copy and a marketplace copy keep separate state. Observed on this machine: `model-router-claude-code-model-router`, `model-router-inline` and `model-router-synced`, plus an empty `model-router-local` that the fallback in `store.data_dir` made. `local` is no documented origin.
- Shared by sessions and projects: the path has no session or project part, so every session and project that loads the plugin under one id uses one folder. No page says this in words. For the mod store the docs do: "A key-value store that every session on the machine shares" (https://code.claude.com/docs/en/plugins/mods/reference, "Mods API methods").
- Shared by versions: "Because `${CLAUDE_PLUGIN_ROOT}` points at a version directory, a plugin's root path changes with every version. Keep a plugin's durable files in `${CLAUDE_PLUGIN_DATA}` instead" (https://code.claude.com/docs/en/plugins/loading#find-plugins-on-disk). Two releases can run at once: "It removes that directory in a background cleanup 14 days later, so a session that already loaded the old version keeps running" (https://code.claude.com/docs/en/plugins/loading#cleanup-of-previous-versions), and "When a copied plugin updates mid-session, hook commands, monitors, MCP servers, and LSP servers keep using the previous version's path" (same page, "When auto-update runs").
- Uninstall: "When you uninstall a plugin from the last scope it's installed at, Claude Code also deletes the plugin's stored options and secrets and its data directory". It stays "With `--keep-data`", when "another installed plugin uses the same folder", or when the install records can't be read back (https://code.claude.com/docs/en/plugins/cli-reference#what-an-uninstall-deletes-and-keeps).
- No age-out: the sweep list at https://code.claude.com/docs/en/claude-directory#cleaned-up-automatically names `plugins/data/.set-aside/`, the folders of a marketplace "your organization replaced", and not `plugins/data/<id>/`. The plugin has to bound its own files, as it does.
- Who gets the path: hook commands get "`CLAUDE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA`, `CLAUDE_PROJECT_DIR`, and `CLAUDE_PLUGIN_OPTION_<KEY>`" in their environment, and "The variables aren't present in the environment of commands Claude runs through the Bash tool ... In skill, command, and agent content, write the `${...}` reference in the Markdown body instead" (https://code.claude.com/docs/en/plugins/manifest-reference, "Where each variable resolves"). A mod gets it from `$.process.hookEnv()`: "`CLAUDE_PLUGIN_DATA` is this plugin's data folder, kept across updates: the call makes it, and rejects when it cannot" (type file, `process.hookEnv`).
- History: 2.1.78 "Added `${CLAUDE_PLUGIN_DATA}` variable for plugin persistent state that survives plugin updates; `/plugin uninstall` prompts before deleting it", and 2.1.281 "Changed `claude plugin uninstall --json` and the /plugin dialog to say a plugin's data was kept when its folder stays" (https://code.claude.com/docs/en/changelog).

### What runs at the same time

- "When an event fires, its matching hooks run in parallel" (https://code.claude.com/docs/en/hooks#hook-handler-fields). In `hooks/hooks.json` only SessionStart has two handlers, and they write different files: `session-start` writes `state.json` and `sessions.json`, `refresh-cache` writes `upstream.json`. This rule alone needs no lock here.
- Across events it does: "`PostToolUse` fires once per tool, which means it fires concurrently when Claude makes parallel tool calls" (https://code.claude.com/docs/en/hooks#posttoolbatch). So `post-agent` and `post-edit` runs overlap, and they write `routes`, `done`, `launched`, `edits`, health and the ledger.
- Subagents add more: "When a subagent calls a tool, tool events such as `PreToolUse` and `PostToolUse` fire the same configured hooks as in the main conversation" (https://code.claude.com/docs/en/hooks, "Hook locations"), and "Background subagents run concurrently while you continue working" (https://code.claude.com/docs/en/sub-agents, "Run subagents in foreground or background"), up to 20 at once by default (same page, "Concurrent subagent limit"). Edits from several subagents reach `edits.json` at the same moment.
- Sessions add more: one folder per plugin id, so every open session writes the same shared files.
- The mods docs name this race for their own store, and the fix: "A `get` followed by a `set` isn't atomic. When two sessions each read a value, change it, and write it back, they race, and the second write replaces the first." The first advice is "Give each item its own key: a `set` changes only its own key, so sessions that write different keys don't overwrite each other" (https://code.claude.com/docs/en/plugins/mods/interface#save-from-more-than-one-session).
- The primitives the lock and the writes rest on hold by spec. For `O_CREAT` with `O_EXCL`, "The check for the existence of the file and the creation of the file if it does not exist shall be atomic" (https://pubs.opengroup.org/onlinepubs/9799919799/functions/open.html). `os.replace`: "If successful, the renaming will be an atomic operation (this is a POSIX requirement)" (https://docs.python.org/3/library/os.html#os.replace). With `O_APPEND`, "the file offset shall be set to the end of the file prior to each write and no intervening file modification operation shall occur" (https://pubs.opengroup.org/onlinepubs/9799919799/functions/write.html).
- A record lock goes away with its holder: "All process-owned locks associated with a file for a given process shall be removed when any file descriptor for that file is closed by that process ... or the process holding that file descriptor terminates" (https://pubs.opengroup.org/onlinepubs/9799919799/functions/fcntl.html). A lock file made with `O_EXCL` stays behind when its holder dies, which is why `store.locked` needs its 10 s stale check. Two waiters that both find a stale lock can both remove it, the second removing the first one's new lock.
- Observed here, not a source: this machine's `locks.json` shows 6 waits on `routes.json` and 2 on `ledger.jsonl`, none skipped and none on another session's lock. The waits came from inside one session.

### Can the mod keep state in memory

- Three places, three lifetimes (https://code.claude.com/docs/en/plugins/mods/interface#keep-state). A module-level variable lasts until "The module reloads", for "Values you can lose". `$.state` lasts until "The session ends, or the user runs `/clear`, `/resume`, or `/branch`". `$.store` lasts until "Your mod deletes it, or no session reads or writes the store for `cleanupPeriodDays`", and is "saved as a JSON file of your plugin's own under `~/.claude/plugins/store/`". The type file caps it: "Rejects a function, a cycle, or a store over 4 MiB of JSON text in all."
- "a mod's hooks share the variables in its file, so what one hook records, another can show" (https://code.claude.com/docs/en/plugins/mods/overview#what-a-mod-can-do). `router.ts` already does this for the values only the mod reads.
- Settings hooks can't read that memory. A mod is "Functions in a plugin that Claude Code calls in its own process", and a settings hook is "A shell command, HTTP request, or prompt that Claude Code runs on a lifecycle event" (https://code.claude.com/docs/en/plugins/mods/overview#compare-mods-settings-hooks-skills-and-mcp-servers). In this plugin, results, stops, edits, prompts and the Stop checks all arrive through settings hooks, and the mod's own questions go to a new Python process each time.
- The mod can't take those events over everywhere. Where the built-in guard loads, a user's mod hook on "`classic.<Event>`, such as `classic.Stop`" never runs (https://code.claude.com/docs/en/plugins/mods/admin#know-which-hooks-of-a-users-mod-dont-run). With `allowManagedModsOnly`, "Claude Code refuses users' own mods, so none of their hooks run. Users' settings hooks, status lines, and `/goal` keep working" (same page, "Choose how much to allow"). On that path the plugin has only files.
- `$.store` can't stand in for the folder. Its file name and format aren't documented past the line above, so the Python hooks can't read it, and it has the same unlocked read-then-write that the plugin's lock exists to stop.
- After `/clear`, `/resume` or `/branch`, `$.state` is back at its defaults and "`session.start` doesn't fire again" (https://code.claude.com/docs/en/plugins/mods/interface#load-a-saved-value-again-after-clear).

No source forces the rest:

- The options copy in `state.json`. Skill content gets the values itself: "`${user_config.KEY}`: substituted in MCP server config, LSP server config, exec-form hook `args`, and skill and agent content. In skill and agent content, only non-sensitive values are substituted" (https://code.claude.com/docs/en/plugins/manifest-reference#reference-a-saved-value). All eight options in `plugin.json` are non-sensitive. The values live in `pluginConfigs`, whose scope is "User or managed", and "Claude Code ignores project and local entries" (https://code.claude.com/docs/en/settings-reference#pluginconfigs), so there is one set to read, and the copy only lags it.
- `locks.json`, which only counts.
- `done`, `launched`, the request's level and floor, and `learned.json`. They serve the marked redo and the vote learning. The docs name no field that marks a call as a retry, and they do document the caller's own per-call choice: "The per-invocation `model` parameter, which Claude can pass when it starts the subagent" (https://code.claude.com/docs/en/sub-agents#choose-a-model). Whether those records stay is the redo and learning decision, not this one.
- One shared file per record kind. No source asks for it, and the mods docs advise one key per item for state that sessions share.

### Versions and migration

- A new release reads what an old one wrote ("kept across plugin updates"), and the old one can still be running beside it (both quoted above). That backs a `schema` field and the rule that a file from a newer release is read and never written, for files every session shares.
- A record that lives as long as its session is written by the release that session loaded, until `/reload-plugins` switches it (https://code.claude.com/docs/en/plugins/loading, "When auto-update runs"). Held in a file of its own, a shape the reader doesn't know can be dropped, at the cost of that session's redo records.
- `store.MIGRATIONS` has one step, and it returns its input. No source asks for a migration step before a shape changes.

## Verdict

Partly right.

The folder, the atomic replace, the lock and the newer-file rule are right: the docs put durable plugin state in `${CLAUDE_PLUGIN_DATA}`, PostToolUse hooks and background subagents' hooks run at the same time, every session of the plugin shares the folder, and an old release can keep writing it for up to 14 days. The layout is wrong for what the documented behavior needs: nine per-session record kinds sit in nine files that every session shares, so each write rewrites up to 200 sessions' records, can wait on another session's lock, and meets an older release's shape, where the mods docs' own advice for shared state is "Give each item its own key". The options copy, `locks.json` and the do-nothing migration step serve nothing a source requires, and `${user_config.KEY}` already hands skills the options. Mod memory can't replace the files, since the settings hooks run in other processes and the fallback runs with no mod at all, so the mod should keep holding only what it alone reads, as it does now.

## What to change

No item is required by a source. Each is judgment, with the source that backs it.

1. state-design-1. One file per live session. Keep each session's records in a file of its own, such as `sessions/<session_id>.json`, holding the model, the mod flag, the request, edit and check times, routes with pending rewrites, launched and done runs, and the allowlist layers. Check `session_id` against a strict pattern (letters, digits, `-` and `_`, at most 128 characters) before it names a file, and write nothing for one that fails. Lock only that file. At SessionStart, delete session files not written for a day. A SessionEnd hook could delete the file sooner ("Useful for cleanup tasks", https://code.claude.com/docs/en/hooks#sessionend), but it gets 1.5 seconds, so the sweep stays either way. Touches `store._keyed`, `load_entry`, `mutate_entry`, `save_entry`, `update_entry`; `calls._mutate`, `routed`, `route_of`, `strongest`, `_wait_or_finish`, `_stopped`, `last_run`, `finished_run`; `request.load`, `begin`, `raise_to`, `note_edit`, `deliver`, `mark_escalation`; `session.record`, `session.model`; `mod.active`, `mod._heard`; `fallback.remember`, `forget`, `refused`; `gates.note_edit`, `note_check`, `note_agent_checks`, `unverified_edit`; `allowlist.remember`, `allowlist._stored`; `bench/overhead.py`, the store, calls and overhead tests, and ARCHITECTURE.md "State" and PERFORMANCE.md "State locks a spawn takes" and "State size". Deletes the nine shared files, `store.KEEP_ENTRIES` and the session prune in `mutate_entry`, `calls.KEPT_FOR` and `max_age`, every wait on another session's lock, and the fallback spawn's fourth lock, since routes and pending share a file. The trade: an edit and a spawn of one session now share one lock, but each write holds one session's records, not 200 sessions'. Backed by https://code.claude.com/docs/en/plugins/mods/interface#save-from-more-than-one-session (one key per item), https://code.claude.com/docs/en/plugins/manifest-reference#environment-variables (one folder per plugin id) and https://code.claude.com/docs/en/plugins/loading#cleanup-of-previous-versions (two releases at once). Judgment. Size: large.
2. state-design-2. Take options from `${user_config.KEY}`. Pass each option to the skill commands through `${user_config.<key>}` in the `SKILL.md` command lines, and read it there the way hooks read `CLAUDE_PLUGIN_OPTION_<KEY>`. Touches `settings.record`, `settings.resolve` and `settings.Snapshot` (the `recorded` path), the `settings.record` call in `hooks.session_start`, `cli.main` (`Snapshot(None, recorded=True)` and a way to take the values), and the command lines of the four skills that run the launcher (`models`, `refresh`, `route`, `usage`) with their `allowed-tools` patterns. Deletes one `state.json` read-modify-write per SessionStart and the options half of `state.json`, which then holds model health only. Backed by https://code.claude.com/docs/en/plugins/manifest-reference#reference-a-saved-value. Judgment. Size: small.
3. state-design-3. Keep the version rule only where releases share a file. Keep `schema` and "a newer file is read, never written" on the shared durable files: `state.json` (health), `learned.json` and `upstream.json`. Give per-session files no `schema`, and drop one that doesn't parse or has a shape the reader doesn't know. Set aside a corrupt copy only for `state.json` and `learned.json`, since `upstream.json` refetches. Delete `store.MIGRATIONS` and its loop in `_read_state` until a shape really changes. Touches `store.SCHEMA`, `MIGRATIONS`, `_read_state`, `_set_aside`, `KEEP_SET_ASIDE`, `set_aside`, `newer_files`, and ARCHITECTURE.md "State" and "Compatibility". Deletes the do-nothing migration step and set-aside copies of files that are a day's cache. Backed by https://code.claude.com/docs/en/plugins/loading#cleanup-of-previous-versions and the same page's "When auto-update runs" for the part kept. Judgment. Size: small.
4. state-design-4. Drop `locks.json`. Write a ledger row when a write is skipped, and stop counting waits. Touches `store._count`, `lock_counts`, `owner` and the owner write in `locked`; `report.LOCK_EVENTS`, `lock_rows`, `lock_table`; `cli.main` (`store.owner`); the `locks` key of `models --json`, whose removal bumps `model-router.models/1` under the repo's own compatibility rule. Deletes one shared file written without a lock and the read of each held lock's session name. Its stated purpose, telling whether cross-session waits matter, ends with state-design-1. No source needs it. Judgment. Size: small.
5. state-design-5. Drop the redo and vote records with their decisions. If the redo and learning decisions settle on the caller's own `model` and `effort` and drop the marked redo and the votes, delete `done`, `launched`, the request's `level`, `need` and `floor_off`, and `learned.json` from the store in the same change. The per-session record is then the model, the mod flag, edit and check times, routes with pending rewrites, the allowlist layers and the escalation flag, and the shared files are health, the upstream cache and the ledger. Touches `calls._wait_or_finish`, `_stopped`, `last_run`, `finished_run`, `_keep_done`; `learn._path`, `_update`, `reset`; `request.Request` and `request.start`; `cli._reset_feedback`. Backed by https://code.claude.com/docs/en/sub-agents#choose-a-model (the caller's per-call `model`); that no input marks a retry is not documented either way. Judgment, and it waits on those decisions. Size: medium.
6. state-design-6. Optional: OS record locks. Lock with `fcntl.lockf` on POSIX (and `msvcrt.locking` on Windows) on the lock file, in place of `O_EXCL` plus the 10 s age check, so a dead holder's lock goes away with it. Touches `store.locked` and `LOCK_STALE_SECONDS`. Deletes the stale-lock branch, its `broken` count and the race where two waiters remove one stale lock. Backed by https://pubs.opengroup.org/onlinepubs/9799919799/functions/fcntl.html. Judgment, lowest priority: the current lock is correct while no holder dies. Size: small.

## What the sources do not say

- In words, that the data folder is shared by all sessions and projects. It follows from the path, which has no session or project part.
- Whether the PreToolUse hooks of parallel tool calls run at the same time. The docs say it for PostToolUse only.
- Whether a mod's hooks for different events, such as two `agent.spawn` calls, run at the same time or one after another. `router.ts` assumes they overlap (`inFlight`).
- The file name and format of `$.store` under `~/.claude/plugins/store/`.
- Whether a variable a mod sets with `$.env.set` reaches later settings hook processes. The type file says it "Sets the variable for this process and everything it starts after", which would let the mod flag replace the `mod` record, but no page says hooks see it, and "Some names are launch-only". A live check would be needed first.
- What a command run by hand, outside Claude Code, should use as its data folder. `model-router-local` is the plugin's own choice.
- Whether `session_id` is always safe as a file name. The examples show a UUID, so the plugin has to check it before using it as one.
- Whether a session's id changes on `/clear`. SessionEnd fires with reason `clear` and SessionStart with source `clear`, but no page says the id changes.
- Whether `os.replace` is atomic on Windows. The Python docs tie atomicity to POSIX. Nothing in the Claude Code docs covers a write cut off by power loss, and the plugin calls no `fsync`.
- Whether one folder serves a plugin installed at user and project scope at once. "from the last scope it's installed at" implies one.
