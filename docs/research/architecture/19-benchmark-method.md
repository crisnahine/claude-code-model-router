# The benchmark method

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

## What we built

- `bench/run.py` `run_one` copies a task's `repo/` to a fresh temp folder and runs `command()`: `claude -p <PROMPT> --output-format json --model <m> --max-budget-usd <b> --setting-sources project --strict-mcp-config --permission-mode dontAsk --allowedTools Read Edit Write Glob Grep "Bash(python3 *)" "Bash(python *)" "Bash(tail *)" "Bash(head *)" "Bash(echo *)"`, plus `--plugin-dir` for router configs.
- `command()` strips inherited `CLAUDE_CODE_*` and `CLAUDE_PLUGIN_*` variables (keeping `CLAUDE_CODE_USE_*` and `CLAUDE_CODE_OAUTH_TOKEN`), sets `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and a per-run `CLAUDE_CODE_PLUGIN_CACHE_DIR`. It does not set `CLAUDE_CONFIG_DIR`, so `~/.claude.json` and `~/.claude/projects/` are shared. `session_dir` and `_forget_session` guess and delete the transcript folder.
- `PROMPT` tells the main loop to hand the task to one subagent and relay its answer. `configs.json` holds 20 configs: no plugin (`defaults`), forced subagent models (`CLAUDE_CODE_SUBAGENT_MODEL` plus `_FORCE`, some with `CLAUDE_CODE_SUBAGENT_EFFORT`), `opusplan`, `advisor`, and nine router variants.
- `grade()` runs each task's deterministic `check.py` under `python -I` with credentials stripped. Each task ships a reference solution plus `wrong/` and `right/` sets that `tests/test_bench.py` checks. `record()` keeps `total_cost_usd`, `modelUsage`, the undocumented `subagent_stats`, and only the `tool_name` of each `permission_denials` entry.
- `bench/analyze.py` pools runs per task class and config: Clopper-Pearson on runs (`exact_interval`), a run-level bootstrap for cost per solved task (`_cell`), and an exact one-sided test with Holm across baselines (`_quality`, `_lower_p`). `MIN_RUNS = 10`. A class counts as saturated when the weakest forced baseline can't be told from the strongest.
- Data: in `docs/BENCHMARKS.md`, 5 of 8 classes in the Opus table are saturated (Haiku 10 of 10, `fable-high` 10 of 10). Bash was denied in 78 of the 90 quality-pilot rows (`bench/results/pilot/`), in 11 of 12 `redo-mark` rows, and in 507 of the 1,280 rows in `bench/results/*.jsonl`. The rate differs by config: 12 to 17 of 80 for the `sonnet-*` and `opusplan` configs, 35 to 63 for the rest. Pilot answers say what this did: "The subagent's shell commands were denied, so it couldn't build a test database, compare old and new output, or count the statements" (`defaults`, `bugfix-statement-queries`).

## What the sources say

Checked 2026-11-24 against Claude Code 2.1.331 (`claude --version`). Pages were fetched that day as `.md` from code.claude.com and platform.claude.com, and as HTML from anthropic.com.

### Building evals: success criteria, tasks, grading

- Success criteria should be "Specific", "Measurable", "Achievable" and "Relevant", and "Most use cases need multidimensional evaluation along several success criteria", with latency and price named as criteria. https://platform.claude.com/docs/en/test-and-evaluate/develop-tests
- "Be task-specific: Design evals that mirror your real-world task distribution." "Prioritize volume over quality: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." https://platform.claude.com/docs/en/test-and-evaluate/develop-tests
- Grading order: "Code-based grading: Fastest and most reliable, extremely scalable, but also lacks nuance for more complex judgments". "LLM-based grading: Fast and flexible, scalable and suitable for complex judgment. Test to ensure reliability first, then scale." Tips: detailed rubrics, "instruct the LLM to output only 'correct' or 'incorrect'", and "Use a grader model with thinking on". https://platform.claude.com/docs/en/test-and-evaluate/develop-tests
- Capability evals "should start at a low pass rate, targeting tasks the agent struggles with and giving teams a hill to climb." "An eval at 100% tracks regressions but provides no signal for improvement." https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- "A good task is one where two domain experts would independently reach the same pass/fail verdict." "For each task, it's useful to create a reference solution: a known working output that passes all graders." "Test both the cases where a behavior should occur and where it shouldn't." https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- "It's essential that the agent in the eval functions roughly the same as the agent used in production, and that the environment itself doesn't introduce further noise." Each trial should start "from a clean environment", since "Unnecessary shared state between runs (leftover files, cached data, resource exhaustion) can cause correlated failures due to infrastructure flakiness rather than agent performance." https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- "We recommend choosing deterministic graders where possible, LLM graders where necessary or for additional flexibility, and using human graders judiciously for additional validation." "it's often better to grade what the agent produced, not the path it took." "LLM-as-judge graders should be closely calibrated with human experts". https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- Work that is not code: for research agents, "Groundedness checks verify that claims are supported by retrieved sources, coverage checks define key facts a good answer must include", "For tasks with objectively correct answers ... exact match works", and "LLM-based rubrics should be frequently calibrated against expert human judgment". https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- "You won't know if your graders are working well unless you read the transcripts and grades from many trials." https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- For cost and model choice: "Pull a few tasks from production logs, weighted like real traffic, and write outcome checks for each". "Baseline the model tiers across effort levels, not only the default, and plot score against spend. A multimodel configuration must beat the single model's whole curve." "On your own workload, judge a pairing against the same model at lower effort and against the next model down running alone." "Price the tail of your workload, not the median: compare models on the hardest tenth of your tasks, not the typical one." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence
- The documented cheap policy ("run every task at a low setting and re-run only the failures at a higher one") was "computed ... task by task from the Claude Opus 5.5 effort runs", and "you need a failure signal (here, the benchmark's own tests)". https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#re-run-failures-at-higher-effort

### Sample size and statistics

- "20-50 simple tasks drawn from real failures is a great start." "this large effect size means small sample sizes suffice. More mature agents may need larger, more difficult evals to detect smaller effects". "Because model outputs vary between runs, we run multiple trials". https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents
- On clustering: "we recommend clustering standard errors on the unit of randomization", and "clustered standard errors on popular evals can be over three times as large as naive standard errors". https://www.anthropic.com/research/statistical-approach-to-model-evals
- On resampling: "we recommend resampling answers from the same model several times, and using the question-level averages as the question scores". https://www.anthropic.com/research/statistical-approach-to-model-evals
- On pairing: "conducting a paired-differences test lets us eliminate the variance in question difficulty", and the paper "recommends reporting pairwise information ... whenever two or more models are being compared." https://www.anthropic.com/research/statistical-approach-to-model-evals
- On power: "Researchers might use the power formula to conclude that an eval with a limited number of available questions is not worth running on a particular pair of models." https://www.anthropic.com/research/statistical-approach-to-model-evals
- Infrastructure noise: "the gap between the most- and least-resourced setups on Terminal-Bench 2.0 was 6 percentage points (p < 0.01)". Pass rates "fluctuate with time of day". "running at multiple times and on multiple days would help average out the noise." "leaderboard differences below 3 percentage points deserve skepticism until the eval configuration is documented and matched." https://www.anthropic.com/engineering/infrastructure-noise
- Anthropic's own cost tables pool few runs: "Each score pools two runs on SWE-bench Pro and three on DeepResearch Bench II". They call close results "within run-to-run noise" without naming the test. https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#tune-effort

### Headless runs: isolation, permissions, budget, result JSON

- "`--bare` is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release." But "Hooks still don't run in bare mode when you pass them with `--settings`, or in the `hooks/hooks.json` or `hooks` manifest key of a plugin you load with a flag. Don't use bare mode for a run that needs them." So the router arm can't use `--bare`, and the bench is right to avoid it. https://code.claude.com/docs/en/headless#start-faster-with-bare-mode
- `--setting-sources` takes a "Comma-separated list of setting sources to load (`user`, `project`, `local`)". https://code.claude.com/docs/en/cli-reference
- Setting sources leave some inputs in: "`~/.claude.json` global config | Always read | Relocate with `CLAUDE_CONFIG_DIR` in `env`", and managed policy "loads from the host". "For multi-tenant deployments, run each tenant in its own filesystem and set `settingSources: []` plus `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`". https://code.claude.com/docs/en/agent-sdk/claude-code-features
- `CLAUDE_CONFIG_DIR`: "All settings, session history, and plugins are stored under this path." `CLAUDE_CODE_PROJECT_DIR_NAME`: "Set together with `CLAUDE_CONFIG_DIR` to choose the `projects/` directory name Claude Code stores that session's transcripts and auto memory under". https://code.claude.com/docs/en/env-vars
- Credentials follow the config dir: Claude Code "keys the macOS Keychain entry to that directory too, so a session with a different `CLAUDE_CONFIG_DIR` reads a different entry". `CLAUDE_CODE_OAUTH_TOKEN` is for "CI pipelines and scripts where browser login isn't available". https://code.claude.com/docs/en/authentication
- `--restricted` exists for this case: "Use it when an evaluation harness drives `claude` on a shared machine and Claude Code must not run commands or read that machine's user and project settings." It removes command tools "unless you name them individually in `--tools`" and "loads only managed settings and `--settings`". https://code.claude.com/docs/en/cli-reference
- `dontAsk` with an exact allowlist is the documented CI setup: "Run in CI with an exact allowlist | `claude -p "run the test suite" --permission-mode dontAsk --allowedTools "Bash(npm test)" "Read"`". In `dontAsk`, "Claude Code denies every call that would otherwise prompt". https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/headless#auto-approve-tools
- Why an allowlist misses commands: "Every subcommand must be allowed for a compound command to run without a prompt". A command that starts with a variable assignment needs that assignment in the rule ("`Bash(FOO=bar npm *)` approves `FOO=bar npm test`"). "Commands the analysis can't parse" ask for approval. https://code.claude.com/docs/en/permissions, https://code.claude.com/docs/en/sandboxing
- Subagents inherit the rules. Built-in subagents each inherit "the parent conversation's permission rules". A background subagent's permission prompts go to the main session, and `-p` with `dontAsk` has nobody to answer them. https://code.claude.com/docs/en/sub-agents
- Budget: `--max-budget-usd` counts subagent spend, and "Spend can pass the cap, so leave headroom." "Once spend reaches the cap, spawning another subagent fails with `Budget limit reached`, and Claude Code stops background subagents that are still running". https://code.claude.com/docs/en/cli-reference, https://code.claude.com/docs/en/agent-sdk/agent-loop#budget-headroom
- Result JSON: it "includes `total_cost_usd` and a per-model cost breakdown", and both are "client-side estimates". `modelUsage` covers "the main loop, subagents, and internal calls". A denial is `{ tool_name; tool_use_id; tool_input }`, and "`permission_denials` on the result message is the authoritative record". `terminal_reason` includes `"budget_exhausted"`. The result type lists no `subagent_stats`. https://code.claude.com/docs/en/headless, https://code.claude.com/docs/en/agent-sdk/typescript
- Checking that a plugin loaded: "Use the plugin fields in the `system/init` event to catch a plugin that didn't load" (`plugins`, `plugin_errors`). In stream output, subagent messages carry `parent_tool_use_id`, and "The last line of the stream is a `result` message". https://code.claude.com/docs/en/headless
- `CLAUDE_CODE_RETRY_WATCHDOG`: "Set to `1` for unattended sessions such as eval harnesses". https://code.claude.com/docs/en/env-vars

### Letting a headless subagent run tests safely

- The built-in sandbox: "Bash commands that modify files within the sandbox boundaries execute without prompting, even in Manual mode". "Auto-allow mode works independently of your permission mode setting, with three exceptions": plan mode, auto-mode per-command domains, and auto-mode classifier review. Settings: `sandbox.enabled` and `sandbox.autoAllowBashIfSandboxed`, set from a file or `--settings`. https://code.claude.com/docs/en/sandboxing, https://code.claude.com/docs/en/permission-modes
- Default boundary: writes go to "The working directory, a per-user temp directory, and directories you've added". Network has "No direct route out". But reads cover "Most of the machine, including credential files such as `~/.ssh` and `~/.aws/credentials`", and the environment is "Inherited from Claude Code, including any secrets in its environment". So add `denyRead` or `credentials` entries and `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`. Set `allowUnsandboxedCommands: false` to drop the unsandboxed retry and `failIfUnavailable` to refuse to start unsandboxed. https://code.claude.com/docs/en/sandboxing, https://code.claude.com/docs/en/env-vars
- `claude plugin eval` does the same: "When you grant `Bash` in any form, every command runs under Claude Code's OS-level sandbox. Writes are confined to the run's workspace, your home directory and Claude Code configuration are unreadable, and network access is limited to domains you grant". https://code.claude.com/docs/en/plugin-evals
- For fully unattended runs: "Run fully unattended inside a container | `claude -p "<prompt>" --dangerously-skip-permissions` | Required: a container, VM, or the sandbox runtime". The sandboxed Bash tool "on its own constrains only shell commands, so it is not sufficient for fully unattended runs in either mode". Hooks and MCP servers "run unconstrained on the host". https://code.claude.com/docs/en/permission-modes, https://code.claude.com/docs/en/sandbox-environments

### `claude plugin eval`

- It runs "a fresh, isolated non-interactive session with only your plugin loaded". "Each run gets a temporary home directory, working directory, and Claude Code configuration". Only an allowlist of environment variables plus `EVAL_*` reaches the run. https://code.claude.com/docs/en/plugin-evals
- "One run of a non-deterministic agent tells you little, so each case runs three times by default." `runs` is "1 to 50". Each case also runs "with no plugin loaded", and the difference between the two scores "is what the plugin contributed". https://code.claude.com/docs/en/plugin-evals
- Graders are `regex`, `tool_used`, `tool_order`, `file_exists`, `llm` and `baseline`. "There are no custom-code graders." An `llm` grader passes when "A judge model votes PASS on the rubric in at least two of three votes". To grade a test run: "have the prompt ask Claude to run it and write the outcome to a file, grade that file". That trusts the agent's own report. https://code.claude.com/docs/en/plugin-evals
- Runs "never stop to ask for permission". Tools that need a grant "are removed from the session". The CI advice is to pin `--model` and `--judge-model` "so scores are comparable over time", and to leave `partial: true` results "out of any trend you chart". https://code.claude.com/docs/en/plugin-evals
- It arrived in 2.1.269. Since 2.1.299 "a run that ends on an API error now scores 0 without grading". https://code.claude.com/docs/en/changelog

## Verdict

Partly right. The core matches the sources: fresh temp copies, deterministic outcome checks with reference solutions and wrong-answer sets, a documented `dontAsk` plus allowlist headless setup, a no-plugin baseline, a budget cap, list-price cost from `total_cost_usd`, and no claim of parity. A custom harness is also the right call, because `claude plugin eval` has "no custom-code graders" and only a with/without arm, so it can't express forced-model baselines. But the measurement doesn't match real use: Bash was denied in most runs, at rates that differ by config, so the agents couldn't run the checks the docs say they need ("functions roughly the same as the agent used in production"). The tasks are saturated (Haiku solves what Fable solves), and the analysis pools runs as independent with no clustering, pairing or power analysis. On top of that, the baselines skip the single-model effort curve that "a multimodel configuration must beat", and no task is work other than code.

## What the sources do not say

- Which commands were denied in the stored rows. `run.record` kept only `tool_name`, and the pages name likely causes (compound parts, a variable assignment in front, commands the parser can't read), but the data can't say which ones applied.
- Whether sandbox auto-allow covers commands a background subagent runs inside a `-p` `dontAsk` session. The sandboxing page says auto-allow works "independently of your permission mode", but doesn't name background subagents. Not documented; test it with one run before a batch.
- Whether `--bare`, once it is the `-p` default, also skips a flag-loaded plugin's mod (the `modules` key in `hooks/hooks.json`). The page names hooks only. Not documented.
- Whether `--restricted` keeps a `--plugin-dir` plugin and its hooks. It "loads only managed settings and `--settings`", and plugins are not mentioned. Not documented.
- `subagent_stats` in the `-p` JSON result. Not documented.
- Whether two `-p` runs in different temp folders share a prompt-cache prefix, and so how much cache sharing lowers later runs' cost. Not documented.
- Whether `claude plugin eval` reports cost per run in its JSON. The page lists suite-level `costUsd` and a per-case `COST` column only. Not documented.
- A sample size or test that Anthropic treats as enough for an agentic cost comparison. Its own tables pool 2 or 3 runs and say "within run-to-run noise" without naming the test. Not documented.
- A margin for "quality unaffected". No page gives one. The 5-point example in item 7 is judgment.
- How much the infrastructure-noise figures (Terminal-Bench, SWE-bench on Kubernetes) carry over to `claude -p` runs on one laptop. Not documented.
- How to calibrate an LLM judge against humans: how many human-graded samples, and what agreement counts as enough. The pages say to calibrate, not how much. Not documented.
