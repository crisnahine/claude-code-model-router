# Hook wiring and what each event costs

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.2.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Checked 2026-11-24 against Claude Code 2.1.331 (`claude --version`), with every page fetched the same day as `.md` from `code.claude.com/docs/en/`. The mod type files named in the brief are not in the worktree; they are at `plugins/model-router/.claude-plugin/types/` in the main checkout, headed "Written by Claude Code 2.1.330", and are cited as `[mod-types]`.

## What we built

- `hooks/hooks.json` loads the mod `./router.ts` under `modules` and registers ten command hooks, all in exec form: `"command": "sh"`, `"args": ["${CLAUDE_PLUGIN_ROOT}/scripts/model-router.sh", "<command>"]`.
- Events and commands: SessionStart (matcher `startup|resume|clear|compact|fork`) runs `session-start` (10 s) and `refresh-cache` (30 s, `async: true`); UserPromptSubmit runs `user-prompt` (5 s); PreToolUse `Agent|Task` runs `pre-agent`; PostToolUse `Agent|Task` runs `post-agent`; PostToolUse `Edit|Write|NotebookEdit` runs `post-edit`; PostToolUseFailure `Agent|Task` runs `agent-failed`; SubagentStop (no matcher) runs `agent-stopped`; Stop runs `stop`; PostModelSwitch (no matcher) runs `model-switch`. Every timed hook but `user-prompt` is 10 s. None sets `onFailure` or `if`.
- `scripts/model-router.sh` starts the first Python 3.9+ on PATH; `model-router.py` exits 87 on an old Python so the next one is tried. A hook that fails exits 1, never 2, and a missing Python exits 0. `cli.main` catches any handler error and exits 0.
- Handlers are in `scripts/modelrouter/hooks.py`: `session_start` (records options and model, prints the routing note), `user_prompt` (profiles the request, may add a note), `pre_agent` (stands down when `mod.active`, else `fallback.route` with `updatedInput`), `post_agent`, `agent_failed`, `agent_stopped` (bookkeeping, rarely a note), `post_edit` (`gates.note_edit`), `stop` (`gates.before_stop`, returns `decision: "block"`), `model_switch` (`session.record`).
- The mod `hooks/router.ts` runs the same launcher through `$.process.run(['sh', ...])` on `session.start` (`mod-start`), `agent.spawn` (`mod-spawn`), each main-loop `turn.start` (`mod-turn`) and every `turn.complete` that has usage, main loop and subagents (`mod-usage`).
- Measured cost per command hook: 54 to 60 ms warm p50, 179 to 188 ms cold, of which 43 ms is starting `sh` and Python (`docs/PERFORMANCE.md`). With the mod active, one Agent call costs `pre-agent` (stand-down only), `mod-spawn`, `post-agent`, `agent-stopped` and one `mod-usage` per subagent turn; each prompt costs `user-prompt` and `mod-turn`.

## What the sources say

Short names: `[hooks]` https://code.claude.com/docs/en/hooks, `[mods-ref]` https://code.claude.com/docs/en/plugins/mods/reference, `[mods-events]` https://code.claude.com/docs/en/plugins/mods/events, `[mods-admin]` https://code.claude.com/docs/en/plugins/mods/admin, `[mods-overview]` https://code.claude.com/docs/en/plugins/mods/overview, `[mods-api]` https://code.claude.com/docs/en/plugins/mods/api.

### What every hook pays

- Blocking: "By default, hooks block Claude's execution until they complete" `[hooks]` (Run hooks in the background). "When an event fires, its matching hooks run in parallel" `[hooks]` (Hook handler fields).
- The cheap filters. A matcher made of "Only letters, digits, `_`, `-`, spaces, `,`, and `|`" is an "Exact string, or list of exact strings"; any other character makes it a JavaScript regular expression `[hooks]` (Matcher patterns). `if` skips the spawn: "the `if` check would fail and `block-rm.sh` would never run, avoiding the process spawn overhead". It is "Only evaluated on tool events: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, and `PermissionDenied`. On other events, a hook with `if` set never runs" `[hooks]` (How a hook resolves, Common fields).
- `async: true`: "Async hooks can't block or control Claude's behavior"; output "is delivered on the next conversation turn"; "Claude Code doesn't enforce `timeout` on it"; with `-p`, "Claude Code kills any async hook still running at teardown" `[hooks]` (Run hooks in the background).
- Default timeouts: "600 for `command`, `http`, and `mcp_tool`"; "Claude Code lowers the `command`, `http`, and `mcp_tool` default to 30 on `UserPromptSubmit`, `PreModelSwitch`, and `PostModelSwitch`" `[hooks]` (Common fields).
- Exit codes: exit 2 is a blocking error; "any other code, or fails in some other way, such as not starting or printing invalid JSON. The action goes ahead", except for hooks with `onFailure: "block"` `[hooks]` (Exit code output). "a hook that can't start is a non-blocking error too" `[hooks]` (Other exit codes).
- Cache: "Claude Code never invalidates the cache for a plugin's skills, commands, agents, hooks, monitors, or themes. It appends their content after the existing conversation, so the next request pays for that content" https://code.claude.com/docs/en/prompt-caching (Plugin components that keep the cache). A hook that prints nothing adds no tokens.
- The debug log times each hook: "`Hooks: PostToolUse:Write [.claude/hooks/log-write.sh] finished with status 0 (31ms)`" `[hooks]` (Debug hooks). No millisecond cost is documented.

### Points that bear on single hooks

- **Stop's output form.** "Use `additionalContext` when the hook is working as designed and giving Claude guidance, such as 'run the test suite before finishing'. It keeps the conversation going through the same loop protections as `decision: "block"` ... but the transcript labels it `Stop hook feedback` and no hook error notification is shown" `[hooks]` (Stop decision control). `gates.before_stop` asks for a test run or a stronger check, which is that case, and `hooks.stop` returns `decision: "block"`.
- **Following the model.** "Only `SessionStart` hooks can receive a `model` field, and Claude Code doesn't always include it ... use a PostModelSwitch hook to follow the model as it changes during a session" `[hooks]` (Common input fields). The transcript "is written asynchronously and may lag the in-memory conversation" (same section). `session.model` reads the transcript first and the PostModelSwitch record second, so right after `/model`, before the next reply, it returns the old model.
- **`Task`.** "In version 2.1.63, the Task tool was renamed to Agent. Existing `Task(...)` references in settings and agent definitions still work as aliases" https://code.claude.com/docs/en/sub-agents. The PreToolUse section lists the tool as `Agent` `[hooks]` (PreToolUse). The plugin needs 2.1.329. That a `Task` hook matcher is still an alias is not documented.
- **The fallback's reach.** Mods "are on by default. In the terminal, use Claude Code v2.1.287 or later" `[mods-overview]` (Turn mods on or off), below the plugin's 2.1.329 floor. `allowManagedModsOnly` refuses a user's mod while "their hooks in settings files and in plugins' `hooks/hooks.json` ... aren't affected" `[mods-admin]` (Stop user-installed mods from loading). Under `allowManagedHooksOnly`, "hooks and mods from other installed plugins" are both blocked https://code.claude.com/docs/en/settings-reference (What runs under allowManagedHooksOnly). So `pre-agent` routes only where `allowManagedModsOnly` is set or the mod failed, and pays a Python start on every Agent call everywhere else.
- **Moving work into the mod.** Mods are "Functions in a plugin that Claude Code calls in its own process" `[mods-overview]` (Compare mods, settings hooks, skills, and MCP servers). The saving holds only for work done in JavaScript: `$.process.run` "takes an argument list and uses no shell" and starts a process like a command hook `[mods-api]` (Reach files, processes and the network). Where the guard loads, a user's mod hooks on `classic.<Event>` and `skill.prompt` "never" run `[mods-admin]` (Know which hooks of a user's mod don't run); `agent.spawn`, `turn.*` and `tool.call` are not on that list. A mod hook gets "10 seconds" of its own time per event, not counting time inside `next` or a mods API call `[mods-ref]` (Limits).

### The shell, and Windows

- **Exec form.** "A command hook runs as exec form when `args` is set ... Claude Code resolves `command` as an executable on `PATH` and spawns it directly with `args` as the argument vector. There is no shell". "Set `args` whenever the hook references a path placeholder" and "Prefer exec form for any hook that references a path placeholder" `[hooks]` (Exec form and shell form, Reference scripts by path). The `shell` field is "Ignored when `args` is set". Exec form came in 2.1.139: "Added hook `args: string[]` field (exec form) that spawns the command directly without a shell" https://code.claude.com/docs/en/changelog.
- **Shell form.** "`sh -c` on macOS and Linux, Git Bash on Windows, or PowerShell when Git Bash isn't installed" `[hooks]` (Exec form and shell form).
- **Windows, exec form.** "On Windows, exec form requires `command` to resolve to a real executable such as a `.exe`" `[hooks]` (Exec form and shell form). Placeholders "keep their native backslashes in an exec-form hook" https://code.claude.com/docs/en/plugins/components (Path variables and persistent data).
- **Windows without Git Bash.** "a shell-form `PreToolUse` or `PermissionRequest` command hook that fails with `onFailure` unset can instead block the tool call" `[hooks]` (Block the action when a hook fails). "Without Git Bash, any exit code other than 0 or 2 from that hook counts as a failure" `[hooks]` (Failed hooks on Windows without Git Bash). The listed fix for a hook where "The call should go ahead when the hook fails" is "add `"onFailure": "continue"`". Both passages name shell form; our hooks are exec form.
- **Finding Git Bash.** Git for Windows is "optional. It provides Git Bash, which the Bash tool and the Monitor tool need" https://code.claude.com/docs/en/setup (Install on native Windows). `CLAUDE_CODE_GIT_BASH_PATH` is for "when Git Bash is installed but not in your PATH" https://code.claude.com/docs/en/env-vars. No page says that exec form looks there, or that `sh` is on PATH on Windows.
- **Hook environment.** "Handlers run in the current directory with Claude Code's environment" `[hooks]` (Hook handler fields). "A hook process inherits the parent environment, apart from the `OTEL_*` exporter variables" `[hooks]` (Common input fields). Both forms "export them as the environment variables `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, and `CLAUDE_PLUGIN_DATA`" `[hooks]` (Exec form and shell form). On macOS and Linux, hooks "run in their own session without a controlling terminal" `[hooks]` (Hook input and output).
- **Windows paths in input.** "On Windows, the path arrives with backslash separators, even when your hook runs under Git Bash" `[hooks]` (PreToolUse input). And "On Windows without Git Bash, the tool is enabled automatically and Claude Code doesn't register the Bash tool at all" `[hooks]` (PowerShell), so a check that reads only Bash commands would miss PowerShell ones.

## Verdict

Partly right.

The shape follows the docs: exec form with `args` is what the docs say to use with `${CLAUDE_PLUGIN_ROOT}`, exact matchers keep `pre-agent`, `post-agent`, `agent-failed` and `post-edit` off every other tool call, the refresh is `async`, and no hook can block by mistake because every failure exits 0 or 1 and none sets `onFailure: "block"`. What isn't right: the Stop gate uses `decision: "block"` where the docs say to use `additionalContext` for this kind of guidance; the PostModelSwitch record that the docs name as the way to follow the model gets shadowed by a transcript read the docs say can lag; SubagentStop has no matcher, so it also spawns Python for Claude Code's internal agents; and on the default mod path, three hooks spawn Python for no result: `pre-agent` to stand down, `user-prompt` and `mod-turn` profiling the same prompt twice, and `mod-turn` with `main_effort` off. Windows is unverified: the docs require exec form's `command` to be a real executable on PATH and never say that `sh` is one.

## What to change

1. **Stop gate: answer with `additionalContext`, not `decision: "block"`.** Change `hooks.stop` in `scripts/modelrouter/hooks.py` to return `{"hookSpecificOutput": {"hookEventName": "Stop", "additionalContext": reason}}`, and update the tests that assert the `decision` shape. This removes nothing else: `stop_hook_active` and the 8-in-a-row cap still apply. Source: `[hooks]` (Stop decision control). Required by a source.
2. **Follow the model through PostModelSwitch first.** In `session.model` (`scripts/modelrouter/session.py`), read the record written by `session_start` and `model_switch` before the transcript, and fall back to `from_transcript` only when no record exists. This touches every caller (`hooks.user_prompt`, `gates.escalation`, `spawn.py`, `mod._facts`) through the one function. It deletes nothing. Sources: `[hooks]` (Common input fields: "use a PostModelSwitch hook to follow the model", and the transcript "may lag"); `[hooks]` (PostModelSwitch: fires on fallback, `opusplan` and resume). Required by a source.
3. **Give SubagentStop the matcher `.`** in `hooks/hooks.json`, a regex that never matches an empty `agent_type`, so prompt suggestions and `/btw` no longer start Python. Check first that `hooks.agent_stopped` never needs those events: they have no Agent call to close. It deletes one process per internal agent. Source: `[hooks]` (SubagentStop input). Judgment: the docs back what the matcher does; they don't say to filter these events.
4. **Drop `Task` from the three `Agent|Task` matchers** in `hooks/hooks.json`, and the "Its hooks match `Agent|Task`" line in `docs/CLAUDE_CODE_DOCS.md`. The tool has been `Agent` since 2.1.63 and the plugin needs 2.1.329. Source: https://code.claude.com/docs/en/sub-agents. Judgment: the docs don't say whether a `Task` matcher still matches.
5. **Skip `mod-turn` when it can't change anything.** In `hooks/router.ts` `turn.start`, call `ask(..., 'mod-turn', ...)` only when `options.main_effort` is on or the turn is a typed command (`command` set). With `main_effort` off, its default, `mod.turn` only raises a typed command's level and logs a ledger row. This deletes one blocking Python start per plain prompt. Keep the ledger row by logging the level from `user-prompt`, which already profiles the prompt. Source for the cost: `[mods-api]` (`$.process.run` starts a process); `[mods-events]` (`turn.start`). Judgment.
6. **Stop profiling the prompt twice on the mod path.** `hooks.user_prompt` and `mod.turn` both run `intake` and `profile_prompt` on the same text. Keep `user-prompt` as the one reader for plain prompts, since only a settings hook can add the hard-request note (a user mod's `prompt.attachment` hook doesn't run where the guard loads, `[mods-admin]`). `mod-turn` then reads the stored level from `request.load` and profiles only a typed command's rendered body. This touches `mod.turn` and `intake.from_turn` and deletes one regex pass per prompt. Judgment.
7. **Keep `pre-agent` and its matcher, and record its cost.** It is the only router under `allowManagedModsOnly` `[mods-admin]`, and no documented setting lets a mod switch off a plugin's settings hook. Add one line to `docs/ARCHITECTURE.md` replacing "It covers Claude Code versions without mods", which can't happen above the 2.1.329 floor (`[mods-overview]`: mods from 2.1.287), with the `allowManagedModsOnly` case. Judgment.
8. **Prove Windows before claiming it.** Run the plugin live on native Windows with and without Git for Windows, watching the debug log's `Hooks:` lines `[hooks]` (Debug hooks) for `failed to start`. If `sh` is not found, add `"onFailure": "continue"` to every entry (harmless where it already continues, and the docs' own fix for a call that must go ahead when a hook fails), and in `docs/GUIDE.md` and `README.md` name Git for Windows with its `bin` folder on PATH as a requirement, since `CLAUDE_CODE_GIT_BASH_PATH` is documented for Git Bash detection, not for exec form. The same check covers the mod's `$.process.run(['sh', ...])`. Do not switch to shell form: without Git Bash a failing shell-form PreToolUse hook "can instead block the tool call" `[hooks]`. Sources: `[hooks]` (Exec form and shell form; Failed hooks on Windows without Git Bash). Judgment on the test; the PATH rule is from a source.
9. **Small matcher cleanups.** Drop the SessionStart matcher, which lists every documented `source` and so equals "omitted": "fires on every occurrence of the event" `[hooks]` (Matcher patterns); a source added later is then not missed. Narrow `refresh-cache` to `startup`, since it refreshes at most once a day and an async SessionStart hook "runs every time the event fires" `[hooks]` (Limitations). Judgment.

Kept as is, with reasons: `post-agent`, `agent-failed` and `post-edit` stay synchronous settings hooks. A mod `tool.call` would see the same results (`[mods-events]`), but the work is in Python, so it would still start a process, and the settings hooks also serve the fallback path. `post-edit` stays synchronous because the Stop check reads what it writes, and the docs give no order between an async hook's write and a later Stop. `user-prompt` keeps its 5 s timeout, which is under the 30 s default, and a timeout there only drops the note: "The prompt still reaches Claude without that context" `[hooks]` (UserPromptSubmit).

## What the sources do not say

- Whether `sh` resolves on PATH for an exec-form hook, or for `$.process.run`, on native Windows, and whether Claude Code adds Git Bash's folder to a hook's PATH. Not documented.
- Whether the "Windows without Git Bash" blocking rule ever reaches an exec-form hook. The docs name shell form only.
- Whether a `Task` matcher still matches the Agent tool. Not documented.
- Whether `if: "Agent(...)"` can filter Agent hooks by subagent type or model. Not documented.
- The process-start cost of a command hook in milliseconds. Not documented; the repo's own measure is 54 to 60 ms warm.
- The order between an async hook's side effect and a later synchronous hook on another event, such as an async PostToolUse and the Stop that follows. Not documented.
- Whether `tool.call`'s result for an Agent call carries the same fields as PostToolUse's `tool_response`. The events page shows only `deny` and `isError`; the shape is in `[mod-types]`, which was not checked for this decision.
- Whether a SubagentStop or Stop hook's `additionalContext` costs fewer tokens than `decision: "block"`. Both continue the turn; the docs compare only the transcript label and the error notice.
- How the PostModelSwitch record behaves across `/clear`, where SessionStart's `model` "can be omitted". The docs don't say whether the session's model changes there.
