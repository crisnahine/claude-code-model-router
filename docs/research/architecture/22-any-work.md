# Routing work that is not software

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Researched 2026-11-24 against Claude Code 2.1.331 (`claude --version`), every page fetched the same day as `.md` or HTML. Code read in the `redo-fixes` worktree. This builds on `docs/research/` and on the sibling pages in this folder: `02-level-signal.md` (who names the level), `05-stop-gates.md` (the Stop gates) and `13-role-agents.md` (the role agents). Where one of those already settles a point, this page names its item and does not argue it again. This page asks one thing: does each part hold when the work is legal, finance, writing, research or operations, not code?

## What we built

- `scripts/modelrouter/profile.py` reads every brief with English regex. The four `SIGNALS` lists (risk, scope, load, ambiguity) are software words: auth, schema, migration, payments, race conditions, monorepo, qps. `_CHANGE_VERB`, `_DEFECT`, `_FIND_DEFECT` and `_HEAVY_NAME` / `_LIGHT_NAME` are code verbs and code role names.
- `_call_level()` sends any English brief with no signal and no change or reasoning verb to `lookup` (Haiku `medium`). `_request_level()` does the same for the person's request through `profile_prompt()`, called from `intake.from_prompt()` and `intake.from_turn()`.
- `gates.unverified_edit()` asks "Code changed since the last check" whenever a file outside `_NON_CODE` (`.md .mdx .txt .rst .adoc .csv .log`) was edited, and clears only when `gates.is_check()` matches `CHECK_COMMAND`: pytest, jest, tsc, ruff, `npm test`, `cargo test` and the like.
- `hooks.post_agent()` warns about a mid-run model swap only when the brief has the software "risk" signal.
- The role agents are scout, implementer, verifier, architect, reviewer, deep-solver and docs-researcher. Their prompts talk about `path:line`, diffs, tests and the codebase. `config/models.json` `use_for` and `crew.*.role`, shown to Claude by `report.policy()` in `/model-router:route`, are all code uses.
- `skills/route/SKILL.md` gives Claude a split table with rows "One file or function" and "Security, data, money, public API, migrations", and says "The router reads them from each brief's wording".
- `bench/tasks/` has 30 tasks, all software. The three `evals/` cases are routing checks.

## What the sources say

### Claude Code and its subagents for work that is not code

- The docs index calls Claude Code "Anthropic's agentic coding tool", and its default prompt is for code: "Claude works from Claude Code's standard system prompt, which is written for software engineering tasks." https://code.claude.com/docs/en/output-styles (Default)
- The same page says it can be set up for other work: "A custom style can also turn Claude into something other than a software engineer, such as a writing assistant or a data analyst", and `keep-coding-instructions` should be left out "if Claude won't be doing software engineering." Styles reach the main conversation and forks only: "Other subagents run their own system prompt, so styles don't change how they respond." https://code.claude.com/docs/en/output-styles
- "Claude Code works in any directory. Run it inside a notes vault, a documentation folder, or any collection of markdown files to search, edit, and reorganize content the same way you would code." https://code.claude.com/docs/en/common-workflows (Work in notes and non-code folders)
- The built-in general-purpose subagent is for "complex research, multi-step operations, code modifications", and Claude picks it "when the task requires both exploration and modification, complex reasoning to interpret results, or multiple dependent steps." The one non-code example definition is a data scientist that "explicitly sets `model: sonnet` for more capable analysis." https://code.claude.com/docs/en/sub-agents (Built-in subagents, Example subagents)
- Workflows are for "codebase audits, large migrations, and cross-checked research", and `/deep-research` "fetches and cross-checks the sources it finds, votes on each claim, and returns a cited report." https://code.claude.com/docs/en/workflows
- Anthropic's own account (September 2025): "Claude Code has become far more than a coding tool. At Anthropic, we've been using it for deep research, video creation, and note-taking, among countless other non-coding applications." It lists finance agents, customer support agents that "handle high ambiguity user requests", and deep research agents. https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk
- Anthropic's teams (July 2025): "Lawyers built phone tree systems. Marketers generated hundreds of ad variations in seconds. Data scientists created complex visualizations without knowing JavaScript." The Growth Marketing workflow used "two specialized sub-agents". https://www.anthropic.com/news/how-anthropic-teams-use-claude-code
- The platform names knowledge work as a main use of the default model: Opus 5.5 is "built for long-running agentic coding and knowledge work" https://platform.claude.com/docs/en/about-claude/models/choosing-a-model, and on knowledge work it "is much less likely to state an incorrect figure or cite the wrong source. It's better at financial modeling tasks ... and it catches details that are easy to miss in large inputs" https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5.
- "In Anthropic's testing, Opus 5.5 at `medium` matches or exceeds Opus 5 at `high` on coding and knowledge-work evaluations." https://code.claude.com/docs/en/model-config#choose-an-effort-level

### Choosing model and effort by difficulty, in general terms

- Two ways to start. Efficiency-first (Haiku) is "best for ... High-volume, straightforward tasks". Capability-first (Opus 5.5) is "best for: Complex reasoning tasks; Scientific or mathematical applications; Tasks requiring nuanced understanding; Applications where accuracy outweighs cost considerations; Advanced coding and high-autonomy agentic work". "Most workloads start with Claude Opus 5.5." https://platform.claude.com/docs/en/about-claude/models/choosing-a-model
- The matrix names non-code work on every row: Fable 5.2 for "multistep deep research, analysis carried through to a finished document, spreadsheet, or deck"; Sonnet 5.5 for "data analysis, content creation"; Haiku 5.5 for "high-volume intelligent processing ... subagent tasks". Same page, Model selection matrix.
- Legal: "Model accuracy is extremely important when summarizing legal documents. Claude Opus 5.5 is an excellent choice for use cases such as this where high accuracy is required. If the size and quantity of your documents are large such that costs start to become a concern, you can also try using a smaller model such as Claude Haiku 5.5." https://platform.claude.com/docs/en/about-claude/use-case-guides/legal-summarization
- Effort per model, in general terms. Haiku 5.5: "Use `high` for knowledge work, longer agent tasks, and strict instruction following." Sonnet 5.5: "Start with `high` unless your workload is agentic or latency-sensitive." General rule: "Adjust effort based on task complexity. Simple queries might warrant low effort, whereas agentic coding and complex reasoning benefit from high effort." https://platform.claude.com/docs/en/build-with-claude/effort (Recommended effort levels, Best practices). Fable 5.2: "`medium` suits interactive coding, chat, and everyday knowledge work. `high` suits hard coding, research, agentic work, and long unattended runs." https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-2#calibrate-effort
- Claude Code's own effort table is written in terms of the work, not the domain: `low` for "Quick exchanges where you review each result", `high` for "Work where verification matters or edge cases are likely", `max` for "Hard problems you want Claude to work through without you". https://code.claude.com/docs/en/model-config#choose-an-effort-level
- The model already scales its thinking to the request: effort "lets the model decide whether and how much to think on each step based on task complexity" https://code.claude.com/docs/en/model-config#adjust-effort-level, and thinking "improves performance on complex tasks such as math, coding, analysis, and long-running agentic work" https://platform.claude.com/docs/en/build-with-claude/thinking.
- Measured outside code. DRACO (100 research tasks in 10 domains): "Claude Opus 5.5 scored 13.3 points lower at `low` than at `medium`." DeepResearch Bench II: "Claude Opus 5.5 scored 2.4 points above Claude Sonnet 5.5 for 1.5 times the cost per task. Claude Fable 5.2 cost 4.3 times as much as Claude Sonnet 5.5 for no measurable gain in score." On WideSearch, BrowseComp, DeepWideSearch and GDPval ("Knowledge-work deliverables graded against task rubrics") with Fable 5, "`low` effort gave up 1 to 3 points for a third to a half off the cost per task, `medium` matched the default's accuracy". https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#tune-effort and the Benchmarks referenced section.
- "Price the tail of your workload, not the median: compare models on the hardest tenth of your tasks." Same page, #compare-models-on-cost-per-task.
- Biology work changes models on its own: "For substantive biology work on a Fable model or Opus 5.5, the first flagged request that switches models moves the session to Opus 5. ... On Opus 5 and Sonnet 5.5, those refusals start with the first flagged request." https://code.claude.com/docs/en/model-config (Security research and biology workloads)
- On rules versus the model deciding: "Agents struggle to judge appropriate effort for different tasks, so we embedded scaling rules in the prompts." The rules are by kind of query, not by domain: "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents ... and complex research might use more than 10 subagents." https://www.anthropic.com/engineering/multi-agent-research-system (June 2025, earlier models)
- A classifier is a documented pattern only when it is accurate: "Routing works well for complex tasks where there are distinct categories that are better handled separately, and where classification can be handled accurately", and "consider adding complexity only when it demonstrably improves outcomes." https://www.anthropic.com/research/building-effective-agents

### What makes a task hard

No page gives one list. Read together, the pages name these properties, and none of them is a domain:

| Property | What the sources say | Source |
| :- | :- | :- |
| Stakes: how much a mistake costs | "Applications where accuracy outweighs cost considerations"; "where high accuracy is required" (legal); "Work where verification matters" | choosing-a-model; legal-summarization; model-config effort table |
| Checkability: whether a check can catch a mistake | "High-volume work with outputs you can check: Try Claude Haiku 5.5 first"; re-running failures needs "a failure signal ... a checker that passes bad work lets those failures through" | optimizing-for-cost-and-intelligence #start-here, #re-run-failures-at-higher-effort |
| Open-endedness: no known path or one right answer | Research is "open-ended problems where it's very difficult to predict the required steps in advance"; "Tasks requiring nuanced understanding"; research quality "can only be judged relative to the task" | multi-agent-research-system; choosing-a-model; demystifying-evals (below) |
| Length and size: how long the run, how big the input | `xhigh` for "Long-running agentic and coding tasks (over 30 minutes)"; Haiku `high` for "longer agent tasks"; Opus 5.5 "catches details that are easy to miss in large inputs" | effort; prompting-claude-opus-5-5 |
| Who reviews: a person at each step, or nobody | `low` for "Quick exchanges where you review each result"; `max` for "Hard problems you want Claude to work through without you" | model-config effort table |
| Overlookable detail | Raise effort "when getting it right depends on cases that are quick to overlook" | https://code.claude.com/docs/en/best-practices#change-the-model-and-effort |
| Volume | Efficiency-first is for "High-volume, straightforward tasks" | choosing-a-model |

"Software" is not on the list. The software words in `profile.py` stand in for stakes (auth, payments, migrations) and open-endedness (root cause, design), which is why they miss the same properties in a contract or a forecast.

### Checking work that is not code

- Claude Code's own rule is about any check Claude can read: "The check can be almost anything, as long as Claude can read the result", listing "A script that diffs output against a fixture" and "A browser screenshot next to the mockup". The in-prompt version "works for any task, today, with no setup." https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run
- `/goal` is the documented domain-neutral check: "After each turn, a model checks whether the condition holds." It "is a wrapper around a session-scoped prompt-based Stop hook" that sends the condition and the conversation to the small fast model. https://code.claude.com/docs/en/goal
- Prompt hooks are for judgment: "For decisions that require judgment rather than deterministic rules, use `type: "prompt"` hooks." https://code.claude.com/docs/en/hooks-guide (Prompt-based hooks)
- Anthropic's hosted agents check a non-code deliverable with a rubric in a fresh context: "the harness automatically provisions a grader to evaluate the artifact against a rubric. The grader uses a separate context window to avoid being influenced by the main agent's implementation choices." The example rubric is for a DCF model in an `.xlsx` file, and the advice is "explicit, gradeable criteria, such as 'The CSV contains a price column with numeric values' rather than 'The data looks good.'" https://platform.claude.com/docs/en/managed-agents/define-outcomes
- Three ways to check, from the Agent SDK post: "Defining rules" ("When generating an email, you may want Claude to check that the email address is valid"), "Visual feedback", and "LLM as a judge" ("Our email agent might have a separate subagent judge the tone of its drafts"). https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk
- For research: "Groundedness checks verify that claims are supported by retrieved sources, coverage checks define key facts a good answer must include, and source quality checks confirm the consulted sources are authoritative ... For tasks with objectively correct answers ('What was Company X's Q3 revenue?'), exact match works." https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents (January 2026). Anthropic's research system graded on "factual accuracy ... citation accuracy ... completeness ... source quality ... and tool efficiency." https://www.anthropic.com/engineering/multi-agent-research-system
- Grading order: "Code-based grading: Fastest and most reliable ... but also lacks nuance for more complex judgments"; "LLM-based grading: Fast and flexible, scalable and suitable for complex judgment. Test to ensure reliability first, then scale." https://platform.claude.com/docs/en/test-and-evaluate/develop-tests (Grade your evaluations)
- A fresh reviewer is worth it where delegation alone is not: "A fresh reviewer does help, because it hasn't seen your reasoning." https://code.claude.com/docs/en/best-practices (What you can stop doing)
- The sources disagree on how far a model judge can be trusted. The Agent SDK post: "This is generally not a very robust method, and can have heavy latency tradeoffs". The research post: "LLM-as-judge evaluation scales when done well", and a single judge call "was the most consistent and aligned with human judgements." The platform: "Test to ensure reliability first." Both posts are from 2025, on earlier models.
- Plugin evals take model-judged graders: "plus three short judge calls per `llm` or `baseline` grader per run", with a rubric "written as concrete PASS and FAIL conditions." https://code.claude.com/docs/en/plugin-evals

### A signal that a session is not software

The one field found: a mod's `prompt.compose` input has `outputStyle: { name, isKeepingCodingInstructions } | null`, "What the person chose in place of the default way of answering, and whether it keeps the coding instructions; null for the default style." Source: the generated type file `plugins/model-router/.claude-plugin/types/claude-code/index.d.ts` (written by 2.1.330, in the main checkout; the worktree has no copy). `prompt.compose` is on the list of hooks the built-in guard stops on managed machines https://code.claude.com/docs/en/plugins/mods/admin, and the default style is used for every kind of work, so the field can show "not software" but never "software". No hook input names the kind of work.

Of the 21 non-software briefs, 12 read as `lookup` on the call path and 13 on the request path; 18 hit none of the four signal lists. The two right lookups were the population fact and five email subject lines. The level follows whether the brief happens to use a software word, not how hard the work is.

The gate, read-only: `gates.is_check()` returns false for `diff out.csv expected.csv` (the docs' own "script that diffs output against a fixture"), `python3 scripts/reconcile.py --check ledger.csv`, `vale docs/`, `markdownlint memo.md` and `languagetool report.txt`, and true for `npm test`, `pytest -q` and `make check`. An edit to `contract.docx`, `model.xlsx`, `deck.pptx`, `report.pdf` or `campaign.html` counts as a code change and draws a request for tests and lint. An edit to `memo.md`, `chapter3.txt` or `data.csv` is never checked.

## Verdict

Wrong.

The docs and Anthropic's own posts say Claude Code and its subagents are used for research, writing, legal, finance and operations work, and they define difficulty by stakes, checkability, open-endedness, length and who reviews, never by domain (choosing-a-model, the legal guide, the effort pages, the model-config effort table). The plugin reads difficulty from software words, so 12 of 21 non-software briefs fell to Haiku, including a legal summary the legal guide puts on Opus 5.5, and the one documented condition for a classifier, that it "can be handled accurately" (building-effective-agents), is not met for this work. The verify gate asks for tests on a Word or Excel edit, never sees a non-code check, and skips prose deliverables entirely, where the docs say a check "can be almost anything, as long as Claude can read the result" and Anthropic's own harness checks a DCF spreadsheet with a rubric grader in a fresh context. What carries over is the ladder of model and effort pairs, the cap, and the principle of asking for a check; the parts that choose a level and recognise a check need to be domain neutral.

## What to change

None of these is required word for word by a source; each is judgment backed by the sources named. Items 1 and 2 build on `02-level-signal.md`, items 3 and 4 on `05-stop-gates.md`, item 5 on `13-role-agents.md`.

1. **any-work-1. Key the caller's level table on task properties, not domains** (small). Where `02-level-signal.md` item level-signal-1 rewrites the session text in `hooks.session_start()` and `skills/route/SKILL.md` to have Claude name `model` and `effort`, write the table by the properties above, with examples from several kinds of work: a fact or file a reader checks at a glance (Haiku `medium`; reading and summing up documents at Haiku `high`); a draft or change to a clear spec that someone reviews (Sonnet `high`); work where a mistake is costly or hard to spot, such as money, legal, health, security, data or anything published or sent, or that needs a judgment between options (Opus `high`); long unattended runs or large inputs with stakes (Opus `xhigh`); open-ended research with no known approach (Fable `high`, or Opus first). Deletes the Ambiguity / Scope / Risk table in `skills/route/SKILL.md` "How to split the work" and its line "The router reads them from each brief's wording". Backed by https://platform.claude.com/docs/en/about-claude/models/choosing-a-model, https://platform.claude.com/docs/en/build-with-claude/effort (Haiku `high` for knowledge work, Sonnet `high` by default), https://code.claude.com/docs/en/model-config#choose-an-effort-level, https://platform.claude.com/docs/en/about-claude/use-case-guides/legal-summarization, https://www.anthropic.com/engineering/multi-agent-research-system (scaling rules). The written instruction itself is required for the effort column, since the Agent tool's `effort` text says to set it only when instructions ask (02); the rows are judgment.

2. **any-work-2. Do not add legal, finance or writing words to the lists; stop scoring briefs** (large). Adding a word list per domain repeats the miss for the next domain and still fails "classification can be handled accurately". Take the deletion in level-signal-2 (`SIGNALS`, `_SYSTEMS`, `_DECISION`, the change, defect, lookup and frontier patterns, `_not_english`, `Reading`, `read()`, `_call_level()`, `profile_call()`) and apply it to the request path too: `_request_level()`, `profile_prompt()`, `asks_for_work()`, the level in `intake.from_prompt()` / `intake.from_turn()` / `intake.profile_skill()` and `request.start()` / `request.raise_to()`. In `hooks.post_agent()`, warn on every mid-run model swap, not only on a software "risk" brief: a biology brief on Opus 5.5 moves to Opus 5 on its first flagged request. Until the deletion lands, an unread brief should stay on Claude Code's own order (the parent's model) rather than fall to `lookup`. Backed by https://www.anthropic.com/research/building-effective-agents, https://code.claude.com/docs/en/model-config (Security research and biology workloads), https://platform.claude.com/docs/en/about-claude/models/choosing-a-model ("Most workloads start with Claude Opus 5.5"). Judgment.

3. **any-work-3. Word the verify ask for any deliverable** (small). In `gates.unverified_edit()`, replace "Code changed since the last check" and the tests-lint-types list with an ask by kind of work: code gets `model-router:verifier` and the project's tests, lint or build; figures, spreadsheets and data get a recompute or a script that diffs against known values; documents and analysis get a fresh subagent that reviews the file against the request's criteria, written as a few pass or fail points; a draft the person will read next, or work still in progress, ends with one line. Same change to the `verify_gate` text in `plugin.json`, `docs/GUIDE.md` ("Asks for a test run ... when code changed") and `README.md`. Nothing new runs: no prompt hook is added, so no tokens are spent on turns with no edits. This is `05-stop-gates.md` item 5 with the non-code checks spelled out. Backed by https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run, https://platform.claude.com/docs/en/managed-agents/define-outcomes, https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents. Judgment.

4. **any-work-4. Count edits to every deliverable, not only to non-prose files** (small). Delete `gates._NON_CODE` and its test in `gates.note_edit()`, so a legal memo in `.md` or reconciled figures in `.csv` are checked like a `.docx` or a `.py`. The cost is one short extra turn after a batch of edits that pass silently today, such as a README tweak in a code repo, which item 3's one-line exit covers. Rename the "Code ... changed" docstring in `request.note_edit()`. Smaller option: keep `_NON_CODE` and add `.docx .xlsx .pptx .pdf .odt .ods .odp`, which makes the gate honestly code-only and leaves other work to the in-prompt check the docs say "works for any task". Backed by https://code.claude.com/docs/en/common-workflows (notes and non-code folders) and https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run. Judgment.

5. **any-work-5. Let the reviewer check any finished work; label the code-only roles** (small). Judgment.

6. **any-work-6. Reword the code-only text Claude reads** (small). `hooks.user_prompt()`: "can't be settled from the code in a few reads" becomes "from what is in front of you". `config/models.json` `use_for`: add the matrix's non-code uses (Haiku: search, extraction, classification and summaries where a mistake is cheap to spot; Sonnet: data analysis, content creation, documents to a clear brief; Opus: legal and financial analysis, documents built from large inputs, judgment calls; Fable: multistep deep research and analysis carried to a finished document). `crew.*.role` follows item 5. Backed by https://platform.claude.com/docs/en/about-claude/models/choosing-a-model (matrix) and https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5 (knowledge work). Judgment.

7. **any-work-7. Measure on work that is not code before claiming every subagent** (medium). Add non-software tasks to `bench/tasks/` with a known answer or a rubric: a contract clause summary, a DCF or runway forecast from given figures, a ledger reconciliation with known mismatches, a cited research survey, a customer reply. Grade them with rubric graders like the define-outcomes example, and add `evals/` cases with `llm` graders whose prompts are not code. Until those run, `README.md` and `docs/BENCHMARKS.md` say the benchmark covers software tasks only. Extends level-signal-6. Backed by https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence ("measure on your own workload", "Price the tail"), https://code.claude.com/docs/en/plugin-evals, https://platform.claude.com/docs/en/test-and-evaluate/develop-tests. Judgment.

Not recommended: reading `outputStyle` on `prompt.compose` to switch the router into a non-software mode. It is type-file only, the guard stops it on managed machines, and the default style covers every kind of work, so items 1 to 6, which hold for code and non-code alike, make it unneeded.

## What the sources do not say
