# Redo escalation: the signal, the climb and the window

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Checked 2026-11-24 against Claude Code 2.1.331 (`claude --version`), with each page fetched the same day as `.md`. Builds on `docs/research/caller-levels-and-redo.md` (Q3, "Which design the docs support") and `docs/research/quality-first-routing.md` (Q4, rec 9) and does not repeat their field tables.

## What we built

- Two redo triggers, both read in `spawn.facts`. The unmarked one: `calls.identify` hashes `subagent_type` plus the exact `prompt`; `calls.finished_run` returns a finished run under that key from the same request (same `prompt_id`, else within `REDO_WINDOW`, 30 minutes).
- The marked one: `calls.marked_redo` matches a `description` that starts with "Redo:". `calls.task` keys the work by agent plus the description with the mark stripped, and `calls.last_run` finds the latest finished run of that task in the session within `REDO_WINDOW`, across requests. With no run on record, `spawn._unmarked_run` uses what the call would get without its mark.
- A run counts as finished in `calls.returned` (foreground result that is not a swap and not `calls.cut_off`) or `calls._stopped` (a background launch whose agent stopped with an answer). Only `Route.redoable` runs are kept.
- The climb is in `router.decide`: the level goes one step up (`Level.up`), on the shipped ladder lookup Haiku `medium`, standard Sonnet `medium`, complex Opus `high`, hardest Opus `xhigh`, frontier Fable `high` (`config/models.json`). `router._above_earlier` asks for one effort step above the earlier run when the model is not stronger. If a router-chosen redo would run on the same model and effort again, it moves to the next stronger usable model.
- A caller-named `model` turns the redo off (`redo = ... and not tool_input.get("model")`); a caller-named `effort` keeps its effort but the model still climbs.
- Workflow stages never redo (`spawn.facts`: `marked = not workflow and ...`, `earlier = None if workflow`). The mod passes resumed runs through untouched (`hooks/router.ts`, `if (e.fork || e.resume) return next(e)`).
- Claude is taught the mark in three places: `hooks.session_start`, `fallback._note` and `skills/route/SKILL.md`.
- In the 12-run pilot under `bench/results/pilot/redo-mark/`, every `routed` row has `escalated_from: null`. No redo fired there, but every run passed first time, so this says nothing either way.

## What the sources say

The policy we model on, and its condition

- "When a task's outcome is checkable, the cheapest policy on the effort curve is not a fixed setting: run every task at a low setting and re-run only the failures at a higher one." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#re-run-failures-at-higher-effort
- "Two conditions apply. First, you need a failure signal (here, the benchmark's own tests); a checker that passes bad work lets those failures through. Second, every first-pass failure takes two runs' worth of wall-clock time, so the saving is paid for in latency on the failures." (same URL)
- "Use this policy for the saving, not the lift. Most of the small lift is the second attempt: re-running the failures of one `high` run at `high` scores about the same, for more money." (same URL). The references give the numbers: "`high` re-run on its own failures, 96.9% for $0.31 USD; everything at `high`, 94.8% to 95.8% for $0.29 USD", against "`low` first, then `high` on its failures, solved 96.4% to 97.5% ... for about $0.17 USD" (same page, "Escalation figures" in the benchmark notes).
- The measured policy changes effort only, on one model: "Anthropic computed this policy task by task from the Claude Opus 5.5 effort runs on the SWE-bench Pro subset" (same URL).
- The start-here row: "You can check outputs (tests, a verifier) | Run at `low` effort and re-run failures at `high`". https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#start-here

Do we have a failure signal from a check?

- No check result reaches the redo code. The gates record only that a check ran: `gates.note_check` writes `verified_at`, and `gates.note_agent_checks` looks for a check command in the subagent's transcript. Pass or fail is never read. Both triggers are the caller's own judgment, one by its mark and one by issuing the same prompt again.
- What the docs say about judgment without a check: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually *is* done, 'looks done' is all it has to go on." And: "ask Claude for *evidence*: the command it ran and its output ... 'All tests pass' on its own tells you very little." https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run
- The same section describes the check loop that repeats one check on purpose: "`run the auth tests after, and keep going until they pass`" (same URL). A verifier or test brief sent again with the same prompt after a fix is a new check of changed code, not a redo of a weak result. The unmarked trigger counts it as a redo.
- The earlier research already found the unmarked hash cannot catch a real redo, since Claude rewrites the brief and no input field marks a retry (caller-levels-and-redo.md, Q3, "What this means for the router").
- `CLAUDE_CODE_DOCS.md` (Effort table) says: "Its redo is modeled on this: a call re-issued after its result came back runs one level higher." Its own "Where it goes past the docs" section concedes that "its trigger is the same call issued again, not a check". The two lines don't agree.

Effort first or model first

- Reference page: "Quality isn't good enough | If you lowered effort, restore it; otherwise try the next tier up at its default effort." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#start-here. This rule is for tuning a workload, not for one redo.
- Sonnet's own default is above our standard rung: "At `medium`, Claude Sonnet 5.5 scored about 7 points lower than at its default, `high`, on the SWE-bench Pro subset for about 59% of the cost per task." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#tune-effort
- The Claude Code blog post linked from the model configuration page (https://code.claude.com/docs/en/model-config): "If Claude has all the pertinent context, clearly tried, and still got it wrong, that's a signal to pick a more capable model. If Claude got it wrong by skipping a file, not running the tests, or bailing on a refactor partway through, pick a higher effort level." The same post adds that the effort advice "is most relevant if you selected an effort level below the model's default." https://claude.com/blog/claude-model-and-effort-level-in-claude-code
- Anthropic's developer blog (not linked from the reference pages fetched here) gives an order: "When a model isn't good enough for a task, take these steps in order: Check that the model can verify its own work ... Raise effort one level. Move to the next model up, starting at a lower effort level than you used on the smaller one." It also says "Past `high`, one more effort level can cost as much as a bigger model ... If you're past `high`, test the next model up at a lower effort instead," and "moving to a higher effort level won't give a model knowledge or skill it doesn't have." https://claude.dev/blog/which-claude-model-should-you-build-with/
- Mapped onto our ladder: lookup to standard changes only the model (Haiku `medium` to Sonnet `medium`), with no effort step first. Standard to complex goes to Opus at `high`, which is higher effort than Sonnet's `medium`, the reverse of "starting at a lower effort level". Complex to hardest raises effort past `high` on Opus. Hardest to frontier moves to Fable at a lower effort (`high` after `xhigh`), which matches.
- On the repeat rule: the docs say a second attempt at the same setting gets most of the lift (first group above). So no source says a run that would repeat its model and effort is worthless. Moving it to the next model is a quality-first choice the sources neither back nor forbid.

Is the description field a sound place for a marker?

- The Agent tool's schema: "A short (3-5 word) description of the task" (generated type file `plugins/model-router/.claude-plugin/types/claude-code-tools/index.d.ts`, `Agent.description`, in the main checkout; the worktree has no `types/` folder). The hooks reference: "`description` | string | `"Find API endpoints"` | Short description of the task". https://code.claude.com/docs/en/hooks (Agent table under PreToolUse input)
- It is display text: "the delegation appears as a tool call row showing the subagent's name followed by a short task description, such as `code-improver(Suggest code improvements)`". https://code.claude.com/docs/en/sub-agents (Quickstart). The mod type file says of `description`: "A rewrite is what the task shows as" (`claude-code/index.d.ts`, `AgentSpawnInput.description`).
- It is in the schema, so it survives the input check that drops unknown keys (caller-levels-and-redo.md, Q3, citing the 2.1.300 changelog entry). No page gives it any meaning beyond display, and no page forbids text in it.
- The documented fields for "run this harder" are `model` and `effort`. On effort, the tool text says: "Set this ONLY when the user, or instructions such as CLAUDE.md or a skill, explicitly ask that this agent or delegated work run at a specific effort level" (type file, `Agent.effort`). The docs: "When you ask Claude to run a non-fork subagent at a specific effort level, it can also pass an `effort` parameter for that invocation." https://code.claude.com/docs/en/sub-agents#choose-an-effort-level. A skill such as `route` counts as such an instruction.
- Today a marked redo that carries the caller's `effort` still climbs a model in `router.decide`, so the caller asks for more effort and gets a different model as well.

Resuming a subagent instead of starting a new one

- "Each subagent invocation creates a new instance rather than continuing an earlier one. To continue an existing subagent's work, ask Claude to resume it." "Resumed subagents retain their full conversation history, including all previous tool calls, results, and reasoning." "Claude uses the `SendMessage` tool with the agent's ID or name as the `to` field to resume it." https://code.claude.com/docs/en/sub-agents#resume-subagents
- What a resume keeps: "If Claude passed an alias, the subagent keeps that alias when it resumes or receives a follow-up message." https://code.claude.com/docs/en/sub-agents#choose-a-model. The effort parameter "stays in effect when the subagent is resumed" https://code.claude.com/docs/en/sub-agents#choose-an-effort-level. For a mod: "If you pass a changed event to `next` for a resumed run, such as a different `model`, Claude Code ignores the change." https://code.claude.com/docs/en/plugins/mods/reference#subagents. The changelog for 2.1.327: "Changed subagents launched without a model to stay on the model they started on when resumed". https://code.claude.com/docs/en/changelog. So a resume can't move to a stronger model, and the mod's pass-through for `e.resume` is right.
- What the docs use resume for: "When a subagent stops at its `maxTurns` limit, Claude Code marks the returned output as partial, and Claude can resume the subagent to continue its work" (sub-agents#resume-subagents), and after an API error, "Once the underlying API error clears, ask Claude to retry the task or resume the subagent." https://code.claude.com/docs/en/errors (Agent terminated early due to an API error)
- Cost: "when Claude resumes a subagent, the resumed run's first request can read the cache the original run warmed." https://code.claude.com/docs/en/prompt-caching (Subagents and the cache)
- Against resuming after a wrong result: "If you've corrected the same thing twice and it's still wrong, a third correction mostly adds to a conversation that already contains two failed attempts for Claude to keep re-reading. `/clear` plus one new prompt that folds in what you learned works better almost every time." https://code.claude.com/docs/en/best-practices#steer-the-session. That page is about the main session; that it holds for a subagent is our inference.
- The skill and session text never mention resume, and no code reads a partial `maxTurns` result.

The cut-off case

- `calls.cut_off` treats a result whose whole text matches `API Error: \d{3}` as a retry, not a finished run. The errors page says that shape is gone: "This message requires Claude Code v2.1.199 or later; before then the API error text was returned to Claude as if it were the subagent's result." On current builds a terminal error is "`Agent terminated early due to an API error: <error detail>`", and "When a rate limit, overload, or server error interrupts a foreground subagent that already produced text output, Claude receives that partial output marked as incomplete instead of this error." https://code.claude.com/docs/en/errors (Agent terminated early due to an API error)
- Even in the old shape the regex misses two listed messages, "`API Error: Repeated 529 Overloaded errors`" and "`API Error: No response from API`" (same page, index table). The plugin requires 2.1.329, so on supported builds `calls.cut_off` can't match the documented shapes. A partial result "marked as incomplete" counts as finished, so a later redo climbs from it.

Workflow stages

- A workflow's script owns repeats and quality passes: "Moving the plan into code also lets a workflow apply a repeatable quality pattern ... it can have independent agents adversarially review each other's findings." Its cache needs siblings that match: "Two agents that run with the same model, effort level, agent type, tools, output schema, and working directory build the same tools-and-system-prompt prefix." https://code.claude.com/docs/en/workflows (and "Prompt caching in a fan-out"). Never redoing a stage fits both.

## Verdict

Partly right. The shape is the documented one: a first pass, a climb on a weak result, workflow stages and resumes left alone. But the trigger is the caller's judgment. The docs' condition is "a failure signal (here, the benchmark's own tests)", and no check's pass or fail reaches the redo code. The unmarked exact-prompt trigger also fires on a deliberate re-run of the same check. The climb jumps model before effort and raises effort on the new model, while the reference page says to restore effort first and the Claude Code blog says to pick by failure kind, which only the caller can see. The description marker is in-schema and visible, so it is usable, but its meaning beyond display is not documented, and resume, the documented way to continue a run that was cut short, is never offered.

## What to change

1. **Stop claiming the measured policy for a trigger that isn't a check, and tie the mark to evidence.** Rewrite the Effort row in `docs/CLAUDE_CODE_DOCS.md` ("Its redo is modeled on this") so it says the trigger is the caller's judgment. Change the redo line in `skills/route/SKILL.md`, `hooks.session_start` and `fallback._note` to: mark "Redo:" when a check failed or the report shows no check output. Deletes the claim, no code. Source: https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#re-run-failures-at-higher-effort ("you need a failure signal") and https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run. The claim fix is required by the source; the wording of the instruction is judgment.
2. **Drop the unmarked exact-prompt redo.** Delete `calls.finished_run`, the `earlier = ... calls.finished_run(...)` line in `spawn.facts` (a marked redo then always reads `calls.last_run`), and the call-key copy written by `calls._keep_done` and `calls._stopped` (keep the `task:` copy). Rewrite `evals/route-redo-escalates` to use the mark, and the tests that call `finished_run`. Keep `calls._same_request`, which `calls.routed` still uses for votes. Why: it counts a deliberate re-run of the same check as a redo, which raises the level and casts an "up" vote in `learn.spawned`, and earlier research found it misses real redos. Source: https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run (the "keep going until they pass" loop). Judgment.
3. **Let the caller pick the lever, and honor it.** In `skills/route/SKILL.md` and the session text, say: a redo of work that skipped files, tests or steps passes `effort` one level up; a redo of work that tried and was wrong passes nothing and climbs. In `router.decide`, when a marked redo carries the caller's own `effort`, keep the model of the run it redoes and skip the level climb. Deletes the case where a caller's `effort` is overridden by a model jump. Source: https://claude.com/blog/claude-model-and-effort-level-in-claude-code (failure kind picks the lever) and https://code.claude.com/docs/en/sub-agents#choose-an-effort-level, plus the `Agent.effort` text in the generated type file (a skill may ask for `effort`). Judgment.
4. **When the caller names no lever, climb effort before model.** In `router.decide`'s redo block and `router._above_earlier`: below `high`, a redo first raises effort one step on the same model (Sonnet `medium` to Sonnet `high`, Haiku `medium` to Haiku `high`). At `high` or above, it moves to the next model at an effort no higher than the earlier run's. The first-pass ladder in `config/models.json` stays as it is. Deletes the Sonnet `medium` to Opus `high` jump on a redo. Source: https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence#start-here ("If you lowered effort, restore it; otherwise try the next tier up at its default effort") and https://claude.dev/blog/which-claude-model-should-you-build-with/ (the ordered steps). Judgment, since the reference rule is written for tuning a workload, not for one redo. Under quality first, weigh it against a third run when effort alone was not enough.
5. **Resume a run that was cut short; redo only a finished weak one.** Add to `skills/route/SKILL.md`: a result marked partial at `maxTurns`, or one cut off by an API error, is continued with `SendMessage` to its agent ID, not sent again with "Redo:". No router code changes, since a resume keeps its model and the mod already passes `e.resume` through. Source: https://code.claude.com/docs/en/sub-agents#resume-subagents, https://code.claude.com/docs/en/errors (Agent terminated early due to an API error), https://code.claude.com/docs/en/prompt-caching (resumed subagents read their own cache). Judgment.
6. **Remove the cut-off detector that can't match on supported builds.** Delete `calls.cut_off`, `calls.API_ERROR`, `calls.CUT_OFF`, `Outcome.cut_off`, its use in `hooks.post_agent` and `calls.returned`, and `test_a_run_an_api_error_cut_off_is_retried_at_its_level`. A terminal error arrives as "Agent terminated early due to an API error" on the failure path (`calls._failed`). Source: https://code.claude.com/docs/en/errors (the shape changed in 2.1.199; the plugin needs 2.1.329). Judgment: the source shows the code can't fire; deleting it, and giving up on detecting the "marked as incomplete" partial, is our call.

## What the sources do not say

- Whether the calling model's own judgment of a result counts as a failure signal for the re-run policy. The docs measured a benchmark's tests only.
- How to link a failing check (a Bash `Exit code N`, a verifier's report) to the subagent run whose work caused it: not documented (also caller-levels-and-redo.md Q3).
- Any re-run measurement that changes model, or that starts at `medium` or above on Sonnet or Haiku. The only measured policy is Opus 5.5, `low` or `medium` then `high`.
- Whether a one-step climb (`low` to `medium`, `medium` to `high`) keeps the measured result. The measured policy jumps to `high`.
- What text marks a foreground partial result "as incomplete", and whether hooks can read that mark: not documented.
- Whether a "Redo:" prefix in `description` does anything besides display, or how reliably Claude follows a session-start instruction to write it. No live run here shows it firing.
- Whether a mod's `turn.step` can raise the effort of a resumed run, and what that does to its cache.
- How long after a result a redo still means that result was weak. `REDO_WINDOW` (30 minutes) is our own number; no source gives one.
- Whether the "third correction" advice in best-practices, written for the main session, applies to resuming a subagent.
