# main_effort: setting the main conversation's effort per turn

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.2.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Researched 2026-11-24 on Claude Code 2.1.331 (`claude --version`). Every page below was fetched the same day as `.md`. "Type file" means the mod API types Claude Code wrote for the plugin, `plugins/model-router/.claude-plugin/types/claude-code/index.d.ts`, headed "Written by Claude Code 2.1.330" (the copy in the main checkout; the worktree has no `types/` folder).

## What we built

- `plugin.json` option `main_effort`, boolean, default `false`. `settings.py` reads it into `Settings.main_effort`.
- `hooks/router.ts` `turn.start`: for a main-loop turn it reads `$.session.model()`, calls `hasFirstPartyCredential` (`$.session.authorize()`, a null outside the desktop app counts as "no first-party credential") and the settings layers, then asks the Python runtime `mod-turn` for an effort and keeps it in `turnEffort` by `turnId`.
- `mod.turn` profiles the request text with `intake.from_turn` (the same English-regex profile as for briefs: `profile_prompt`, or `profile_skill` for a typed command), then `mod.turn_effort` decides from `TurnFacts`: nothing unless routing is `auto`, the option is on, `CLAUDE_CODE_EFFORT_LEVEL` is unset, the credential check did not answer `false`, and `_cache_drop` finds no reason the cache would drop.
- `_cache_drop` says no on Foundry, Bedrock, Vertex, Mantle, any `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`, any `DISABLE_PROMPT_CACHING*`, and a session model outside `main.effort_keeps_cache` in `config/models.json` (Fable 5.1 and later, Opus 5.5, Sonnet 5.5, Haiku 5.5). An unknown model version passes.
- The effort comes from `main.effort` (`complex` to `high`, `hardest` and `frontier` to `xhigh`), held to `maxEffortLevel` by `router.capped`.
- `router.ts` `turn.step` applies it to every main-loop request of that turn whose current effort ranks below it. It never lowers. `ledger.turn` writes a `turn` row; no code reads those rows back.
- HIPAA and a Claude apps gateway reached from Claude Desktop are not detected; the option text tells the person to leave it off there.

## What the sources say

Cache effects of changing effort mid-session, per model and provider

- "On most models, changing the effort level mid-session means the next request reads the entire conversation history with no cache hits. While the cache is still warm, Claude Code asks you to confirm the change first." And: "With an API key or a Claude subscription, changing effort keeps the cache on Fable 5.1 and later, Opus 5.5, Sonnet 5.5, and Haiku 5.5. Claude Code applies the new level without asking. On Amazon Bedrock, Google Cloud's Agent Platform, or a Claude apps gateway, or when you set `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS` or your organization has a HIPAA configuration, it works as on most models." https://code.claude.com/docs/en/prompt-caching.md (section "Changing effort level")
- Same page, top tip: "Pick your model and effort level at the top of a session, then save `/compact` for natural breaks between tasks. The fewer changes you make mid-task, the higher your cache hit rate." https://code.claude.com/docs/en/prompt-caching.md
- The API mechanism: "A per-message effort change keeps the prompt cache. A new top-level value on the next request can invalidate all or part of the prompt cache." https://platform.claude.com/docs/en/build-with-claude/effort.md (section "Change effort mid-conversation")
- Per-message effort is a beta (`mid-conversation-output-config-2026-07-01`). Its supported models include `claude-opus-5`, and its platforms include Bedrock, Claude Platform on AWS, both Google Cloud offerings and Foundry. https://platform.claude.com/docs/en/build-with-claude/effort-per-message.md (front matter and "Availability"). Claude Code's own list is narrower (Opus 5 and the cloud platforms are not on it), and Claude Code's list is the one that governs what Claude Code sends.
- What Claude Code sends: "Effort set per turn: On Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.2, and Fable 5.1, a beta header pairs with `output_config.effort` on `role: "system"` entries." The fix for a gateway that strips it: "Forward both, or have developers set `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` to stop the field and the empty entries." https://code.claude.com/docs/en/llm-gateway-protocol.md (section "Beta header and body field pairs")
- What a top-level change costs, measured: "Changing effort at the top level cost 20 to 40 times what changing it in a message cost." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md (section "What breaks the cache")
- A quality note on the cheaper form: "On Claude Fable 5.1, a top-level change also steers the model less reliably. The model's earlier replies were written at the previous level, and the model tends to stay consistent with them." https://platform.claude.com/docs/en/build-with-claude/effort-per-message.md (section "Per-message or top-level effort")

HIPAA and gateway caveats

- HIPAA applies only to "A Claude Enterprise account, connecting directly to the Claude API". Bedrock, Agent Platform, Foundry, Claude Platform on AWS, a Claude apps gateway, an LLM gateway or any custom `ANTHROPIC_BASE_URL` are "No". https://code.claude.com/docs/en/hipaa-setup.md (section "Check how developers sign in and connect")
- The documented ways to see it are for people: the startup notice, a "`HIPAA configured` tag" in the footer, and `HIPAA` on the `Organization configuration` line of `/status`. The page names no env var, setting or hook field, and says nothing about effort or the cache. https://code.claude.com/docs/en/hipaa-setup.md (section "Confirm the configuration on a computer")
- Behind a gateway the type file gives a usable signal: `$.session.authorize()` is "Null with no first-party credential (a 3P provider, a gateway, no login)". Type file, `session.authorize`.
- Claude Platform on AWS authenticates "with AWS credentials or a workspace API key". https://code.claude.com/docs/en/claude-platform-on-aws.md. Whether an effort change keeps the cache there, or on Claude Models on Google Cloud (Anthropic managed), is on no Claude Code page.

What a mod may set per request

- `turn.step`: "One request is about to go to the model". A hook can return "`yield* next(e)`, or `next({ ...e, model })`, `next({ ...e, effort })`". https://code.claude.com/docs/en/plugins/mods/reference.md (section "Turns")
- Type file, `TurnStepInput.effort`: "the level its loop, `CLAUDE_CODE_EFFORT_LEVEL`, turn or session set, or the model's default. Absent on a model without effort, or if that variable is `unset` or `auto` with no `maxEffortLevel` cap. A rewrite lasts one step. On a model that takes effort per message, a level on tool results alone is not sent if another is in force, and one on a step with input stays for later tool steps whose `effort` is a level." The step result's `effort` is "the step's `effort` as the hooks left it, unless a limit lowered it or another level was in force".
- So "turn" is one of the sources the step's current effort can come from. A skill's level is such a turn level: "`effort`: Effort level for the rest of the current turn. Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable." https://code.claude.com/docs/en/skills.md (frontmatter table). And: "While either one applies, the skill or subagent runs at its level, whatever level you launch with, save, or pick." https://code.claude.com/docs/en/model-config.md (section "Set the effort level")
- The person's own pick ranks high in Claude Code's order: "2. A level you pick in the session, such as with `/effort`". https://code.claude.com/docs/en/model-config.md (section "Adjust effort level"). Nothing in the mods docs says a mod's raise should yield to it or not.

Does Claude Code already adapt effort?

- Per step, inside the model: "Effort levels control adaptive reasoning, which lets the model decide whether and how much to think on each step based on task complexity." https://code.claude.com/docs/en/model-config.md (section "Adjust effort level"). And "Adaptive reasoning makes thinking optional on each step, so Claude can respond faster to routine prompts and reserve deeper thinking for steps that benefit from it." Same page, "Adaptive reasoning and fixed thinking budgets".
- Per turn, by the person: "Include `ultrathink` anywhere in your prompt to request deeper reasoning on that turn without changing your session effort setting." "To raise that turn to `xhigh` effort as well, type the word in" the terminal, VS Code or the desktop Code tab. "Where the word can't raise a turn, such as on Amazon Bedrock, Google Cloud's Agent Platform, or a Claude apps gateway, set the effort level instead." https://code.claude.com/docs/en/model-config.md (section "Use ultrathink for one-off deep reasoning"). Changelog 2.1.311: "Changed `ultrathink` in the interactive terminal to run its turn at xhigh effort on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 through Anthropic's API; typed while Claude is working, it raises the rest of that turn". https://code.claude.com/docs/en/changelog.md
- Per turn, by a skill author: the skill `effort` row quoted above.
- Per session: `/effort` with `s` applies "the level to this session only"; `max` applies to the current session only. https://code.claude.com/docs/en/model-config.md
- Ultracode does not change effort: it plans workflows "at whichever effort level the session runs at", and "Turning ultracode on or off with `/effort` or the `ultracode` setting leaves the effort level unchanged." Only `--effort ultracode` also sets `xhigh`. https://code.claude.com/docs/en/model-config.md (section "Adjust effort level")
- For a mod's own side jobs, Claude Code added "an `effort` option to a mod's `$.model.fork`" (changelog 2.1.318). That is a fork's effort, not the main loop's. https://code.claude.com/docs/en/changelog.md

Is there evidence that per-turn effort helps?

- General advice in favor: "Consider dynamic effort: Adjust effort based on task complexity. Simple queries might warrant low effort, whereas agentic coding and complex reasoning benefit from high effort. See the next item before varying it within one conversation." The next item: "Hold top-level effort constant within cached conversations". https://platform.claude.com/docs/en/build-with-claude/effort.md (section "Best practices")
- What effort buys, whole task at one level: Opus 5.5 on the SWE-bench Pro subset, `medium` 92.8% at $0.21 a task, `high` 95.3% at $0.29, `xhigh` 96.7% at $0.74 (a single run). https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md (section "Tune effort")
- The measured policy that beats a fixed level is outcome-driven, not predicted: "run every task at a low setting and re-run only the failures at a higher one", with the condition "you need a failure signal". Same page, "Re-run failures at higher effort".
- How Anthropic says to measure effort: "Sweep two or three effort levels on a sample of your own traffic, each in a separate session". Same page, "Tune effort".
- A side effect of the `xhigh` raise on a Sonnet session: "At `xhigh` and `max`, Claude Sonnet 5.5 can start its own rounds of review after it finishes a task, which takes more time and tokens." Same page, "Tune effort".
- Claude Code's table puts `high` at "Work where verification matters or edge cases are likely, such as fixing a bug in an existing codebase". https://code.claude.com/docs/en/model-config.md (section "Choose an effort level")
- No page measures effort picked per turn from the request's text, by a classifier or by any rule. The plugin's own benchmark ran every Model Router configuration with `main_effort` off (`bench/configs.json`), so there is no local measurement either.

## Verdict

Partly right. The cache guard follows the sources closely: it raises only on the models and credentials the prompt-caching page names, stays off on Bedrock, Agent Platform, Mantle, Foundry, the betas switch and any custom base URL, and uses the type file's `authorize()` null to catch a gateway. It is also off by default, which matches "The fewer changes you make mid-task, the higher your cache hit rate". What is not supported is the trigger and the override: the level is an English-regex guess at the request, no source shows that a predicted per-turn raise helps, Claude Code already gives the person a per-turn raise (`ultrathink`) and the model already varies its thinking per step. The raise also goes over a lower level that a skill set for the turn or the person picked with `/effort`, which the skills and model-config pages treat as the level that applies.

## What the sources do not say

- Not documented: any measurement of effort chosen per turn from the request text, by a classifier, or by any rule. The platform's "Consider dynamic effort" is advice without a number.
- Not documented: whether a mod's `turn.step` effort goes out as a per-message entry (cache kept) or a top-level value. The prompt-caching page speaks of the person's change and the gateway page of "effort set per turn"; the type file implies per-message on models that take it, without saying so for mods in plain words.
- Not documented: whether a `turn.step` effort outranks `CLAUDE_CODE_EFFORT_LEVEL`. The type file lists that variable as one source of the step's current level only. The plugin stands down when it is set, so this is not tested.
- Not documented: whether the turn after a raised turn goes back to the session level with the cache intact. The per-message page says a level "stays in effect until a later message changes it"; how Claude Code writes that later message after a mod's one-turn raise is not stated.
- Not documented: any way for a plugin to detect a HIPAA configuration. The signals are for people only.
- Not documented: whether an effort change keeps the cache behind an LLM gateway that forwards both halves of the per-turn pair, on Claude Platform on AWS, or on Claude Models on Google Cloud (Anthropic managed). The platform lists per-message effort on those providers; Claude Code's page names neither outcome.
- Not documented: whether Claude Code will add Opus 5 to its keep-cache list. The platform supports per-message effort on `claude-opus-5`; Claude Code does not list it, and the plugin follows Claude Code.
- Not documented: how Claude Desktop's sign-in looks to `$.session.authorize()` behind a Claude apps gateway; the null-in-desktop rule in `router.ts` rests on the binary, as model-control.md records.
- Not documented: whether `ultrathink` and a mod's raise to `xhigh` on the same turn interact in any way beyond both naming `xhigh`.
