# Security and privacy model

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Researched 2026-11-24 against Claude Code 2.1.331 (`claude --version`), with every page fetched the same day as `.md`. Code read in `.claude/worktrees/redo-fixes`. Three claims below were checked by calling the plugin's own functions from scratch scripts against an empty data folder (not the test suite); the scripts are `p1.py`, `p3.py`, `p4.py` and `p5.py` in a scratch folder outside the repository.

## What we built

- Settings-hook fallback (`hooks.pre_agent`, only while `mod.active` is false): `fallback.route` returns the whole Agent input with `model` and `effort` changed (`fallback._rewritten_input`) and no `permissionDecision`. `fallback._guard` passes a refused rewrite through unchanged, or returns the one `deny`, when the call's model is above `max_tier`.
- Mod (`hooks/router.ts`): `agent.spawn` sets `model`, `turn.step` sets effort. Each event goes to the Python runtime through `$.process.run` with an argv list (`ask`). It sends six settings keys (`KEYS`, `effortCaps`) and checks only whether `$.session.authorize()` is null (`hasFirstPartyCredential`).
- What it reads: briefs and prompts (`profile.profile_call`, `intake.from_prompt`, `intake.from_turn`), the user's and the project's `model-router.json` (`config.load`, `config._clean`, `config._raises_only`), settings and managed files (`allowlist.read`, `allowlist._policy`, `allowlist._repository_root`), agent frontmatter (`agents.find`), skill and command files (`intake._read_skill`) and transcript tails (`session.transcript_tail`, `gates.checks_ran_since`).
- What it writes, all under `store.data_dir()`: the ledger (`ledger.spawn` keeps 120 characters of each `description`), per-session state (`routes`, `done`, `launched`, `prompts`), and two global files: `learned.json` (`learn._tally`) and the health table in `state.json` (`health.failed`, `health.ran`).
- Network: only `upstream.http_get`, five fixed HTTPS URLs. The API key goes only to the Models API (`upstream.api_models`), with redirects refused (`RefuseRedirect`).

## What the sources say

### What a hook may decide

- `allow` skips the prompt, `deny` stops the call, and `updatedInput` "Replaces the entire input object, so include unchanged fields alongside modified ones." "With no `permissionDecision`, auto mode can deny the changed call." Precedence is "`deny` > `defer` > `ask` > `allow`." https://code.claude.com/docs/en/hooks (PreToolUse decision control)
- In auto mode: "The server reviewed the input Claude wrote, not the input your hook returned." If Claude repeats the changed input, "Any `updatedInput` it returns is dropped, so what runs is what the server reviewed." Only "Bash, PowerShell, Monitor, Edit, Write, and NotebookEdit calls" are exempt. Agent is not. https://code.claude.com/docs/en/hooks (PreToolUse `updatedInput` in auto mode)
- Auto mode drops "`Agent` allow rules", and "Before a subagent starts, the delegated task description is evaluated, so a dangerous-looking task is blocked at spawn time." So a hook `allow` on Agent would skip a review Claude Code keeps on purpose. https://code.claude.com/docs/en/permission-modes (How auto mode evaluates actions; How auto mode handles subagents)
- "If a hook or mod changes an action's input after the server's review, Claude Code can deny the action with no verdict." https://code.claude.com/docs/en/permission-modes (Server-side classifier review)
- "PreToolUse hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns." https://code.claude.com/docs/en/permissions (Precedence among rules, hooks, and mods)

### Plugins, mods and managed policy

- "A Claude Code plugin you install can execute arbitrary code on your machine with your user privileges." Permission rules and the sandbox "cover the tool calls Claude makes, not the code a plugin runs by itself", and hooks and mod processes run "outside the sandbox." https://code.claude.com/docs/en/plugins/security
- A mod can "Read your secrets: environment variables and settings files, including an API key you keep in either" and "Act without asking you: approve a tool call before you're asked." https://code.claude.com/docs/en/plugins/mods/overview (What a mod can reach)
- The built-in guard loads with managed settings, `managed-mcp.json`, or a Team or Enterprise `/login`. It then "blocks a user's mod from rewriting: ... The answer a mod gets when it reads settings". A user mod's hook on `skill.prompt` "never runs". Network policy for mods does not cover "a program the mod starts with `$.process.run`, which reaches the network with the user's own access." https://code.claude.com/docs/en/plugins/mods/admin
- `allowManagedModsOnly` refuses user mods while "their hooks in settings files and in plugins' `hooks/hooks.json`" keep running (https://code.claude.com/docs/en/plugins/mods/admin). Under `allowManagedHooksOnly`, "Your user, project, local, and plugin hooks are blocked" (https://code.claude.com/docs/en/hooks, Hook locations). So the fallback path is what runs in the first case, and nothing runs in the second.
- `$.session.authorize()` "Holds the session's Anthropic credential on the host and answers an opaque handle and its kind; the secret never reaches the plugin." `$.process.run`'s `env` is "Variables set over the host process's own environment." The type file opens with "EARLY ACCESS: this surface may change between releases without notice." Source: the generated type file `plugins/model-router/.claude-plugin/types/claude-code/index.d.ts`, "Written by Claude Code 2.1.330" (in the main checkout; the worktree has no copy).
- The manifest `network` field: "The field doesn't allow or block any host." https://code.claude.com/docs/en/plugins/manifest-reference
- Caps that hold: when managed settings define `availableModels`, "that list alone applies ... entries in user, project, or local settings cannot extend it". Otherwise the lists "are concatenated and deduplicated" (https://code.claude.com/docs/en/model-config, Merge behavior). For `maxEffortLevel`: "When several scopes set a cap, the lowest applies, so a cap set in one scope can't be raised from another" (https://code.claude.com/docs/en/settings-reference).
- Managed sources: under the default `"first-wins"`, Claude Code "uses the highest-ranked source that delivers at least one policy key and ignores the rest rather than merging them". Remote and MDM policy rank above the files. "On WSL, `/etc/claude-code` is user-writable as well." https://code.claude.com/docs/en/managed-settings (How Claude Code combines managed sources)

### Repository content and trust

- When you trusted only a parent folder, or in `claude -p`, "Hooks in settings files, the `env` block and helper commands such as `apiKeyHelper`" are "Used". For `-p` on a repository you didn't write: "Pass `--setting-sources user`", start with `--bare`, or pass `--settings '{"disableAllHooks": true}'`. https://code.claude.com/docs/en/permissions (What runs before you trust a folder)
- "Project and local settings can't set variables that a checked-out repository shouldn't control". The list includes `CLAUDE_CONFIG_DIR`, `HOME` and `TMPDIR`, but not `PATH` or `PYTHONPATH`. "Variables Claude Code classifies as safe, such as model selection ... at startup from every settings file." https://code.claude.com/docs/en/settings-reference (`env`)
- "A hook process inherits the parent environment, apart from the `OTEL_*` exporter variables". https://code.claude.com/docs/en/hooks (Common input fields)
- "Interactive session: Claude Code holds back hooks from every settings file ... until you accept the workspace trust dialog". For mods: "no mod loads until they answer the trust prompt." https://code.claude.com/docs/en/hooks (Workspace trust), https://code.claude.com/docs/en/plugins/mods/admin

### Prompt injection

- "Prompt injection is a technique where an attacker attempts to override or manipulate an AI assistant's instructions by inserting malicious text." Best practice: "Avoid piping untrusted content directly to Claude". https://code.claude.com/docs/en/security
- Auto mode: "Tool results are stripped from those requests, so hostile content in a file or web page can't manipulate the classifier directly", and "A separate server-side probe scans incoming tool results". https://code.claude.com/docs/en/permission-modes
- For hook text: "Write the text as factual statements rather than imperative system instructions." Hook security: "Validate and sanitize inputs: never trust input data blindly" and "Use absolute paths". https://code.claude.com/docs/en/hooks (Add context for Claude; Security best practices)
- `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` strips credentials from hooks: "This reduces what a prompt injection attack can read." It removes `ANTHROPIC_API_KEY` and `CLAUDE_CONFIG_DIR`. https://code.claude.com/docs/en/env-vars
- On escalation: "you need a failure signal"; "a checker that passes bad work lets those failures through." https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence (Re-run failures at higher effort)

### Data a plugin stores, and the network

- `${CLAUDE_PLUGIN_DATA}` is "`~/.claude/plugins/data/<id>/`, created on first reference and kept across plugin updates", meant for "Installed dependencies such as `node_modules`, generated code, and caches". It is deleted "when you uninstall the plugin from the last place it's installed." A `sensitive` option "stores the value in secure storage instead of `settings.json`". https://code.claude.com/docs/en/plugins/manifest-reference
- Claude Code's own data: "These files are plaintext." "Transcripts and history are not encrypted at rest. OS file permissions are the only protection." The sweep deletes files "older than `cleanupPeriodDays` ... The default is 30 days". Neither the sweep list nor `claude purge` names `plugins/data/<id>/`. https://code.claude.com/docs/en/claude-directory (Application data; Clear local data)
- Under HIPAA, `cleanupPeriodDays` is "The number of days your records policy lets a computer keep session data", and Claude Code removes "`ANTHROPIC_API_KEY` ... from the environment of the shell commands, hooks, and MCP servers it starts." https://code.claude.com/docs/en/hipaa-setup
- Claude Code stores keys on Linux "in a file with mode `0600`". https://code.claude.com/docs/en/security (Additional safeguards)
- `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` disables "auto-updates, telemetry, error reporting, ... release notes" and similar traffic. https://code.claude.com/docs/en/env-vars
- The Models API example sends `-H "Authorization: Bearer $ANTHROPIC_API_KEY"`. https://platform.claude.com/docs/en/api/models/list
- A subagent's `tools`: "Inherits every tool available to subagents if omitted." https://code.claude.com/docs/en/sub-agents (Supported frontmatter fields)

### Paths that let a repository or a brief steer spend or quality

1. A project's `routing_mode: "off"` (or `"advise"`) lifts the user's `max_tier`. `router.decide` returns before `Registry.clamp` whenever `settings.mode != "auto"`, and `settings.resolve` takes the weakest of the user's option and the files. Probe `p1.py`, with `max_tier: haiku`: an Agent call naming `opus` was kept on `opus` ("routing is off"). Without the project file it was lowered to `haiku`.
2. One repository can route a model around for every project. An agent pinned to an exact ID that fails (`model: claude-opus-9-9` plus an `effort` field, so the router keeps it) strikes the family, not the ID. That happens in `calls._failed`, then `health.failed("opus")`. The health table is global, in `state.json`. Probe `p3.py`: after two failures `opus` left the usable list, and the hook told Claude to re-issue on `sonnet`. Probe `p4.py` on that state: a `complex` call with no cap went to `fable` at `high`, about twice Opus's list price (prices in model-control.md Q5). With `max_tier: opus` it went to `sonnet` at `xhigh`, a weaker model. On a clean state the same call went to `opus` at `high`. A project `env` that remaps `ANTHROPIC_DEFAULT_OPUS_MODEL` can do the same through `health.ran`'s substitution count, which checks no remap.
3. Six marked redos in one session raise a level for every later session and project. A file Claude reads can ask it to put "Redo:" in front of descriptions, and the session-start note teaches that mark. `learn._tally` then bumps the level in the global `learned.json`. Probe `p5.py`: after six fix-then-"Redo:" pairs, `complex` had a learned raise of 1, and a new session's `complex` call went to `fable`. Only relax votes or `/model-router:models reset` undo it.
4. Text from a cloned repository reaches Claude through the plugin's own output. `config._clean` keeps any string as a model or agent key. `report.policy` prints model names in the output of `/model-router:route`, which Claude may invoke on its own. `report.models` prints the held entries, which include those keys.
5. Bounded paths: brief wording raises or lowers a call's level, and a mark with no run on record still climbs one level (`spawn._unmarked_run`). Both stay under `max_tier`. A project's `.claude/settings.json` `availableModels`, `maxEffortLevel` and model-selection `env` steer Claude Code itself, and the router follows them (`allowlist.from_layers`, `router._pinned`). Only managed `availableModels` and `maxEffortLevel` are caps a repository can't lift.

## Verdict

Partly right. The core matches the docs: never returning `allow` keeps the spawn review auto mode protects by dropping `Agent` allow rules, the rewrite copies every field because `updatedInput` "Replaces the entire input object", the cap `deny` is a documented decision, and the key goes only to Anthropic in the documented header. Three verified paths break the page's own trust story: a project file lifts the user's cap, and one repository's failures or marked redos change routing in every project through global state. SECURITY.md also misstates which agents reach the web, what is read and stored, and how the data folder is protected, and its stored text follows none of the retention rules Claude Code gives its own plaintext data.

## What the sources do not say

- Whether a hook or mod can read the folder's workspace-trust state, so a plugin could ignore `.claude/model-router.json` until trust: not documented.
- Whether plugin `hooks/hooks.json` hooks wait for workspace trust like settings-file hooks. The docs name settings-file hooks and mods, not plugin hook files: not documented.
- Whether a mod's `agent.spawn` model change counts as changing "an action's input" for the auto-mode no-verdict denial: not documented. Earlier research recorded a live run with no denial.
- Whether `PATH` set in a project `env` block reaches plugin hooks before trust, that is, which class "safe" covers: not documented.
- Where `CLAUDE_PLUGIN_DATA` points when `CLAUDE_CONFIG_DIR` is set: not documented. The scrub removes `CLAUDE_CONFIG_DIR` from hooks, so `store.claude_home()` then reads `~/.claude/model-router.json`, not the user's own file. Whether the plugin can find the real folder from `CLAUDE_PLUGIN_DATA` depends on that path.
- Any rule on how long a plugin may keep data, or whether `cleanupPeriodDays`, `claude purge`, `CLAUDE_CODE_SKIP_PROMPT_HISTORY` or HIPAA retention should cover `plugins/data/<id>/`: not documented.
- What file modes Claude Code gives `~/.claude/plugins/data/<id>/`: not documented (0755 here, inside a 0700 `~/.claude`).
- Whether plugins are expected to honor `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`: not documented.
- Whether the framing `intake.is_delivered` matches ("Another Claude session sent a message:", `<teammate-message`) is stable. The hook input has no origin field, and only the mods' `origin.kind` is documented.
- Whether the classifier's review of "the delegated task description" reads the Agent `description` field, so a "Redo:" mark could change its verdict: not documented.
