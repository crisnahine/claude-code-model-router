# The model registry: aliases, newest IDs, allowlists and effort caps

2026-11-25: this note checks Model Router as it stood on 2026-11-24, before the 0.3.0 redesign. "What we built" describes that code, and some of what it names is gone or works differently now. What the code does now is in the [architecture review](../architecture-review.md).

Checked 2026-11-24 against Claude Code 2.1.331, the docs pages named below fetched as `.md` the same day, and the mod type files written by 2.1.330 (`plugins/model-router/.claude-plugin/types/claude-code/index.d.ts` in the main checkout; the worktree has no `types/` folder).

## What we built

- `plugins/model-router/config/models.json` holds four families (`haiku`, `sonnet`, `opus`, `fable`) with plugin-made `strength`, `speed` and `cost` ranks, the alias `best -> opus`, a `newest` table (`claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`), an `older_aliases` table naming per provider the families whose alias lags, per-ID list prices, levels and the crew.
- `registry.Registry.family` maps an alias or full ID to a family by exact name, then by substring. `available` filters families by the `max_tier` cap, `allowlist.Allowlist.permitted` and the health table; `clamp` and `select` pick from what is left.
- `registry.Registry.newest_id` returns the family's newest full ID when `settings._provider` (from the `CLAUDE_CODE_USE_<NAME>` switches) names a provider listed in `older_aliases` for that family, no `ANTHROPIC_DEFAULT_<FAMILY>_MODEL` is set, `Allowlist.permits_id` passes (which refuses whenever any `modelOverrides` is set) and the ID has no health strike. `mod._newest` sends that ID from `agent.spawn`; a refused ID gets one strike and the alias runs after (`health.failed(newest=True)`, `hooks.agent_failed`).
- `allowlist.py` (339 lines) rebuilds Claude Code's list rules: `from_layers` (managed list alone, else user, project, local and flag concatenated; `deniedModels` and `availableModelsMatch` from policy only), `_effective` (a specific entry turns off its family wildcard), `_blocked_family`, `permits_id` and `effort_cap` (lowest `maxEffortLevel` across sources, a source's `modelSettings` entry replacing its top-level one). The layers come from the mod's `$.settings.read` per source (`hooks/router.ts` `modelSettings`, stored by `allowlist.remember`), and otherwise from the files: `file_layers`, `_policy` (managed file plus drop-ins), `_local`, `_repository_root`. The managed files always apply as a stricter floor.
- `router.capped`, `spawn.py`, `mod.py` and `report.py` hold every effort the router sets to `effort_cap`.

## What the sources say

Aliases and what they resolve to

- "The `opus`, `sonnet`, and `haiku` aliases resolve to the newest version on the Anthropic API and to an earlier version on some other providers". The table: Anthropic API Opus 5.5 / Sonnet 5.5 / Haiku 5.5; Claude Platform on AWS Opus 5.5 / Sonnet 4.6 / Haiku 4.5; Claude Models on Google Cloud (Anthropic managed) Opus 5.5 / Sonnet 5.5 / Haiku 4.5; Amazon Bedrock and Agent Platform Opus 5.5 / Sonnet 4.5 / Haiku 4.5; Microsoft Foundry Opus 4.6 / Sonnet 4.5 / Haiku 4.5. https://code.claude.com/docs/en/model-config.md, "Model aliases". `older_aliases` matches this table row for row.
- "`best`: Uses the same model as `opus`" (from v2.1.321, "Version history"), and "the `fable` alias resolves to Fable 5 in Claude apps gateway sessions and to Fable 5.2 everywhere else". Same page. The registry's `best -> opus` and the absence of a `fable` entry in `newest` both fit.
- "Where `opus` or `sonnet` resolves to an older model, newer models are available by selecting the full model name explicitly or setting `ANTHROPIC_DEFAULT_OPUS_MODEL` or `ANTHROPIC_DEFAULT_SONNET_MODEL`." Same page, "Model aliases".
- The same pages warn that the newest model may not be turned on for the account: the alias default "can lag the newest Anthropic release, and the model it points to may not yet be enabled in a user's account", and "pin model versions before rolling out to users". https://code.claude.com/docs/en/model-config.md, "Pin models for third-party deployments". Bedrock adds that "the startup model checks still cover the session's default models", so a subagent's own full ID is not covered by that check. https://code.claude.com/docs/en/amazon-bedrock.md
- On Bedrock, "Anthropic-format model IDs resolve through the same mapping as the `/model` picker". https://code.claude.com/docs/en/amazon-bedrock.md. On Foundry, "Claude Code reads the model from the deployment name ... Name each deployment with its model ID ... or map the model to your deployment name with `modelOverrides`". https://code.claude.com/docs/en/microsoft-foundry.md. The platform table: "Foundry deployments default to the Claude API model ID ... the deployment name is what you send", and Claude Platform on AWS and Claude Models on Google Cloud (Anthropic managed) use the Claude API IDs. https://platform.claude.com/docs/en/about-claude/models/overview.md
- A family alias does not always run the alias's version: "if your main conversation runs on `claude-opus-4-7`, a subagent with `model: opus` runs on that version too. To run another version, set a full model ID in the `model` field." https://code.claude.com/docs/en/sub-agents.md, "Which version a model alias selects".

Is a full ID from a plugin supported

- The Agent tool parameter does not take one: "On an Agent tool call, the parameter takes a model alias, not a full model ID or `inherit`." https://code.claude.com/docs/en/sub-agents.md, "Choose a model". The fallback hook keeps to aliases, which fits.
- The mod can: "If an installed mod sets a model in its `agent.spawn` hook, Claude Code uses that model in place of the per-invocation parameter." Same section. The type files say the spawn `model` is "an alias (`haiku`) or a full id", and an `AgentSpawnResult.model` "from a hook an alias (`haiku`) or an id" (type file, `AgentSpawnInput`, `AgentSpawnResult`). So sending `claude-sonnet-5-5` from `agent.spawn` is supported.

availableModels, deniedModels, availableModelsMatch, modelOverrides

- The allowlist "applies everywhere a user can specify a model", including "the `model` field in subagent frontmatter, the Agent tool's `model` parameter, agent team teammate models, `CLAUDE_CODE_SUBAGENT_MODEL`". https://code.claude.com/docs/en/model-config.md, "Restrict model selection". Workflow agents follow "the same substitution rules as subagents". https://code.claude.com/docs/en/workflows.md
- Claude Code itself does not fail a blocked subagent: it "runs the subagent or teammate on a fallback model rather than failing the request". The order: "For a blocked family alias, the newest permitted version in that family, on providers that support this substitution", then `CLAUDE_CODE_SUBAGENT_MODEL`, then "The main conversation's model, or the spawning subagent's model". https://code.claude.com/docs/en/sub-agents.md, "When an allowlist blocks a subagent model".
- That substitution is provider-bound: "On the Anthropic API and Claude Platform on AWS, a model family alias ... resolves to its usual model when the allowlist permits that model. When the allowlist blocks that model, Claude Code substitutes the newest version of the family that the allowlist permits." For teammates: "On providers with provider-specific model IDs, where the substitution doesn't operate, a blocked alias falls back like any other blocked value". https://code.claude.com/docs/en/model-config.md and https://code.claude.com/docs/en/agent-teams.md, "Specify teammates and models".
- Merge: a managed list "alone applies"; "Otherwise, lists from user, project, and local settings are concatenated and deduplicated". "an entry naming a specific model in a family ... disables that family's wildcard entry." https://code.claude.com/docs/en/model-config.md, "Merge behavior". Within the file source, "`managed-settings.json` first, then every `*.json` file in the directory", and lists "combine, with duplicates removed". https://code.claude.com/docs/en/managed-settings.md
- `deniedModels` and `availableModelsMatch`: "Claude Code reads both keys from managed settings only." A deny entry "such as `claude-opus-5-5` blocks that version in every spelling", one "with no minor version, such as `claude-opus-5`, also blocks later minor versions", and `best`, `opusplan`, `default` entries are ignored. https://code.claude.com/docs/en/model-config.md, "Block specific models or versions"; https://code.claude.com/docs/en/settings-reference.md, `deniedModels`. `allowlist.py` follows each of these.
- Provider IDs: "Provider-specific prefixes such as `us.anthropic.` are not stripped", and on Agent Platform an entry needs the `@` date. https://code.claude.com/docs/en/model-config.md, "Pin models for third-party deployments".
- `modelOverrides` "maps individual Anthropic model IDs to the provider-specific strings", and applies to an Anthropic ID passed "through `--model`, the `ANTHROPIC_MODEL` environment variable, or an `ANTHROPIC_DEFAULT_*_MODEL` environment variable". "The allowlist is evaluated against the Anthropic model ID, not the override value." https://code.claude.com/docs/en/model-config.md, "Override model IDs per version".
- Enterprise organization restrictions are "delivered with the account's entitlements", and "Haiku models are always available and can't be disabled". Same page, "Organization model restrictions". No hook or mod field exposes them.
- Under `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`, "Claude Code ignores provider-selection, endpoint, and authentication variables such as `CLAUDE_CODE_USE_BEDROCK` ... in settings files" and ignores managed `modelOverrides` and `ANTHROPIC_DEFAULT_*_MODEL`. https://code.claude.com/docs/en/env-vars.md

Effort caps

- `maxEffortLevel`: "Any higher level runs at the cap instead, including one from ... a skill's or subagent's `effort` frontmatter ... Claude Code applies the cap itself before each request, so it holds on every provider." Scope "Any file"; "When several scopes set a cap, the lowest applies"; a `modelSettings` entry "replaces this key for the model only within the settings source that sets both"; `"max"` sets no cap. https://code.claude.com/docs/en/settings-reference.md, `maxEffortLevel`. `effort_cap` follows each rule.
- `modelSettings` entries are written "under the model's canonical name" and Claude Code "matches that model's alias, date-suffixed, `[1m]`, and recognized provider-specific IDs to the same entry". Same page, `modelSettings`.
- Enterprise per-role caps exist too, and "When both apply to a model, the lower cap applies." https://code.claude.com/docs/en/model-config.md, "Organization effort limits". Not readable by a plugin.

Quality of the older versions an alias runs

- Haiku 4.5 to Haiku 5.5: "From 62% to 93% of attempts passed". "If you are a model or two behind, upgrade first". https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md, "Upgrade the model".

Prices

- `prices` in `models.json` match the overview table for Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5, and the cache-read rates in its notes ("2.5% on Claude Fable 5.2 and Claude Fable 5.1, 5% on Claude Opus 5.5 and Claude Sonnet 5.5"). https://platform.claude.com/docs/en/about-claude/models/overview.md. They are used for reporting only.

## Verdict

Partly right.

The alias table, the `best` and `fable` handling, the alias-only rule on the Agent tool and the full ID on `agent.spawn` all match the docs and type files, and sending the newest ID where the alias lags is the documented way to reach a newer model, which serves quality first. The list rules in `allowlist.py` are a faithful copy for the Anthropic API, but they assume the newest-permitted-version substitution on every provider, which the docs limit to the Anthropic API and Claude Platform on AWS, so on Bedrock, Agent Platform, Foundry and Google Cloud the plugin can count a family as usable that Claude Code will swap for the parent's model. Most of the layer repeats what Claude Code already enforces for every subagent, teammate and workflow agent (lists with a fallback, effort caps before each request), and the file-reading half can never see server-managed settings, MDM or organization restrictions, so it costs a lot of code for a narrow gain. When a newest ID is refused, the registry keeps ranking the lagging family (Haiku 4.5, Sonnet 4.5) as if it were the 5.5 model, which the platform figures say is a large quality drop.

## What to change

1. Make the blocked-family test provider-aware. In `allowlist._blocked_family` and `Allowlist.permitted`, count the alias as still usable after a version is blocked only on the Anthropic API and Claude Platform on AWS. On other providers, a family is usable only if the version its alias resolves to is permitted, or a permitted full ID can be sent in its place. This needs the alias table as versions per provider, not only as `older_aliases` flags, so `models.json` `older_aliases` becomes a table of resolved IDs per provider and family. It deletes the comment's claim that "Claude Code moves the alias to the newest permitted version" on every provider. Required by source: https://code.claude.com/docs/en/model-config.md ("Restrict model selection") and https://code.claude.com/docs/en/agent-teams.md ("Specify teammates and models").
2. Treat the provider as unknown, and send aliases only, when `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` is set. In `settings._provider` and `settings.Options`, the switch would make `newest_id` return None. The docs say Claude Code ignores `CLAUDE_CODE_USE_*` from settings files in that mode, so the plugin's guess at the provider can be wrong, and the host's alias table is not documented. The gap is required by source (https://code.claude.com/docs/en/env-vars.md); the remedy is judgment.
3. Drop the settings-file reader and read the lists only from the engine. Delete `file_layers`, `_policy`, `_local`, `_repository_root`, `_load`, `_first_line`, `MANAGED_ROOTS`, `managed_root` and the `floor` logic in `from_layers` and `read` (about 150 lines and their tests). With no engine read, run with no list filter and let Claude Code's own fallback act, then learn from `resolvedModel` as `hooks.post_agent` already does. The reason: Claude Code enforces the list on every subagent model and falls back instead of failing, and the files miss server-managed settings, MDM and organization restrictions. Under first-wins, the file floor is also stricter than what Claude Code applies, which can push a pick down for no reason. Judgment, backed by https://code.claude.com/docs/en/sub-agents.md ("When an allowlist blocks a subagent model") and https://code.claude.com/docs/en/managed-settings.md.
4. Stop ranking a lagging family at full strength. When `newest_id` returns None on a provider whose alias for that family lags (a strike, a `modelOverrides` map, or a list that rules out the newest ID), `Registry.available` should drop that family from automatic picks, or `select` should move the level one family up. For example, a lookup runs on the newest permitted Sonnet, not on Haiku 4.5. Leave out the case where the user pinned the family with `ANTHROPIC_DEFAULT_<FAMILY>_MODEL`. Judgment, backed by https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence.md ("Upgrade the model": Haiku 4.5 62% vs Haiku 5.5 93%).
5. Optional, for the owner to decide: on any provider, send the newest full ID when the parent runs an older version of the same family, since the alias then runs the parent's version. This would go in `registry.newest_id` and `mod._newest`, using `parentModel` from the spawn event, under the same pin, list and health checks. Judgment, backed by https://code.claude.com/docs/en/sub-agents.md ("Which version a model alias selects": "To run another version, set a full model ID"). Counter-point: the user may have chosen the older version on purpose.

No change is needed to `effort_cap` and `router.capped`. Claude Code enforces the cap itself, so the plugin only uses it to know when an effort climb cannot rise and to report the level honestly, and the rules it copies match the settings reference.

## What the sources do not say

- Whether a model a mod sets in `agent.spawn` is checked against `availableModels` and `deniedModels`, and which fallback applies if not. The docs list "the Agent tool's `model` parameter", and the mod's value replaces it, but no page or type comment says the mod's value is checked. Not documented.
- Whether `modelOverrides` maps a full Anthropic ID that a subagent definition or a mod names. The docs name `--model`, `ANTHROPIC_MODEL` and the `ANTHROPIC_DEFAULT_*_MODEL` variables only. Not documented, which is why `permits_id` refusing under any `modelOverrides` is a safe default and not a rule from a source.
- Whether the Bedrock Invoke API, as Claude Code maps it, serves Sonnet 5.5 and Haiku 5.5. The overview's Bedrock column shows the `bedrock-mantle` IDs for these models. Not documented for Claude Code's Invoke mapping.
- What aliases resolve to behind an LLM gateway (`ANTHROPIC_BASE_URL`) other than the apps gateway's `fable`. Not documented. The plugin sends aliases there, which is the safe reading.
- What aliases resolve to on a host that sets `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`. Not documented.
- Whether a subagent's request for a model the account has not turned on fails, falls back, or triggers Bedrock's availability fallback. The docs describe startup checks for the session's default models only. Not documented.
- Whether the `effort` on `turn.step` is the level after `maxEffortLevel` and organization caps. The type file implies it for forks ("The result's `effort` is what was sent"), but not for `turn.step`. Not documented.
- Enterprise organization model restrictions and per-role effort caps: no hook, mod method or settings source exposes them. Not documented as readable.
- Prices on Bedrock, Agent Platform and Foundry: the overview points to "per-platform pricing", and `models.json` holds Anthropic API prices only, so reports on those providers are list-price estimates.
