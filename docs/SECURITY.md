# Security

Checked against the code on 2026-11-24, with Claude Code behavior as documented for 2.1.330. References use module, function, class and constant names, so an edit elsewhere in a file can't make one wrong. Python modules are in `plugins/model-router/scripts/modelrouter/`. `SecurityClaims` in `tests/test_model_router.py` reruns this page's main claims on every change.

## Reporting a problem

GitHub private vulnerability reporting is not turned on for this repository yet, so there is no private channel. Until there is, open an issue titled "Security contact" with no details in it, and the maintainer will reply with a private way to send them. Do not put a vulnerability, a repro or a secret in a public issue.

## What the plugin does

- It reads hook and mod event payloads, its own JSON state, the user's and the project's `model-router.json`, the settings sources for `availableModels` and `deniedModels`, and agent `.md` frontmatter (`agents.parse`). It runs no code from the repository it works in.
- The launcher starts Python with `-I`, so a `PYTHONPATH`, `PYTHONHOME` or user site that a repository's settings `env` block sets for hook processes can't load code ahead of the standard library or the plugin's own package (`scripts/model-router.sh`).
- From each settings source the mod passes only `availableModels`, `deniedModels`, `availableModelsMatch`, `modelOverrides`, `maxEffortLevel` and each `modelSettings` entry's `maxEffortLevel`, never `env` or any other key (`effortCaps` in `hooks/router.ts`, `allowlist.remember`). A read that fails or takes over two seconds is left out, and the runtime keeps what it last had for that source, else reads the file. A source that took over two seconds is read without waiting from then on, and its newest answer goes with each later command. An allow list is cut to 200 entries of 200 characters; a policy deny list over that size is unreadable and leaves no model open.
- The managed files bound the answer when the engine reports no policy. When it does, that answer stands, since under Claude Code's default `first-wins` it can skip these files, and the mods guard keeps other mods from rewriting it; only the files' `maxEffortLevel`, which Claude Code reads from every admin source, still applies, and only when that policy sets none, since a `policyHelper`'s output replaces every admin source (`allowlist.read`). A managed file with content that is unreadable or malformed, or a policy list key that isn't a list, leaves no model open; an empty one, or a folder among the drop-ins, is no policy (`allowlist.from_layers`, `allowlist._policy`). A settings file must be a regular file of at most 1 MiB, so a symlink to a device can't hang a hook. The managed folder is fixed per OS and never comes from an environment variable, since a trusted repository's `env` block reaches hook processes (`allowlist.managed_root`).
- The local settings file is read at the repository root only when the root, its `.git` and its `.claude` belong to the current user, and never on Windows or for the home folder. A worktree's root comes only from the layout git writes (`allowlist._repository_root`).
- It writes only under its data directory: `CLAUDE_PLUGIN_DATA`, or `~/.claude/plugins/data/model-router-local` when that is unset (`store.data_dir`).
- On an agent call it sets `model` and `effort`. On a model request it sets `effort`. The effort is one of the five levels in `config.EFFORTS`. The model is a name from the merged registry: `config/models.json` plus models the user's or the repository's `model-router.json` adds (`config.load`).
- One exception, on the mod path only: when the `CLAUDE_CODE_USE_*` switches select a provider whose alias for the decided family runs an older model (`settings.resolve`, `older_aliases` in `config/models.json`), `mod.spawn` sends that family's newest full Claude API ID from `newest`, such as `claude-sonnet-5-5`. It never sends an ID outside the decided family, and none when `ANTHROPIC_DEFAULT_<FAMILY>_MODEL`, `modelOverrides`, `availableModels` or `deniedModels` rules the version out, when the caller or agent named an exact version, or while that ID is routed around after a model error (`mod._newest`, `Registry.newest_id`, `allowlist.Allowlist.permits_id`). `newest` and `older_aliases` come from the shipped file alone: `config._clean` keeps neither from a user's or a repository's file.
- It never approves a tool call. It denies one thing, on the settings-hook path only: a call it already rewrote that came back without running, when the call's own model is above the user's cap. The denial names the model to use (`fallback.route`, `fallback._guard`).

## Who can influence routing

| Source | What it can do | Limits on it |
| :- | :- | :- |
| The user's `~/.claude/model-router.json` and plugin options | Everything, including the cap. | None: it is the user's own file. |
| A repository's `.claude/model-router.json` | Add models, raise levels, raise agents with rules. | `_clean` keeps only well-formed `models`, `levels` and `agents`, and `config.build` lists what it dropped (`Registry.problems`), such as a `routing_mode`, which only `/config` sets. A `models` or `agents` key that isn't a short plain name (`config._PLAIN_NAME`), or a `levels` key that isn't a level, is dropped with a fixed note that doesn't repeat it, since names reach the output of `/model-router:route`, which Claude can run. A model whose name sits inside or around a trusted model's name is dropped. The router never picks a project model, whatever it claims, so one runs only when a call or the user's own rule names it (`Model.project`, `Registry.select`, `router.decide`), and it never stands in for a model that can't run (`Registry.clamp`), or counts at all under a cap (`Registry.available`). A level's `needs` and `effort` can be raised, never lowered: a lower value is dropped without an error (`config._raises_only`), and a `needs` that isn't a finite number is dropped from every file (`config._number`). An agent rule only raises: `level` is a floor, `model` applies only when it isn't weaker than what the call would run on without it, and `route: false` is ignored (`config._rules`). The ledger's `held` field and `/model-router:models` list what was held (`Registry.held`). With no cap set, a raised level or a model a call passes to the `Agent` tool can raise cost. `max_tier` caps the model of every pick, not the effort: `Registry.available` drops models above the cap from what `ladder.pick` and `Registry.select` choose from, and `Registry.clamp` lowers a model named on the call, by a rule or by a pin. More in [Architecture, Trust](ARCHITECTURE.md#trust). |
| Prompt and brief text | Raise or lower its own level by its wording. | Every target passes `Registry.clamp` against the usable models, which apply the cap (`router.decide`, `Registry.available`). A model named in a prompt only adds a reminder for Claude (`request.named_model`, written as a note in `hooks.user_prompt`). A message another Claude session or a teammate delivers isn't read as the user's request (`intake.is_user_prompt`). Wording can't get past a cap, and with none set it can raise cost. |
| Other plugins | Their agents are routed like any other. Their hooks and mods run in their own order. | The router never changes which agent runs. Another plugin's deny or ask still applies. |

## Network

The plugin opens no connection. No shipped Python module imports `urllib`, `http`, `socket` or `ssl`, the mod makes no `$.http` request, and the manifest declares no `network` hosts (`SecurityClaims.test_nothing_shipped_opens_a_connection`). No prompt, brief, path, code or ledger content leaves the machine. Two of the plugin's agents can reach the web through Claude Code's own tools, under your permission rules: `architect` has `WebFetch`, and `docs-researcher` has `WebFetch` and `WebSearch`.

New Claude Code releases, docs changes and model retirements are checked in this repository's CI by `tools/upstream_check.py`, which the marketplace doesn't install (see GitHub workflows below). What it finds reaches users as a plugin update.

## State files

- Writes are atomic: a unique temp file, then a rename (`store.write_atomic`). A read-modify-write takes a lock file and waits up to 1 second for it, with backoff, taking over a lock older than 10 seconds. If it still can't get the lock, it skips that write and counts it: a hook never hangs a session or writes without the lock, and the skip loses that one update (`store.locked`, `store.LOCK_WAIT_SECONDS`, `store.LOCK_STALE_SECONDS`).
- Each shared state file carries a `schema` version (`store.SCHEMA`, `store.DURABLE`). One that fails to parse is moved aside as `<name>.corrupt-<UTC timestamp>` before it is replaced, and the three newest copies of each file are kept (`store._set_aside`, `store.KEEP_SET_ASIDE`). One from a newer release, or one that can't be read, is never written (`store.try_update`). `/model-router:models` lists both. A per-session file carries no version and is replaced when it fails to parse.
- A hand-edited or corrupted state file can change routing decisions, health records and the spend report. It can't run code or get past the cap, since every target is clamped again on each call.
- The ledger keeps the first 120 characters of each agent call's description (`ledger.spawn`), plus session ids, levels, signals, reasons, model names, token counts and Claude Code's cost estimate per subagent. Briefs and prompts are not stored: a repeated call is recognized by a hash (`calls.identify`). The data folder is set to mode 0700 and the files the Python runtime writes there are created 0600 (`store.data_dir`, `store._private_file`), so other local users can't read them. Ledger rows older than 30 days, Claude Code's default `cleanupPeriodDays`, are dropped (`store.append_ledger`). Claude Code's own retention sweep and `claude purge` don't reach the plugin's data folder ([.claude directory](https://code.claude.com/docs/en/claude-directory.md)); uninstalling the plugin from the last place it is installed deletes it ([plugins reference](https://code.claude.com/docs/en/plugins-reference.md)).
- `usage --json` and `models --json` print model names, statuses, counts, Claude Code's dollar estimates and state file paths, never brief text.

## The mod

`hooks/router.ts` holds no routing logic. It runs `sh <plugin root>/scripts/model-router.sh <command>` with an argument array, so no shell parses the input, and sends the event as JSON on stdin with an 8-second timeout (`ask`). `ask()` never throws, and every hook has a `.catch` that passes the event on unchanged. Its in-memory maps keep at most 500 entries (`KEPT`). At a subagent's turn end it reads that agent's entry from `$.agent.list()` and the session's rate-limit kinds from `$.session.usage()`, and sends on only the agent's type, its tokens per model and its dollar estimate (`agentUsage`). It never blocks or rewrites a prompt. Its one file write is an empty mark under `mod-calls/` in `CLAUDE_PLUGIN_DATA` for each `Agent` call while its runtime answers, named by the call's `tool_use_id`, and only when that id is 1 to 128 letters, digits, `_` or `-` (`PLAIN_ID`), so it can't name a path outside that folder. The fallback checks the same pattern before it removes a mark (`mod.routes`).

## Skills

Each skill's `allowed-tools` pre-approves only the launcher commands that skill runs, with the fixed `--data-dir "${CLAUDE_PLUGIN_DATA}"` prefix (the frontmatter of `skills/*/SKILL.md`): `route` runs `policy *` and `explain *`, `models` runs `models *`, and `usage` runs `usage *`. A grant applies for the turn that invokes the skill (https://code.claude.com/docs/en/skills.md#pre-approve-tools-for-a-skill). Claude Code checks each part of a compound command and an output redirect against your file rules on its own (https://code.claude.com/docs/en/permissions.md), so no grant covers a write to another file. `SkillGrants.test_each_skill_may_run_its_own_commands_and_nothing_that_writes_files` checks this.

`usage` and `models` pass `$ARGUMENTS` to their `!` shell lines unquoted. Both have `disable-model-invocation: true`, so only text the user typed reaches those lines. The `models` and `route` lines also pass each option as `--<option>='${user_config.<option>}'`, which Claude Code fills from your user or managed settings only, never a repository's (https://code.claude.com/docs/en/settings-reference.md#pluginconfigs).

## GitHub workflows

Every action in all three workflows is pinned to a commit SHA.

- `ci.yml` has `contents: read` (its top-level `permissions`). Its `validate` job installs `@anthropic-ai/claude-code` from npm at 2.1.329, 2.1.331 and `latest` (the job's `matrix`), and its `eval` job installs 2.1.331 when started by hand and `latest` on its weekly run. The `version` job reads only git history. The `typecheck` job downloads Claude Code's published mod types at a pinned commit and installs `typescript` and `@types/node` at pinned versions (`tests/mod/typecheck.sh`). With read-only contents, a bad release could fail CI and can't change the repository.
- `ci.yml`'s `eval` job runs when started by hand (`workflow_dispatch`) and once a week on `main` (`schedule`), and it is the only job given a secret: `ANTHROPIC_API_KEY`, for the live model calls of `claude plugin eval`, with `--max-cost-usd 2` as a ceiling on the estimated list-price cost (https://code.claude.com/docs/en/plugin-evals.md#command-options). It runs the checked-out branch's plugin code with `--trust-plugin`, so start it only on a branch you trust.
- `upstream-watch.yml` runs daily and by hand with `contents: read` and `issues: write`. It runs `tools/upstream_check.py`, which reads public docs pages and sends no credential. It creates or edits one issue, and fetched text goes into the issue body through a file, never into a shell command. Its only secret is `github.token` (the `GH_TOKEN` env). Its `newest` job installs `@anthropic-ai/claude-code@latest` and downloads the newest published mod types, so it has only `contents: read`.
- `pages.yml` runs on pushes to `main` that touch `site/**`, `docs/assets/**` or `pages.yml`, and by hand. It has `contents: read`, and only its `deploy` job adds `pages: write` and `id-token: write`. It uses no secret.
