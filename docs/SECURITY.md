# Security

Checked against the code on 2026-11-25, with Claude Code behavior as documented for 2.1.331. References use module, function, class and constant names, so an edit elsewhere in a file can't make one wrong. Python modules are in `plugins/model-router/scripts/modelrouter/`. `SecurityClaims` in `tests/test_model_router.py` reruns this page's main claims on every change.

## Reporting a problem

GitHub private vulnerability reporting is not turned on for this repository yet, so there is no private channel. Until there is, open an issue titled "Security contact" with no details in it, and the maintainer will reply with a private way to send them. Do not put a vulnerability, a repro or a secret in a public issue.

## What the plugin does

- It reads hook and mod event payloads, its own JSON state, the user's and the project's `model-router.json`, the settings sources the mod reads from Claude Code for `availableModels` and `deniedModels`, agent `.md` frontmatter (`agents.parse`), Claude Code's plugin install records to find another plugin's agents (`agents.installed_roots`, `agents._listed`), and the tail of the session's and a subagent's transcript: the last 512 KiB for the model the conversation runs on, and the last 1 MiB for check commands and a `SubagentHandback` report (`session.transcript_tail`, `session.tool_calls`). It runs no code from the repository it works in.
- The launcher starts Python with `-I`, so a `PYTHONPATH`, `PYTHONHOME` or user site that a repository's settings `env` block sets for hook processes can't load code ahead of the standard library or the plugin's own package (`scripts/model-router.sh`). `sh` and `python3` are still the first ones on `PATH`, which that block can also set ([settings `env`](https://code.claude.com/docs/en/settings-reference.md)).
- From each settings source the mod passes only `availableModels`, `deniedModels`, `availableModelsMatch`, `modelOverrides`, `maxEffortLevel` and each `modelSettings` entry's `maxEffortLevel`, never `env` or any other key (`effortCaps` in `hooks/router.ts`, `allowlist.remember`). A read that fails or takes over two seconds is left out, and the runtime keeps what it last had for that source. It never reads a settings file itself. A source that took over two seconds is read without waiting from then on, and its newest answer goes with each later command. An allow list is cut to 200 entries of 200 characters; a policy deny list over that size is unreadable and leaves no model open.
- A policy list key that isn't a list leaves no model open (`allowlist.from_layers`). Another mod that blanks the policy the router sees can widen only what the router picks: Claude Code still enforces the lists on every subagent model.
- It writes only under its data directory: `CLAUDE_PLUGIN_DATA`, or `~/.claude/plugins/data/model-router-local` when that is unset, with `CLAUDE_CONFIG_DIR` in place of `~/.claude` when that is set (`store.data_dir`, `store.claude_home`). The one write outside it is Python's own: on a Python that writes bytecode, such as 3.13, each hook's imports write `.pyc` files into `scripts/modelrouter/__pycache__` inside the plugin's install folder. `-I` makes Python ignore `PYTHONPYCACHEPREFIX` and `PYTHONDONTWRITEBYTECODE`, and the plugin doesn't turn bytecode off itself. Apple's Command Line Tools Python 3.9.6 writes none.
- On an agent call it sets `model` and `effort`. On the mod path it also sets the effort of each model request a subagent makes to the one its spawn got (`turn.step` in `hooks/router.ts`). It never changes the main conversation's effort. The effort is one of the five levels in `config.EFFORTS`. The model is a name from the merged registry: `config/models.json` plus models the user's or the repository's `model-router.json` adds (`config.load`). A call that names its effort too, and that the cap doesn't lower, is left as it is.
- Two exceptions, on the mod path only, send a full ID. When a call or an agent names an exact model ID, such as `claude-sonnet-5-1`, or a `[1m]` variant, and the router rewrites the call within that family, `mod.spawn` sends that exact version while the allow and deny lists permit it and it hasn't failed here (`mod.exact`, `allowlist.Allowlist.permits_named`). It is always one the call or the agent definition already named. The fallback then leaves the call's own model (`fallback._rewritten_input`). Otherwise a rewrite carries the family alias (`sonnet`), on both paths (`router.decide`). And when the `CLAUDE_CODE_USE_*` switches select a provider whose alias for the decided family runs an older model (`settings.resolve`, `older_aliases` in `config/models.json`), `mod.spawn` sends that family's newest full Claude API ID from `newest`, such as `claude-sonnet-5-5`. It never sends an ID outside the decided family, and none when `ANTHROPIC_DEFAULT_<FAMILY>_MODEL`, `modelOverrides`, `availableModels` or `deniedModels` rules the version out, when the caller or agent named an exact version (that call gets that version or the alias, as above), when `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` is set, or while that ID is routed around after a model error (`mod._newest`, `Registry.newest_id`, `allowlist.Allowlist.permits_id`). `newest` and `older_aliases` come from the shipped file alone: `config._clean` keeps neither from a user's or a repository's file.
- It never approves a tool call. It denies one thing, on the settings-hook path only: a call it already rewrote that came back without running, when the call's own model is above the user's cap. The denial names the model to use (`fallback.route`, `fallback._guard`).
- The cap holds for every registry model the router keeps or sets. It doesn't reach a call the router leaves as it is (`router.decide`): one that names a model outside the registry, or is for an agent whose own `model` is outside it; one that names no model, for an agent with none of its own, when the router can't see what it would run on: an agent whose definition it can't find, the built-in `Explore` or `Plan`, or, on the settings-hook path, a call made from inside a subagent (`spawn.facts` leaves the parent unknown there); one that names no model for an agent with none of its own while `CLAUDE_CODE_SUBAGENT_MODEL` is set; and any call whose model `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` or, for a workflow agent, `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` pins. A call for an agent it can't find that names a registry model is still held to the cap. Claude Code still applies `availableModels` and `deniedModels` to all of these.

## Who can influence routing

| Source | What it can do | Limits on it |
| :- | :- | :- |
| The user's `~/.claude/model-router.json` and plugin options | The file's models, levels and agent rules apply in full. The options set the routing mode, the cap (`max_tier`) and the check before a turn ends (`verify_gate`). | None: they are the user's own. `routing_mode` is set only in `/config`, so a `routing_mode` in either file is dropped (`config._clean`). |
| A repository's `.claude/model-router.json` | Add models, raise levels, raise agents with rules. | The file read is the nearest `.claude/model-router.json` from `CLAUDE_PROJECT_DIR` (else the hook's `cwd`) up to the repository root, never the home folder, and only the start folder's when the root, its `.git` or its `.claude` belongs to another user (`config.load`, `config._up_to_root`). `_clean` keeps only well-formed `models`, `levels` and `agents`, and `config.build` lists what it dropped (`Registry.problems`), such as a `routing_mode`, which only `/config` sets. A `models` or `agents` key that isn't a short plain name (`config._PLAIN_NAME`), or a `levels` key that isn't a level, is dropped with a fixed note that doesn't repeat it, since names reach the output of `/model-router:route`, which Claude can run. A model whose name sits inside or around a trusted model's name is dropped. The router never picks a project model, whatever it claims, so one runs only when a call, an agent's own `model` or the user's own rule names it (`Model.project`, `Registry.select`, `router.decide`), and it never stands in for a model that can't run (`Registry.clamp`), or counts at all under a cap (`Registry.available`). A level's `needs` and `effort` can be raised, never lowered: a lower value is dropped without an error (`config._raises_only`), and a `needs` that isn't a finite number is dropped from every file (`config._number`). An agent rule only raises: `level` is a floor, and on a call that names no model it applies only where it moves the call to a stronger model, `model` applies only when it isn't weaker than what the call would run on without it and isn't a model that file added, and `route: false` is ignored. A model the file adds matches only its exact name, never part of a longer ID (`Registry.family`). A rule's `model` value is kept as any string (`config._clean`). Where the user's own rule holds that rule, the held list in `/model-router:models` prints the value as written (`config._rules`, `report.models`), so a repository can put text of its choosing into that output, which Claude reads. Where the user's own rule sets an agent's `level` or `model`, the project's rule for that agent is held (`config._rules`, `router.decide`). The ledger's `held` field and `/model-router:models` list what was held (`Registry.held`). With no cap set, a raised level or a model a call passes to the `Agent` tool can raise cost. `max_tier` caps the model, not the effort: `Registry.available` leaves models above the cap out of the usable list, and `Registry.clamp` lowers to it a model named on the call, by a rule or by a pin, and the model a rule's level or a redo moves to. More in [Architecture, Trust](ARCHITECTURE.md#trust). |
| Prompt and brief text | The router reads no brief to pick a model or effort: Claude names them on each call, so text Claude reads can sway what it names. A `description` that starts with "Redo:" makes a call climb, effort before model, unless it names more for itself, from the last finished run of its task in the last 30 minutes, or from what it would run at unmarked when none is on record (`calls.marked_redo`, `calls.REDO_WINDOW`, `router._redo`, `spawn._unmarked_run`). A workflow stage is never redone (`spawn.facts`). | Every registry model a call names, and every redo's model, passes `Registry.clamp` against the usable models, which apply the cap (`router.decide`, `Registry.available`). A model named in a prompt only adds a note for Claude (`request.named_model`, `hooks.user_prompt`). A message another Claude session or a teammate delivers isn't read as the user's request (`intake.is_user_prompt`). A named model or a redo can't get past a cap, and with none set either can raise cost. |
| A repository's `.claude/settings.json` | Its `availableModels`, `maxEffortLevel` and model `env` variables, such as `CLAUDE_CODE_SUBAGENT_MODEL`, steer Claude Code, and the router follows them (`allowlist.from_layers`, `router._pinned`). | Outside managed settings Claude Code joins the `availableModels` lists, so a repository can add to the user's. It can't widen a managed list or `deniedModels`, and it can't raise a `maxEffortLevel`, since the lowest one applies ([model config](https://code.claude.com/docs/en/model-config.md), [settings](https://code.claude.com/docs/en/settings-reference.md)). Its `env` block can set `CLAUDE_CODE_SUBAGENT_MODEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` and `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL`: Claude Code applies a project's `env` once you trust the folder, and variables it classes as safe, model selection among them, at startup ([settings `env`](https://code.claude.com/docs/en/settings-reference.md)). The router doesn't lower a model those set (see the cap above), so a cloned repository can run subagents above your `max_tier`. Under FORCE the session-start note, which Claude reads, names the `CLAUDE_CODE_SUBAGENT_MODEL` value only when it is a short plain name (`config._PLAIN_NAME`, `hooks._rules`), and `/model-router:models` names the `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL` value the same way (`report.models`). On the settings-hook path the router reads its own options from `CLAUDE_PLUGIN_OPTION_ROUTING_MODE`, `CLAUDE_PLUGIN_OPTION_MAX_TIER` and `CLAUDE_PLUGIN_OPTION_VERIFY_GATE` in the hook's environment (`settings.resolve`), and Claude Code's docs don't say whether an `env` block can set those over the values Claude Code exports. On the mod path the options Claude Code gives the mod replace any such variable (`optionEnv` and `ask` in `hooks/router.ts`). |
| Other plugins | Their agents are routed like any other. Their hooks and mods run in their own order. | The router never changes which agent runs. Another plugin's deny or ask still applies. |

## Network

The plugin opens no connection. No shipped Python module imports `urllib`, `http`, `socket` or `ssl`, the mod makes no `$.http` request, and the manifest declares no `network` hosts (`SecurityClaims.test_nothing_shipped_opens_a_connection`). What it puts into Claude's context goes to the model provider with the rest of the conversation, as Claude Code sends it: the session-start note, the prompt, fallback, failure and Stop notes, and the output of its skills. That output includes ledger rows (agents, models, tokens and dollar estimates) from `/model-router:usage` and the full paths of state files from `/model-router:models` (`report.usage_data`, `report.models_data`). Its five agents use Claude Code's own tools, under your permission rules: `scout` and `reviewer` have `Read`, `Grep` and `Glob`, `architect` has those and `WebFetch`, `verifier` has those and `Bash`, and `implementer` lists no `tools`, so it gets every tool the session has, `WebFetch` and `WebSearch` among them ([sub-agents](https://code.claude.com/docs/en/sub-agents.md)).

New Claude Code releases, docs changes and model retirements are checked in this repository's CI by `tools/upstream_check.py`, which the marketplace doesn't install (see GitHub workflows below). What it finds reaches users as a plugin update.

0.1.2 ran a daily fetch on your machine instead, behind its `update_check` option, which was on by default: an async `SessionStart` hook read public docs pages and, when `ANTHROPIC_API_KEY` was set and neither `ANTHROPIC_BASE_URL` nor a cloud provider was, called the Models API with that key, and kept what it found in `upstream.json`. Its manifest declared `code.claude.com`, `platform.claude.com` and `api.anthropic.com` as `network` hosts. This release removes all of it. A saved value for one of the five removed options (`priority`, `agent_pins`, `main_effort`, `update_check`, `strong_agent_gate`) is ignored: the plugin reads only `routing_mode`, `max_tier` and `verify_gate` (`settings.OPTIONS`, `settings.resolve`).

## State files

- Writes are atomic: a unique temp file, then a rename (`store.write_atomic`). A read-modify-write holds the OS's lock (`fcntl.flock`, or `msvcrt.locking` on Windows) on a `<name>.flock` file beside the state file, and waits up to 1 second for it, trying again at most every 10 ms (`store.locked`, `store.LOCK_WAIT_SECONDS`, `store.LOCK_POLL_MAX`). A process that dies lets go of its lock at once, so no lock goes stale. If the lock is still held after the wait, the write is skipped and counted in `locks.json`: a hook never hangs a session, and the skip loses that one update. On a POSIX filesystem that can't lock at all, the write goes ahead without one. The lock file stays on disk. A process that takes the lock writes its session id into it and empties it on release; one killed while it held the lock leaves its id there until the next process takes the lock.
- Each shared state file carries a `schema` version (`store.SCHEMA`, `store.DURABLE`). One that fails to parse is moved aside as `<name>.corrupt-<UTC timestamp>` before it is replaced, and the three newest copies of each file are kept (`store._set_aside`, `store.KEEP_SET_ASIDE`). One from a newer release, or one that can't be read, is never written (`store.try_update`). `/model-router:models` lists both. `locks.json` is the exception: its only writer, `store._count`, skips a copy that fails to parse, so a corrupt `locks.json` is never moved aside or replaced, lock counts stop being kept, and `/model-router:models` doesn't list it. Deleting it starts the counts again. A per-session file carries no version and is replaced when it fails to parse.
- A hand-edited or corrupted state file can change routing decisions, health records and the spend report. It can't run code or get past the cap, since every target is clamped again on each call.
- The health table in `state.json` is shared by every project. A model whose calls fail twice with a model error (`health.MODEL_ERROR`, which matches only the API's error type names, and never in Claude Code's unknown-agent-type error, which echoes the type Claude wrote and every agent's name), or run twice as another model, is routed around in every project for up to a day (`health.failed`, `health.ran`, `health.OUTAGE`). A failure on an exact model ID that a call or an agent named, and that the router left as it is, strikes nothing (`calls._failed`). A provider's refusal text (`health.REFUSED`) strikes only a full ID the router sent, never an alias.
- The ledger keeps session and agent ids, agent names, levels, reasons, model names, token counts and Claude Code's cost estimate per subagent (`ledger.spawn`, `ledger.usage`). Briefs, prompts and descriptions are not stored: a call is recognized by a hash of its agent and prompt (`calls.identify`), and its task by a hash of its agent and description (`calls.task`). A session's records in `routes.json`, `done.json` and `launched.json` are dropped at the first write to the file once that session has gone a day without one (`calls.KEPT_FOR`), and a record goes sooner when 100 newer ones of its session push it out (`store.KEPT_RECORDS`). Every per-session file keeps only its 200 most recently written sessions (`store.KEEP_ENTRIES`). 0.1.2 kept the first 120 characters of each call's description, and the names of the brief signals its scorer matched, in every `ledger.jsonl` spawn row. After an upgrade those rows stay until they pass 30 days, when a later append drops them, or until the 4 MiB halving does. Files 0.1.2 wrote that this release never reads, writes or removes stay in the data folder until you delete them: `learned.json`, `upstream.json`, `mod.json`, `prompts.json` and the `<file>.json.lock` lock files. The data folder is set to mode 0700 and the files the Python runtime writes there are created 0600 (`store.data_dir`, `store._private_file`), so other local users can't read them. Ledger rows older than 30 days, Claude Code's default `cleanupPeriodDays`, are dropped (`store.append_ledger`). Claude Code's own retention sweep and `claude purge` don't reach the plugin's data folder ([.claude directory](https://code.claude.com/docs/en/claude-directory.md)); uninstalling the plugin from the last place it is installed deletes it ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference.md)).
- `usage --json` and `models --json` print model names, statuses, counts, Claude Code's dollar estimates and state file paths, never brief text.

## The mod

`hooks/router.ts` picks no model or effort. The runtime does, and the mod applies the answer, skips forks and resumed agents, only ever raises a workflow agent's effort, and gives a subagent whose first request goes out before its spawn hook has its id the effort of the spawns then in flight with the same prompt, only when they all got the same one. It runs `sh <plugin root>/scripts/model-router.sh <command>` with an argument array, so no shell parses the input, and sends the event as JSON on stdin with an 8-second timeout (`ask`). `ask()` never throws, and every hook has a `.catch` that passes the event on unchanged. Its in-memory maps keep at most 500 entries (`KEPT`). For each spawn it sends the call's agent, prompt, description, model and effort to the runtime, which keeps only hashes of the prompt and description. At a subagent's turn end it reads that agent's entry from `$.agent.list()` and the session's rate-limit kinds from `$.session.usage()`, and sends on only the agent's type, its tokens per model, its dollar estimate and whether the session has plan limits (`agentUsage`). For a workflow agent the engine doesn't list, it sends that turn's tokens. It never blocks or rewrites a prompt. Its one file write is an empty mark under `mod-calls/` in `CLAUDE_PLUGIN_DATA` for each `Agent` call while its runtime answers, named by the call's `tool_use_id`, and only when that id is 1 to 128 letters, digits, `_` or `-` (`PLAIN_ID`), so it can't name a path outside that folder. The fallback checks the same pattern before it removes a mark (`mod.routes`).

## Skills

Each skill's `allowed-tools` pre-approves only the launcher commands that skill runs, with the fixed `--data-dir "${CLAUDE_PLUGIN_DATA}"` prefix (the frontmatter of `skills/*/SKILL.md`): `route` runs `policy *` and `explain *`, `models` runs `models *`, and `usage` runs `usage *`. A grant applies for the turn that invokes the skill (https://code.claude.com/docs/en/skills.md#pre-approve-tools-for-a-skill). Claude Code checks each part of a compound command and an output redirect against your file rules on its own (https://code.claude.com/docs/en/permissions.md), so no grant covers a write to another file. `SkillGrants.test_each_skill_may_run_its_own_commands_and_nothing_that_writes_files` checks this.

`usage` and `models` pass `$ARGUMENTS` to their `!` shell lines unquoted. Both have `disable-model-invocation: true`, so only text the user typed reaches those lines. The `models` and `route` lines also pass each option as `--<option>='${user_config.<option>}'`, which Claude Code fills from your user or managed settings only, never a repository's (https://code.claude.com/docs/en/settings-reference.md#pluginconfigs).

## GitHub workflows

Every action in all three workflows is pinned to a commit SHA.

- `ci.yml` has `contents: read` (its top-level `permissions`). Its `validate` job installs `@anthropic-ai/claude-code` from npm at 2.1.329, 2.1.331 and `latest` (the job's `matrix`), and its `eval` job installs 2.1.331 when started by hand and `latest` on its weekly run. The `version` job reads only git history. The `typecheck` job downloads Claude Code's published mod types at a pinned commit and installs `typescript` and `@types/node` at pinned versions (`tests/mod/typecheck.sh`). With read-only contents, a bad release could fail CI and can't change the repository.
- `ci.yml`'s `eval` job runs when started by hand (`workflow_dispatch`) and once a week on `main` (`schedule`), and it is the only job given a secret: `ANTHROPIC_API_KEY`, for the live model calls of `claude plugin eval`, with `--max-cost-usd 2` as a ceiling on the estimated list-price cost (https://code.claude.com/docs/en/plugin-evals.md#command-options). It runs the checked-out branch's plugin code with `--trust-plugin`, so start it only on a branch you trust.
- `upstream-watch.yml` runs daily and by hand with `contents: read` and `issues: write`. It runs `tools/upstream_check.py`, which reads public docs pages and sends no credential. It creates or edits one issue, and fetched text goes into the issue body through a file, never into a shell command. Its only secret is `github.token` (the `GH_TOKEN` env). Its `newest` job installs `@anthropic-ai/claude-code@latest` and downloads the newest published mod types, so it has only `contents: read`.
- `pages.yml` runs on pushes to `main` that touch `site/**`, `docs/assets/**` or `pages.yml`, and by hand. It has `contents: read`, and only its `deploy` job adds `pages: write` and `id-token: write`. It uses no secret.
